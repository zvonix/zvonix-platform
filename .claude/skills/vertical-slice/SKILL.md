# Вертикальный срез

Новая функциональность делается целиком и по образцу, а не слоями и не «как захотелось».
Так каждая следующая фича делается быстрее предыдущей, а проект остаётся однородным.

## Порядок

1. **Разведка.** Если область незнакома — сначала `explore-area`.
   Обязательный результат: найден **эталон** — ближайшая существующая фича той же формы.

2. **Спроектировать срез до кода.** Перечислить, что войдёт в изменение:
   входная точка (эндпоинт / команда / обработчик) → валидация входа → слой логики →
   доступ к данным → модель/схема → миграция → тесты → документация.
   Если чего-то из списка не будет — сказать, почему.

3. **Проверить пороги остановки** (правило 3 в `CLAUDE.md`).
   Меняется схема БД, публичный контракт или архитектурная граница → сначала согласовать
   и завести ADR, только потом код. Мелкие развилки — решить и записать допущение.

4. **Реализовать по эталону.** Та же структура файлов, то же именование, тот же способ
   обработки ошибок и тот же стиль тестов, что у эталона. Отклоняться только там, где
   для этого есть причина — и назвать её.

5. **Тесты в том же срезе, не потом.** Как минимум: успешный путь, отказ валидации,
   отказ зависимости (недоступна БД / внешний сервис). Тесты по образцу тестов эталона.

6. **Проверка.** Прогнать полную проверку (`/check`), показать вывод.

7. **Закрыть хвосты.** Обновить `docs/` при изменении поведения или контракта,
   `TASKS.md` — если что-то сознательно отложено.

## Отчёт

Что сделано (список файлов) → по какому эталону → что проверено и как →
что осталось / отложено → найденные попутно проблемы (`файл:строка`).

## Чего не делать

- Не делать «сначала все модели, потом все API» — это ломает однородность и откладывает проверку.
- Не изобретать новый паттерн, если в проекте уже есть работающий.
- Не оставлять заглушек и `TODO` без строки в `TASKS.md`.
- Не расширять срез за пределы задачи: идеи улучшений — в `TASKS.md`, не в этот коммит.
