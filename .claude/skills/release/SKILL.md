# Выпуск площадки

Выкладка применяет миграции сама и без вопросов, а откат выпуска возвращает код, но не базу
([ADR-0049](../../../docs/adr/0049-vykladka-ploshchadki.md)). Ошибка на сервере стоит дороже
любой задержки, поэтому здесь нет импровизации: каждый шаг — известная команда из
[deploy/README.md](../../../deploy/README.md), а **каждое внешнее действие** — метка, отправка
на GitHub, любая команда на сервере — **после явного «да» владельца в этом разговоре**.
Разрешение на один шаг не переносится на следующий.

Доступ к серверу — SSH-ключ, который владелец дал в этой сессии. Пароль root, токен GitHub
и пароли базы не записываются ни в файлы репозитория, ни в память, ни в отчёт.

## Порядок

1. **Что выпускаем.** Рабочее дерево чистое (`git status`), pull request слит в `main`,
   локальная `main` совпадает с `origin/main`, последний прогон CI на `main` зелёный:
   `gh run list --branch main --limit 1`. Выпуск из неслитой ветки не делается.

2. **Полная проверка** — `pnpm verify`. Готовность — только блок «Можно выпускать» в конце.
   «Выпускать рано» или красный шаг — остановиться и разобрать, а не выпускать «пока так».
   В отчёте назвать оболочку, в которой проверка прошла (правило 5 в `CLAUDE.md`).

3. **Новые миграции.** База сравнения — то, что стоит на сервере сейчас: вторая строка
   `/opt/zvonix/current/RELEASE` (`commit <sha>`). Нет такого файла — последняя метка.
   ```bash
   node scripts/migration-risk.mjs <база>
   ```
   Каждую находку пересказать владельцу простыми словами: что случится с данными.
   - «теряет данные» и «ломает работающий выпуск» — стоп: такое делается в два шага
     ([ADR-0005](../../../docs/adr/0005-migracii.md)), и решение — владельца;
   - «ПРАВКА ПРИМЕНЁННОЙ» — стоп всегда: исправление — новая миграция;
   - «может не накатиться» — проверить данными сервера, а не рассуждением: например,
     есть ли строки вне нового `CHECK`, повторы под новый уникальный индекс;
   - «запирает таблицу» — назвать размер таблицы; на пустом стенде это миллисекунды.

4. **Копия базы** — на сервере, перед выкладкой:
   ```bash
   sudo install -d -o postgres -g postgres -m 0700 /var/backups/zvonix
   sudo -u postgres pg_dump -Fc -f /var/backups/zvonix/<метка>-$(date +%Y%m%d-%H%M).dump zvonix
   sudo ls -lh /var/backups/zvonix
   ```
   Пустой или крошечный файл — копии нет, дальше не идти.

5. **Метка.** `git tag <метка> && git push origin <метка>` — строку подсказывает сама
   проверка. Затем дождаться выпуска: `gh run watch` по запуску «Release»,
   `gh release view <метка>` — у выпуска есть архив и `.sha256`.
   Выпущенную метку не переносить и не удалять: сервер сверяет архив по ней.

6. **Выкладка:** `sudo zvonix-deploy <метка>`. Успех — последняя строка `DEPLOY_OK <метка>`.
   Любая другая последняя строка значит, что скрипт уже вернул прежний выпуск сам, —
   прочитать его вывод до конца и разобрать причину, а не запускать повторно.

7. **Проверка после** — команды раздела «Проверка после выкладки» в
   [deploy/README.md](../../../deploy/README.md), плюс:
   ```bash
   systemctl is-active zvonix-api zvonix-worker zvonix-web
   journalctl -u zvonix-api -u zvonix-worker --since '-10 min' -p warning --no-pager
   ```
   Кабинет своими глазами — через туннель, если владелец хочет.

8. **Откат**, если после выкладки что-то не так: `sudo zvonix-deploy --rollback` —
   возвращает код, миграции остаются. Если сломаны данные, восстановление из копии шага 4
   (`pg_restore --clean --if-exists -d zvonix <файл>`) — **только решением владельца**:
   оно стирает всё, что записано после копии, включая вызовы и проводки.

9. **Записать** в [TASKS.md](../../../TASKS.md): метка, дата, коммит, итог, находки
   по миграциям и что по ним решили. Выяснилось новое о сервере — в
   [deploy/README.md](../../../deploy/README.md), а не только в отчёт.

## Чего не делать

- Не ставить метку при красной или не выполненной проверке.
- Не пропускать разбор миграций на том основании, что «там только индекс».
- Не восстанавливать базу из копии и не удалять копии без решения владельца.
- Не делать `force push` меток и веток.
- Не выкладывать архив, собранный на Windows: кабинет везёт зависимости под систему сборки.
