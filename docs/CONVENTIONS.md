# Соглашения

Всё, что должно выглядеть одинаково независимо от того, кто пишет код.
Правило простое: **однородность важнее личных предпочтений**.

## Ветки

- `main` — всегда рабочая. Прямые коммиты в неё не делаются.
- Рабочие ветки: `feat/<кратко>`, `fix/<кратко>`, `refactor/<кратко>`, `docs/<кратко>`.
- Ветка живёт коротко: чем дольше, тем дороже слияние.

## Коммиты

Формат Conventional Commits — он машинно разбираем и позволяет собирать changelog:

```
<тип>(<область>): <что сделано в повелительном наклонении>
```

Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`, `build`, `ci`.

- Один коммит — одно логическое изменение. Не смешивать рефакторинг с новой функциональностью:
  такой коммит невозможно ни отревьюить, ни откатить.
- Изменение схемы БД идёт вместе с миграцией и кодом, который на неё опирается.
- Ломающее изменение помечается `!` после области и описывается в теле коммита.

## Именование

- Файлы и каталоги — `kebab-case`: `partner-rate.service.ts`, `operator-resolver.ts`.
- Классы и типы — `PascalCase`, функции и переменные — `camelCase`,
  константы уровня модуля — `SCREAMING_SNAKE_CASE`.
- Таблицы и колонки в БД — `snake_case`, таблицы во множественном числе: `partner_rates`.
- **Имена файлов не должны различаться только регистром** — на Windows это работает,
  на Ubuntu ломается. Проверяется в CI.
- Имя отражает роль: `user_repository`, `call_service`. Запрещены `utils2`, `helpers`,
  `common`, `misc` — в них ничего нельзя найти поиском, а именно поиском находится код
  в большом проекте.
- Доменные термины — строго как в [GLOSSARY.md](GLOSSARY.md). Синонимы запрещены.

## Структура модуля

Одинаковая у всех модулей — тогда незнакомый модуль читается без разведки.
Модуль NestJS в `apps/api/src/modules/<имя>/`:

```
<имя>.module.ts      — сборка модуля
<имя>.service.ts     — доменная логика
<имя>.repository.ts  — доступ к данным, единственная точка обращения к БД
<имя>.controller.ts  — HTTP, если модуль его отдаёт
schemas.ts           — zod-схемы, общие с фронтендом через packages/shared
__tests__/           — тесты модуля
```

## Комментарии

- Комментарий объясняет **почему**, а не **что**: «что» видно из кода.
- Неочевидное решение, обход чужого бага, компромисс — комментируются обязательно,
  со ссылкой на ADR или задачу.
- Закомментированный код не хранится: для этого есть история git.
- `TODO` без строки в [../TASKS.md](../TASKS.md) не оставляется.

## Перед отправкой изменения

1. `bash scripts/check.sh` прошёл (запускается в WSL2).
2. Документация обновлена, если изменилось поведение или контракт.
3. ADR заведён, если принято архитектурное решение.
4. Не осталось отладочных выводов, закомментированного кода и временных заглушек.
