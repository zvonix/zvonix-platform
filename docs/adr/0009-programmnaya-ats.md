# ADR-0009: Программная АТС на узлах

- **Статус:** Предложено — требуется решение
- **Дата:** 2026-09-01

## Контекст

Узел должен: принимать SIP-регистрации GOIP-шлюзов (за NAT), принимать вызовы от клиентов,
**на каждый вызов** спрашивать маршрут у control plane, перебирать кандидатов до ответа,
писать разговор, отдавать CDR и метрики, устанавливаться одной командой и быть заменяемым.

Ключевое: вся бизнес-логика остаётся в control plane. От АТС нужна не гибкость диалплана,
а надёжное исполнение внешнего решения.

## Рассмотренные варианты

| Вариант | За | Против |
|---------|-----|--------|
| **Asterisk** (`res_pjsip` + ARI) | ARI даёт управление вызовом из внешнего кода по REST/WebSocket — точно ложится на «решение принимает control plane»; `MixMonitor` пишет разговор одной командой; отличная работа с NAT; самое большое сообщество и документация, в том числе на русском; проще найм | Потоковая модель: практический потолок — сотни одновременных вызовов на узел; выше расход памяти |
| **FreeSWITCH** | Событийная модель, тысячи вызовов на узел; `mod_xml_curl` запрашивает маршрут по HTTP на каждый вызов «из коробки»; ESL для событий | Меньше сообщество, выше порог входа, слабее документация; сложнее найм |
| **Kamailio / OpenSIPS + RTPengine** | Десятки тысяч вызовов; правильная архитектура для большого масштаба | Это SIP-прокси, а не АТС: запись и логика вызова требуют отдельного медиасервера. Для v1 — многократное усложнение без выигрыша |

## Решение (предлагается)

**Asterisk с `res_pjsip` и управлением через ARI.**

Обоснование: трафик шардируется по узлам — на один узел приходится трафик подмножества
шлюзов, и потолок Asterisk в этих условиях не достигается. Выигрыш FreeSWITCH в concurrency
не окупает разницу в скорости разработки и доступности специалистов, а ARI ложится на нашу
модель «логика снаружи» лучше, чем диалплан.

Путь роста при упоре в потолок узла: добавить Kamailio перед узлами как SIP-балансировщик,
оставив Asterisk медиасервером. Переписывать control plane при этом не потребуется — именно
ради этого логика вынесена из АТС.

## Последствия

- Положительные: быстрый старт; запись и NAT решены штатными средствами; логика вызова —
  обычный код на Python, а не диалплан, значит покрывается тестами и ревью.
- Отрицательные: потолок вызовов на узел ниже, чем у FreeSWITCH; при неверной оценке
  нагрузки придётся раньше вводить балансировщик.
- В коде: диалплан минимален и не содержит бизнес-правил; всё решение вызова — в `routing`.
