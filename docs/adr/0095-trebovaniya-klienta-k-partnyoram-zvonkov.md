# ADR-0095: Требования клиента к партнёрам для звонков

- **Статус:** Принято — 2026-10-22; владелец: «если партнёров будет много… как удобно клиентам выбирать… и то же самое со звонками»,
  «делай что рекомендуешь»
- **Дата:** 2026-10-22
- **Развивает:** [ADR-0092](0092-trebovaniya-klienta-k-akkauntam.md) (то же для MAX), [ADR-0081](0081-prioritety-partnyorov-u-klienta.md)
  (приоритеты), [ADR-0036](0036-dostup-partnyora-k-zapisyam.md) (партнёр слушает записи), [ADR-0014](0014-vybor-partnera-klientom.md)

## Контекст

Партнёров для звонков может быть сотня, у каждого — SIM и/или транк, свои тарифы по направлениям и своё решение «слушаю записи
разговоров». Сейчас клиент может только расставить цифры и отметить «не использовать» по каждому предложению вручную; новый
партнёр площадки попадает в его звонки сам (открытый список, ADR-0081), даже если по условиям клиенту не подходит. Отметку
партнёра «слушаю записи» клиент вообще нигде не видит, хотя подпись у партнёра обещает обратное.

## Решения

1. **Требования клиента к звонкам** — одна запись на клиента (`client_call_requirements`), действуют на каждый вызов всех его
   линий:
   - способ: любой / только SIM / только транк;
   - партнёр не слушает записи разговоров;
   - цена для клиента не дороже N ₽ — стоимость эталонного вызова в 60 секунд с наценкой (та же величина, что в «Ценах» и
     коридорах, ADR-0023). Проверяется **по направлению вызова**: партнёр, дешёвый на МТС и дорогой на Билайне, на МТС берётся,
     на Билайн — нет.
   Доля состоявшихся вызовов как требование — следующим шагом вместе с «доставлено не ниже» у MAX: нужна статистика с порогом
   выборки, иначе новый партнёр отсекается по трём звонкам.
2. **Ручное отключение** — прежнее «не использовать» в приоритетах (ADR-0081), отдельной таблицы нет: два способа сказать одно и то
   же разошлись бы.
3. **Таблица на странице «Приоритеты»** (звонки): рядом с ценой — «слушает записи» и «подходит ли под требования и почему нет»
   («только SIM», «слушает записи», «дороже вашего предела на всех направлениях», «часть направлений дороже предела»).
4. **Порядок выбора:** требования → приоритеты линии или клиента → цена → давность (ADR-0040). Требования сужают кандидатов,
   порядок не меняют.
5. **Новая причина отказа `requirements_unmet`** — без требований кандидат нашёлся бы. Клиенту видна как есть (это его настройка,
   ADR-0014 её не закрывает), узел отвечает `503`, как на прочие «некуда звонить». Вызов без кандидатов и без требований
   объясняется прежними причинами.
6. **Журнал:** изменение — `client_call_requirements.set`, состояние до и после.

## Хранение и горячий путь

- `client_call_requirements`: клиент (уникально), способ (`sim`/`sip`/пусто), «не слушает записи», предел цены (деньги или пусто).
- Способ и «не слушает записи» — условия в том же запросе кандидатов; предел цены — после цены по направлению, той же наценкой,
  что тарификация вызова. На вызов добавляется одно чтение по уникальному индексу, наценка читается только при заданном пределе.
- Причина `requirements_unmet` выясняется на пути отказа повтором отбора без требований — на успешном вызове лишних запросов нет.
