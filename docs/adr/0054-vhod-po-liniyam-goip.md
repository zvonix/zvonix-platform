# ADR-0054: Вход по линиям GOIP — способ подключения выбирается у шлюза

- **Статус:** Принято — 2026-09-25, решение владельца («Да, оба пункта»: общая таблица
  оборудования и выбор способа подключения; новому GOIP по умолчанию — «каждая линия
  отдельно»)
- **Дата:** 2026-09-25
- **Связано с:** [ADR-0009](0009-programmnaya-ats.md) (FreeSWITCH, каталог из control plane),
  [ADR-0043](0043-partnyor-zavodit-svoyo-oborudovanie.md) (оборудование партнёра),
  [ADR-0048](0048-poryadok-blokirovok-portov.md) (блокировки портов),
  [ADR-0053](0053-liniya-goip-po-prefiksu.md) (линия по префиксу)

## Контекст

ADR-0053 ввёл режим «один вход на шлюз»: GOIP регистрируется одной учётной записью,
а линию выбирает префикс `99NNN` в начале номера. Второй режим GOIP — `Config by Line`,
свой вход у каждой линии — был записан следующим шагом.

Владелец (2026-09-25) настраивает GoIP8 и сообщает: «я не могу сейчас авторизовать весь
шлюз целиком, только каждый канал по отдельности». То есть на его устройстве рабочий
путь — вход по линиям, и откладывать его нельзя: без него шлюз не регистрируется вовсе.

У входа по линиям есть и собственные достоинства перед префиксом:

- **Линия выбирается учётной записью, а не толкованием номера.** Площадка набирает
  `user/<вход линии>@realm`, и INVITE приходит ровно в ту линию, где стоит выбранная SIM.
  Как GOIP обращается с префиксом (читает ли строку запроса, срезает ли префикс) —
  главный непроверенный вопрос ADR-0053 — здесь не возникает.
- **Видно, какая линия на связи.** Линия без регистрации — это конкретная SIM, через
  которую вызов не уйдёт, а не «шлюз на связи» при молчащем порте.
- **Проверка одной SIM** — ровно то, чего хотел владелец: в GOIP настраивается
  только Line 1, остальные линии пусты и не регистрируются.

Смешать режимы внутри одного GOIP нельзя: `Config Mode` задаётся на всё устройство.

## Решение

### 1. Способ подключения — свойство шлюза

`gateways.registration_mode` — `gateway` (один вход на шлюз, линия по префиксу, ADR-0053)
или `port` (свой вход у каждого порта). Перечисление `GATEWAY_REGISTRATION_MODES`
в `@zvonix/shared`, в базе — `text` с `CHECK` (ADR-0016). `port` допустим **только
у GOIP**: у телефона Android слот один, у транка регистрируемся мы.

Умолчание в базе и в API — `gateway`: все существующие шлюзы настроены так, и вызов
API без нового поля ведёт себя как раньше. Кабинет для нового GOIP предлагает `port` —
это решение владельца о том, что **предлагать**, а не о смысле пропущенного поля.

Режим меняет партнёр (свой шлюз) и администратор, в журнал — прежний и новый.
Списанный шлюз режим не меняет. При смене режима отметка регистрации **той стороны,
на которую переключаются**, стирается: иначе давняя регистрация, оставшаяся с прошлого
раза, сделала бы шлюз «на связи» до того, как устройство перенастроено.

### 2. Вход линии — у порта

У `gateway_ports` появляются `sip_username`, `a1_hash`, `node_id`, `registered_at`,
по смыслу те же, что у шлюза: имя `pt-xxxxxxxxxxxx` уникально по всей площадке, пароля
нет, только `MD5(имя:realm:пароль)`. Имя и хеш заданы вместе или пусты вместе (`CHECK`):
пустые — «вход линии не выдан». Имена шлюзов (`gw-`), каналов (`ch-`) и портов (`pt-`)
не пересекаются по построению.

Выдача:

- при заведении GOIP в режиме `port` — всем его портам, в ответе один раз;
- при переключении на `port` — портам, у которых входа ещё нет, в ответе один раз;
- отдельно: всем портам шлюза без входа (после «Добавить порты») и перевыпуск одного
  порта — меняются и имя, и пароль, регистрация порта стирается.

Выдача входа при режиме `gateway` — `409`: вход, который каталог не отдаст, партнёр
ввёл бы в устройство и не понял бы, почему линия молчит.

### 3. Каталог и отбор

- Каталог отдаёт вход шлюза **только в режиме `gateway`**, вход порта — только
  в режиме `port`, и в обоих случаях — только у действующего шлюза проверенного
  партнёра (как раньше). Отметка регистрации пишется туда, чей вход спрошен.
- Отбор кандидатов сужается узлом по регистрации **той стороны, что набирается**:
  у `port` — по `gateway_ports.node_id` порта с выданным входом, у `gateway` —
  по `gateways.node_id`, как раньше. Одно выражение в том же запросе, а не второй
  запрос: условия, разложенные по чтениям, разъезжаются.
- Набор: у `port` — `[sip_invite_req_uri=sip:<номер>@realm]user/<вход порта>@realm`,
  без префикса; у `gateway` — как в ADR-0053. Разбор маршрута показывает набираемую
  учётную запись и префикс (у `port` его нет).

### 4. Кабинет: оборудование одной таблицей

«Моё оборудование» показывает все шлюзы одной таблицей: строка шлюза (состояние, связь,
заполненность) и под ней строки его портов — линия (префикс или вход и его связь), SIM,
оператор, состояние, действия с картой. Шлюз сворачивается; «Свернуть все / Раскрыть все».
Страница шлюза остаётся для подключения: выбор способа, поля GOIP для выбранного режима,
входы линий. Строки портов — один компонент на обе страницы.

## Отвергнуто

- **Режим у порта, а не у шлюза.** GOIP задаёт `Config Mode` на всё устройство;
  смешанный шлюз в кабинете был бы настройкой, которую устройство не повторит.
- **Входы портов всегда, а режим выводить из того, какой вход зарегистрировался.**
  Два пути регистрации одновременно — это два набора, между которыми площадке пришлось
  бы выбирать без знания о том, как настроено устройство; ошибка настройки стала бы
  звонками не с той линии вместо явного «линия не на связи».
- **Умолчание `port` в API.** Поменяло бы смысл уже работающих вызовов API и тестов;
  предложение по умолчанию — дело кабинета.
- **Удалять вход шлюза в режиме `port`.** Он нужен при возврате в `gateway`,
  а каталог его в режиме `port` и так не отдаёт.

## Последствия

- Партнёр с GOIP, который не проходит вход целиком, подключает его по линиям.
- Для режима `port` снимается зависимость от того, как GOIP читает префикс; для
  `gateway` вопрос ADR-0053 остаётся и проверяется пробным звонком.
- Один GoIP32 в режиме `port` — 32 регистрации и 32 обращения к каталогу на цикл
  перерегистрации. Запрос — один индексный поиск; нагрузка того же порядка, что
  32 канала клиентов.
- Схема меняется миграцией со значением по умолчанию: существующие строки получают
  `gateway` и пустые входы портов, простоя нет.

## Ревизия 2026-09-25: «Новый пароль» меняет только пароль

Владелец: «может, менять только пароль? кнопка пишет, что смена только пароля». Кнопка
«Новый пароль» у шлюза и у линии меняла и имя: довод был «имя засветилось в логах».
Но имя не секрет, а партнёр, введя в GOIP новый пароль к старому логину, получал молчащую
линию — и двадцать неудач подряд, после которых fail2ban закрывал его офис от площадки
([ADR-0051](0051-svoya-konfiguraciya-uzla.md), ревизия того же дня). Теперь имя прежнее,
меняется пароль; прежний перестаёт действовать сразу, отметка регистрации стирается.
Каналы клиентов (`POST /channels/:id/credentials`) не затронуты — их перевыпускает
администратор, и жалоб на них не было.

**Остаётся честно названным:** отметка «на связи» — факт запроса учётной записи узлом,
а не успешной регистрации (telephony.md, «Отметка о регистрации»). Устройство со старым
паролем тоже запрашивает учётную запись, поэтому после нового пароля его линия
покажется «на связи», пока устройство не перенастроено. Настоящее состояние регистрации —
события FreeSWITCH (ESL), потребителя которых ещё нет; строка в TASKS.md.

## Ревизия 2026-09-25 (вечер): номер — в `To`

На живом узле номер в адресе запроса не работал: FreeSWITCH слал такой INVITE на realm,
то есть самому себе, а GOIP со входом по линиям отвечал `404` на адрес не со своим входом.
Набор теперь `[sip_invite_to_uri=<sip:<номер>@realm>]user/<вход>@realm` — запрос идёт
по адресу регистрации линии, номер в `To`. Каталог отдаёт `dial-string` (без него `user/…`
отвечал `MANDATORY_IE_MISSING`). Подробности — [node.md](../api/node.md), «Что не проверено».

## Ревизия 2026-09-29: префикс линии и при входе по линиям

Номер в `To` GOIP не читает: на звонок на вход линии он отвечает сразу и ждёт номер
тоновым набором (двухступенчатый набор; тоны, посланные до готовности, он теряет —
набрал `30189196` вместо `79230189196`). Номер без префикса на адрес линии получает `404`.
Работает то же, что при входе на шлюз: **Routing Prefix у каждой линии** (`99NNN`) и номер
с префиксом в адресе запроса, направленном прямо на GOIP.

- Набор: `[zvonix_dial=<префикс>+<номер>]user/<вход>@realm`. Строка набора каталога
  (`dial-string`) берёт адрес регистрации (`sofia_contact`) и ставит `zvonix_dial` на место
  входа: `sip:99004+<номер>@<адрес GOIP>`. Выражение проверено на живом узле через `eval`.
- Кабинет показывает поля GOIP Basic VoIP полностью: Config Mode, SIP Proxy, SIP Registrar,
  Re-register Period, Prefix Match Mode, Delete Callee Prefix, Routing Prefix линии, а также
  Call Out → Call OUT via GSM.

## Ревизия 2026-09-30: набор из диалплана

Живой звонок клиента через площадку (`bridge` диалплана) ушёл на `sofia/zvonix/@<адрес>` —
без `99004+<номер>` — и 32 секунды звонил в пустоту, хотя тестовый звонок из ESL с той же
строкой проходил. Причина: переменная плеча `[zvonix_dial=…]` доходит до строки набора
каталога при `originate` из ESL и не доходит из `bridge`, где строка раскрывается в контексте
вызывающего плеча. Диалплан теперь ставит номер литералом в само выражение
(`simBridgeEndpoint`, тот же результат, проверен `eval` на узле); тестовый звонок остаётся
на `simEndpoint`. Расхождение путей — сознательное и записано здесь, а не «одно правило»
из ADR-0055: одна и та же цель, разные способы передать номер.
