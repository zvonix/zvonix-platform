# ADR-0110: Обновление без простоя — два экземпляра за nginx и окно наблюдения

- **Статус:** Принято — 2026-11-02; владелец: «делай всё, что рекомендуешь» (сравнение выкладки с проектами в `D:\dev`)
- **Дата:** 2026-11-02
- **Развивает:** [ADR-0049](0049-vykladka-ploshchadki.md), [ADR-0074](0074-obnovlenie-iz-adminki.md),
  [ADR-0109](0109-podlinnost-vypuska-i-prava-na-kod.md)

## Контекст

Выкладка меняла ссылку `current` и перезапускала `zvonix-api` и `zvonix-web`. Пока новый процесс поднимался, кабинет,
API и машинный контур не отвечали: на 127.0.0.1:8000 никого не было. Простой — десятки секунд на каждое обновление и
на каждый откат. Узел АТС в это время не получает маршрут, и вызовы клиентов срываются. Проверка после переключения
длилась 8 секунд: поломку, которая проявляется под настоящей нагрузкой через минуту, выкладка не замечала.

У regzone, veilnet и vk-modules выкладка без простоя: два экземпляра, переключение обратного прокси, сторож после
переключения.

Ограничения, найденные в коде:
- узел АТС на той же машине ходит в API **напрямую** на `127.0.0.1:8000`, мимо сайта nginx (адрес площадки в его
  настройке, ADR-0045); служба обновления проверяет `127.0.0.1:8000` и `127.0.0.1:3000`; сайт nginx проксирует туда же;
- API сам держит порт SMPP (ADR-0072): два экземпляра одновременно не поделят его обычным `listen`;
- воркер — расписание BullMQ (ADR-0020): два экземпляра безопасны (задачи идемпотентны), но и не нужны.

## Решения

1. **Два экземпляра — «a» и «b».** Юниты-шаблоны `zvonix-api@.service` и `zvonix-web@.service`; порты экземпляра —
   в `/etc/zvonix/slot-<имя>.env` (API: a — 8101, b — 8102; кабинет: a — 3101, b — 3102). Экземпляр работает из
   ссылки `/opt/zvonix/slots/<имя>` на свой выпуск. Активный экземпляр записан в `/etc/zvonix/slot`.
2. **Постоянные адреса держит nginx.** `/etc/nginx/conf.d/zvonix-slot.conf` слушает `127.0.0.1:8000` и
   `127.0.0.1:3000` и проксирует на порты активного экземпляра. Узел АТС, служба обновления и сайт продолжают ходить
   по прежним адресам и ничего не знают об экземплярах. Переключение — новый файл, `nginx -t` и `reload`: старые
   рабочие процессы nginx дорабатывают начатые запросы, новые идут в новый экземпляр. Обрыва нет.
3. **Переход на выпуск:**
   1) выпуск ставится в неактивный экземпляр, тот запускается и должен ответить «готов» на своих портах;
   2) не поднялся — экземпляр останавливается, трафик не трогался, работает прежний выпуск;
   3) поднялся — переключение nginx, ссылки `current`/`previous`, перезапуск воркера;
   4) **окно наблюдения** `ZVONIX_WATCH_SECONDS` (90 с): каждые 5 секунд новый экземпляр должен отвечать «готов»
      через постоянные адреса и быть живым. Сбой — nginx возвращается на прежний экземпляр (он всё это время работал),
      ссылки и воркер — назад, новый экземпляр останавливается;
   5) окно прошло — прежний экземпляр **дорабатывает открытые соединения** (до `ZVONIX_DRAIN_SECONDS`, 300 с —
      предел самых долгих запросов, выгрузки записей) и только потом останавливается; не дождались — соединения
      обрываются, и узел повторит выгрузку.

   В окне считаются и отказы nginx «не достучался» — 502 и 504 от портов нового экземпляра по журналу постоянных
   адресов (`/var/log/nginx/zvonix-slot.log`): три и больше — возврат. API сам этих кодов не отдаёт, поэтому они не
   спутаются с неудачным запросом; 500 и 503 не считаются — 503 API отвечает штатно («все аккаунты заняты»).
   Откат кнопкой — тот же путь с предыдущим выпуском, тоже без простоя.
4. **SMPP — общий порт.** На Linux API открывает порт SMPP с `reusePort`: оба экземпляра принимают подключения, пока
   прежний не остановлен; остановка закрывает его сессии, и клиенты переподключаются к новому. На других системах
   `reusePort` не поддерживается и не включается.
5. **Переход с одного экземпляра — один раз и автоматически.** Выкладка видит прежние `zvonix-api`/`zvonix-web`,
   останавливает и убирает их, поднимает выпуск в «a» и включает постоянные адреса. Не поднялся — прежний выпуск
   поднимается в «b». Прежние службы останавливаются **до** запуска нового: прежний API держит порт SMPP без общего
   режима, и новый рядом с ним его не открыл бы. Перерыв на этом шаге — пока поднимается API, один раз за всю
   историю.
6. **Служба обновления** останавливает и запускает при восстановлении копии службы активного экземпляра, читая
   `/etc/zvonix/slot`.
7. **Проба выкладки в CI** (`scripts/deploy-check.sh`) ставит nginx и проверяет на Ubuntu весь путь: переход с одного
   экземпляра, обновление и откат — с непрерывными запросами, ни один из которых не должен получить отказ.

## Рассмотрено и отклонено

- **`reusePort` и для HTTP**, без nginx посередине. Новый экземпляр тогда нельзя проверить до того, как ему пойдёт
  трафик: оба слушают один порт, и проверка попадает в любой.
- **Переписать сайт nginx на upstream** вместо внутренних адресов. Пришлось бы править сайт на каждом сервере и
  переводить узел АТС с `127.0.0.1:8000`; внутренние адреса не трогают ни то, ни другое. Цена — второй проход через
  nginx на той же машине, доли миллисекунды.
- **Воркер в двух экземплярах.** Перезапуск воркера не виден ни клиенту, ни узлу: задачи догоняющие (ADR-0020).

## Последствия

- Миграции по-прежнему применяются до переключения и обязаны быть совместимы с прежним кодом (ADR-0005): в окне
  наблюдения и при возврате прежний выпуск работает с новой схемой.
- Памяти во время обновления нужно на второй API и второй кабинет — около 300–400 МБ на время окна.
- Выкладка длится дольше на окно наблюдения (90 с); кабинет показывает ход.
- Журналы служб — `journalctl -u 'zvonix-api@*' -u 'zvonix-web@*'`.
- Откат на выпуск до этого решения его код поднимает в экземпляре, а сценарий выкладки и юниты остаются нынешними
  (`install_system_files` ставит их только из выпуска с экземплярами). Если на таком выпуске включён SMPP, его API
  не откроет порт рядом с работающим, и откат не пройдёт — работает текущий выпуск; откатиться можно, выключив SMPP
  на время.
