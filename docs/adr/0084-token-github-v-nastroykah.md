# ADR-0084: Токен GitHub для обновлений — в настройках площадки

- **Статус:** Принято — 2026-10-14; владелец: «токен GitHub в настройках — делай»
- **Дата:** 2026-10-14
- **Развивает:** [ADR-0074](0074-obnovlenie-iz-adminki.md) (служба обновления от root, каталог обмена),
  [ADR-0083](0083-sertifikat-v-nastroykah.md) (то же устройство для сертификата),
  [ADR-0062](0062-trevogi-administratoram.md) (тревоги)

## Контекст

Служба обновления скачивает выпуски у GitHub токеном из `/etc/zvonix/github.env`. Токен выпускается со сроком (раздел
«Токен GitHub» в `deploy/README.md`), и когда срок кончится, обновления из кабинета встанут молча. Менять токен
приходилось по SSH, а увидеть срок было негде. Репозиторий планируется сделать приватным, тогда токен нужен всегда.

## Решение

1. **Токен вводится в «Настройки площадки» → «Обновления»** и уходит службе обновления одной заявкой `token-set`
   (файл с правами 0600). Кабинет токен нигде не хранит: ни в базе, ни в журнале действий, ни в ответах API.
2. **Служба сначала проверяет, потом записывает.** Запрос к GitHub по репозиторию из `github.env` (не из заявки)
   с новым токеном; принят — строка `GITHUB_TOKEN` в файле заменяется подменой файла (права 0600, остальные строки
   сохраняются), не принят — прежний остаётся. Репозиторий назвать заявкой нельзя: подменить источник выпусков
   через кабинет не получится.
3. **Токен не покидает `github.env`.** Ни в состоянии заявки, ни в журнале, ни в `github-token.json` его нет;
   сообщения об ошибках пересказываются по-русски и очищаются от токена. Заявка с токеном удаляется службой сразу
   после приёма, как и остальные.
4. **Состояние токена** — `github-token.json` в каталоге обмена: `valid`, `expires_at` (из заголовка
   `github-authentication-token-expiration`), `checked_at`, `problem`. Пишется при каждой проверке токена и при
   каждом обновлении списка выпусков, поэтому «токен отозван» кабинет узнаёт сам, без отдельных запросов.
5. **Состояния для кабинета:** `ok`, `soon` (осталось 14 суток и меньше), `invalid` (GitHub не принял токен или срок
   истёк), `unknown` (служба ещё не проверяла).
6. **Письмо администраторам** (тревога ADR-0062, те же настройка, очередь и повтор раз в 12 часов):
   `alert_github_token:soon` и `alert_github_token:invalid`.
7. **Только администратор**; поддержка, клиенты и партнёры получают `403`. Пока предыдущая заявка с токеном
   ждёт или проверяется, новая — `409`.

## Последствия и риски

- Токен проходит через API на пути к службе. Тот, кто получил контроль над API, может подставить **свой** токен к
  тому же репозиторию — источник выпусков он сменить не сможет, но сломать обновления способен. Этот риск уже есть у
  остальных действий раздела «Обновления».
- Заявка с токеном лежит в каталоге обмена до приёма службой (до десяти минут, чаще секунды): права 0600,
  читает только владелец и root. Отменить её можно, как любую заявку.
- Нет службы обновления (разработка, площадка без неё) — раздел показывает «ещё не проверен», а заявка ждёт.
- Токен, выпущенный не на организацию-владельца или без права «Contents: Read-only», не принимается;
  причина пересказана подсказкой.

## Проверено

Служба — настоящим `deploy/updater.py` и локальным сервером вместо GitHub (`tests/updater-github-token.test.ts`):
принятый токен записывается, остальное в файле сохраняется, срок виден; отказанный не записывается, прежний остаётся;
репозиторий из заявки игнорируется; токена нет ни в одном файле обмена. API — интеграционные тесты раздела обновлений
(права, формат, файл с правами 0600, отсутствие токена в журнале действий и ответах). Кабинет — e2e.
**Не проверено до живого сервера:** запрос к настоящему GitHub с токеном организации.
