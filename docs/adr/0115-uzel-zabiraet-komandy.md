# ADR-0115: Узел сам забирает у площадки команды — тестовый звонок и сброс входа

- **Статус:** Принято — 2026-11-12, подтверждено владельцем («Да, делай»)
- **Дата:** 2026-11-12
- **Уточняет:** [ADR-0055](0055-testovyy-zvonok-s-sim.md) (тестовый звонок через ESL),
  [ADR-0103](0103-shlyuz-na-svyazi-po-oprosu-i-trevoga-partnyoru.md) (сброс регистрации при новом пароле)
- **Связано с:** [ADR-0051](0051-svoya-konfiguraciya-uzla.md) (ESL только на 127.0.0.1),
  [ADR-0114](0114-uzel-sam-soobshchaet-registracii.md) (узел сам сообщает регистрации),
  [ADR-0019](0019-dostup-mashin.md) (агент узла, ключ машины)

## Контекст

Команды узлу — `originate` тестового звонка и `flush_inbound_reg` после смены пароля — площадка отдаёт по ESL,
а ESL узла слушает только 127.0.0.1. Узел на **отдельном сервере** их не получает: 2026-11-12 у владельца
тестовый звонок с Line 4 (узел 217.197.114.163) ответил «Узел площадки пока не принимает команды на звонок».
ADR-0114 решил обратную сторону — узел сообщает регистрации сам. Здесь — команды от площадки к узлу.

## Рассмотренные варианты

| Вариант | Почему нет или да |
|---|---|
| Открыть ESL узла наружу | Через ESL выполняется любая команда, включая звонки за счёт SIM; протокол без TLS. Отвергнуто ещё в ADR-0055 |
| Отдавать команды в ответе на пульс | Пульс раз в 30 с — тестовый звонок начинался бы через полминуты |
| **Узел держит долгий запрос и забирает команду сразу** | **Выбрано.** Задержка — около секунды, соединение открывает узел (как пульс), по TLS и по ключу узла. Узел выполняет только две разрешённые команды |

## Решение

1. **Очередь — таблица `node_commands`**: узел, строка команды `api`, срок, до которого узел должен её взять
   (10 с), когда взята, когда выполнена, ответ FreeSWITCH. Таблица, а не память процесса: во время обновления
   площадки работают два экземпляра API (ADR-0110), и команда, поставленная одним, должна дойти через другой.
   Строки старше суток удаляет задача `nodes.purge-commands` — в команде звонка номер абонента.
2. **`GET /node/commands`** (ключ узла) — долгий запрос до 25 с: `200` с телом `text/plain` из двух строк
   (идентификатор, команда), как только команда появилась; `204` — команд нет. Каждый запрос отмечает
   `nodes.commands_polled_at`: по ней площадка знает, что служба команд на узле работает.
3. **`POST /node/commands/:id/result`** (ключ узла), тело `text/plain` — ответ `fs_cli` как есть
   (`+OK …`/`-ERR …`). Чужая, не взятая или уже выполненная команда — `404`.
4. **`NodeCommandsService.run`** — одна дверь для вызывающих: узел своей машины — по ESL, как прежде;
   остальные — через очередь, ожидая ответа. Узел не взял команду за срок — отказ `connect` (звонка не было),
   взял, но не ответил вовремя — `timeout` (итог допишет CDR). Тестовый звонок и сброс регистрации
   идут через неё; «узел не принимает команды» — только если нет ни ESL, ни отметки опроса за 90 с.
5. **Служба на узле `zvonix-commands`** (systemd, перезапуск всегда; порождает `node/install.sh`): цикл долгих
   запросов, каждую команду выполняет `fs_cli -x` в фоне и присылает ответ. **Выполняет только** команды,
   начинающиеся с `originate {` и `sofia profile zvonix flush_inbound_reg ` — прочие отвергает
   `-ERR NODE_REFUSED`, даже если их прислала площадка.

## Последствия

- **Положительные.** Тестовый звонок и сброс входа работают на узле любой машины; наружу ничего не открыто.
- **Отрицательные.** Новая таблица и долгоживущая служба на узле. Узлу нужен новый набор (ADR-0068).
  Долгий запрос держит соединение API — по одному на узел; журнал медленных запросов его не считает.
- Схема БД: новая таблица и колонка `nodes.commands_polled_at` — только добавление.
