# ADR-0019: Доступ машин к API — узлы АТС и клиентские ключи

- **Статус:** Предложено
- **Дата:** 2026-09-01

## Контекст

[ADR-0018](0018-autentifikaciya.md) решил вход людей и явно оставил машины на отдельное
решение. К этапу 2 машин становится три вида:

| Кто | Что делает | Частота |
|-----|------------|---------|
| Узел FreeSWITCH | Спрашивает маршрут на каждый вызов (`mod_xml_curl`), отдаёт CDR (`mod_json_cdr`) | **На каждый звонок** |
| Агент узла (`apps/agent`) | Регистрация при установке, heartbeat, метрики, выгрузка записей | Раз в десятки секунд |
| Клиент — служба такси | Инициация вызовов, статусы, записи (этап 5) | Постоянно |

Требования отличаются от людских по всем пунктам: срок жизни долгий — перевыпускать ключ
узла раз в тридцать дней значит ронять телефонию; интерактивного входа нет — некому ввести
пароль и код второго фактора; отзыв нужен поштучно, а не «все сессии пользователя»;
и главное — **проверка выполняется на каждый звонок**, то есть в горячем пути.

## Ограничение, которое определяет решение

HTTP-клиенты FreeSWITCH не программируются: это `libcurl` за XML-конфигурацией.
Проверено по конфигурации модулей и документации:

- **`mod_xml_curl`** (`xml_curl.conf.xml`): `gateway-url`, `gateway-credentials` вида
  `user:pass`, `auth-scheme` (`basic|digest|NTLM|GSS-NEGOTIATE|any`), `timeout`,
  `ssl-cert-path`, `ssl-key-path`, `ssl-cacert-file`, `enable-cacert-check`,
  `enable-ssl-verifyhost`, `enable-post-var`, `response-max-bytes`, `cookie-file`.
- **`mod_json_cdr`** (`json_cdr.conf.xml`): `url` (до двадцати), `cred`, `auth-scheme`,
  `timeout`, `retries`, `delay`, `err-log-dir`, те же `ssl-*`.

**Произвольный заголовок задать нельзя ни там, ни там.** Отсюда:

- `Authorization: Bearer <токен>` узлу недоступен;
- подпись запроса (HMAC по телу и метке времени) недоступна тоже — вычислять её на узле
  нечем, диалплан не выполняет наш код на пути запроса конфигурации;
- остаются ровно два способа: **секрет в схеме Basic/Digest** и **клиентский сертификат TLS**.

Это ограничение внешней системы, а не предпочтение. Контракт, который его не учитывает,
не заработает — и выяснится это на живом железе, а не на ревью.

## Рассмотренные варианты

### 1. Basic: идентификатор ключа в поле имени, случайный секрет в поле пароля

- **За.** Доступно обоим модулям без оговорок. Секрет — 256 бит случайности, в базе лежит
  SHA-256, то есть та же механика, что у сессий в [ADR-0018](0018-autentifikaciya.md).
  Отзыв — одна строка. Ротация — второй действующий ключ рядом с первым. Идентификатор
  ключа безопасно печатать в логах и называть в поддержке, секрет — нет.
- **Против.** Секрет уходит в каждом запросе: без TLS это перехват, с TLS — эквивалент
  Bearer. Секрет лежит открытым текстом в конфигурации узла (`gateway-credentials`),
  то есть кто получил root на узле, получил и ключ.

### 2. Взаимный TLS (mTLS)

- **За.** Секрет не покидает узел: доказывается владение ключом, а не его предъявление.
  Аутентификация происходит до HTTP — неаутентифицированный запрос вообще не доходит
  до приложения. Заодно закрывает подмену control plane, если проверять и серверный
  сертификат.
- **Против.** Нужен собственный удостоверяющий центр и его эксплуатация: выпуск, продление,
  отзыв. Продление сертификата на узле — ещё одна вещь, которая ломает телефонию ночью,
  если не сработает. Отзыв требует CRL или OCSP, либо коротких сертификатов, то есть опять
  автопродления. Терминирование TLS переезжает с обратного прокси в приложение — либо прокси
  пробрасывает факт проверки заголовком, которому приложение вынуждено верить, и тогда
  вся схема держится на том, что заголовок не подделан.

  **И главное: приватный ключ лежит на узле файлом ровно так же, как лежал бы пароль.**
  Против кражи root на узле mTLS не защищает. Он защищает от перехвата на проводе —
  а тот уже закрыт TLS.

### 3. Digest

- **За.** Секрет не идёт по проводу.
- **Против.** Сервер обязан хранить секрет в восстановимом виде — `H(A1) = MD5(user:realm:pass)`.
  Утечка таблицы даёт возможность войти, то есть ровно то, чего [ADR-0018](0018-autentifikaciya.md)
  избегал. Плюс два обращения на каждый запрос вместо одного: на горячем пути маршрутизации
  это удвоение сетевых задержек на каждый звонок. В основе MD5.

## Решение

**Вариант 1: Basic поверх обязательного TLS, идентификатор ключа отдельно от секрета.**

Довод против mTLS не «сложно», а **«не даёт того, ради чего берётся»**: обе схемы кладут
секрет файлом на узел, обе беззащитны перед кражей root на узле, а перехват на проводе уже
закрыт TLS. Остаётся разница в стоимости эксплуатации удостоверяющего центра, и она
не в пользу mTLS. Записано как путь роста: если узлы будут стоять **у партнёров**, а не у нас,
разница станет существенной — там узел заведомо не наш, и «владение ключом вместо его
предъявления» начинает что-то значить.

### Формат ключа

Имя — идентификатор `zvx_<вид>_<12 символов>`, пароль — 32 случайных байта в base64url.

Почему не один склеенный токен: в поле `user:pass` их всё равно два, а раздельные поля
дают **поиск по индексу** вместо перебора всех ключей с постоянным по времени сравнением
каждого. На горячем пути это разница между индексным чтением и полным сканом таблицы.

### Хранение секрета

SHA-256, как у сессий. Argon2 здесь не просто не нужен, а **недопустим**: проверка идёт
на каждый звонок, а argon2id с 19 МиБ памяти — это 19 МиБ и десятки миллисекунд на каждый
запрос маршрута. Перебирать 256 бит случайности всё равно нечего. Сравнение — постоянное
по времени.

### Список разрешённых адресов у каждого ключа

Адрес узла известен: узел заводит администратор, а не случайный посетитель. Утёкший ключ
узла, предъявленный с другого адреса, бесполезен — **это единственная мера, которая
работает и против кражи root на узле тоже**: ключ, украденный с узла, вне узла не годится.

Пустой список означает «откуда угодно» и допустим только у клиентских ключей на время
внедрения. Адрес берётся с учётом `trustProxy` и только из доверенного источника — иначе
список обходится подделкой `X-Forwarded-For`, и мера превращается в её видимость.

### Одноразовый токен установки

Команда установки из [ARCHITECTURE.md](../ARCHITECTURE.md) — `curl … | sudo bash -s -- <токен>` —
попадает в историю оболочки, в переписку и в буфер обмена. Поэтому в ней **не постоянный
ключ, а одноразовый**: срок один час, применение ровно одно, обменивается на постоянный
при регистрации узла.

Второе применение — отказ и запись в аудит: это признак того, что команду прочитал кто-то ещё.

### Ротация без простоя

У одного узла допускается больше одного действующего ключа: завести новый → раскатать
конфигурацию → отозвать старый. Обратный порядок оставляет окно, в котором звонки
не маршрутизируются.

### Отзыв

Пометкой, а не удалением строки — как выход из сессии в ADR-0018. Иначе в журнале дыра
ровно там, где чаще всего и нужно разбираться.

### Срок жизни

У ключей узлов срок **не задаётся по умолчанию**: истёкший ключ узла означает отказ
телефонии, а это худший отказ, чем неотозванный ключ у машины, чей адрес в списке.
Взамен возраст ключа виден в панели и попадает в отчёт: «этому ключу 400 дней» должно
быть видно заранее, а не наступать внезапно. У клиентских ключей срок — год,
с уведомлением до истечения.

### Два представления одного ключа

Наш собственный агент — обычный HTTP-клиент и заголовок задать умеет. Поэтому принимаются
оба вида, `Authorization: Basic base64(id:secret)` и `Authorization: Bearer <id>.<secret>`.
Схема одна, кодировок две, проверка общая. Заводить ради агента вторую схему смысла нет.

### Права

Ключ узла не может ничего, кроме маршрутизации, приёма CDR, heartbeat и выгрузки записей;
клиентский ключ — ничего, кроме своего клиента. Реализуется тем же защитником, что и роли
людей: доступ закрыт по умолчанию, машинный обработчик помечается явно.

**Ключ машины не даёт человеческих прав ни при каких условиях.** Это разные субъекты,
и роль администратора машинным ключом не открывается — иначе украденный с узла ключ
превращается в администратора платформы.

## Схема

Одна таблица `machine_credentials` на оба вида: состав полей у них совпадает, различается
только субъект. Владелец полиморфен — узел или клиент, как `accounts.owner_id`
в [ADR-0010](0010-model-billinga.md).

| Колонка | Тип | Смысл |
|---------|-----|-------|
| `id` | uuid | |
| `kind` | text + CHECK | `node`, `client_api`, `enrollment` |
| `key_id` | text, уникально | `zvx_node_a1b2c3d4e5f6`, публичная часть |
| `secret_hash` | text | SHA-256 от секрета |
| `owner_id` | text | Узел или клиент. Полиморфно — внешним ключом не выразить |
| `label` | text | «Узел Москва-1, ключ от 2026-09-01» |
| `allowed_ips` | text[] | Пусто — откуда угодно |
| `expires_at` | timestamptz, null | У узлов пусто |
| `last_used_at` | timestamptz, null | Обновляется не чаще раза в пять минут, как `last_seen_at` сессий |
| `revoked_at` | timestamptz, null | Отзыв пометкой |
| `used_at` | timestamptz, null | Только у `enrollment`: одноразовость |
| `created_by_user_id` | uuid → users | Кто выпустил |
| `created_at` | timestamptz | |

## Что не решается здесь

**Вебхуки в обратную сторону** (control plane → клиент). Там подпись HMAC уместна
и возможна, потому что вычисляем её мы, а не FreeSWITCH. Отдельно, к этапу 5.

## Последствия

- **Положительные.** Одна схема на все машины. Отзыв мгновенный и поштучный. Утечка таблицы
  ключей не даёт доступа. Список адресов делает украденный ключ бесполезным вне узла.
  Проверка — один индексный поиск, пригодный для горячего пути.
- **Отрицательные и принятая цена.** Секрет лежит открытым текстом в конфигурации узла
  и уходит в каждом запросе: TLS обязателен, а компрометация узла означает компрометацию
  его ключа. Смягчается списком адресов и ротацией, не устраняется — mTLS этого тоже
  не устраняет.
- **Что теперь обязательно в коде.** Машинные обработчики помечаются явно и проверяются
  отдельным защитником; секрет не попадает в логи, ответы и сообщения об ошибках;
  `X-Forwarded-For` учитывается только из доверенного источника; новая таблица
  `machine_credentials` заводится миграцией по [ADR-0005](0005-migracii.md).
