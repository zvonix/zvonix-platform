# ADR-0071: Сообщения MAX через аккаунты партнёров

- **Статус:** Принято — 2026-10-04, решения владельца: личные аккаунты MAX партнёров; провайдер скрыт от
  партнёров и клиентов; инстансы оплачивает площадка; SMPP — отдельным выпуском
- **Дата:** 2026-10-04
- **Связано с:** [ADR-0010](0010-model-billinga.md), [ADR-0014](0014-vybor-partnera-klientom.md)
  (клиент не видит партнёра), [ADR-0020](0020-fonovye-zadachi.md), [ADR-0031](0031-nastroyki-ploshchadki.md),
  [ADR-0064](0064-platezhi-karkas.md) (способ за интерфейсом)

## Контекст

Площадка продаёт голосовые вызовы через оборудование партнёров. Владелец хочет второй продукт —
текстовые сообщения в мессенджере MAX — по той же схеме: аккаунты у партнёров, цену за сообщение
ставит партнёр, лимитами управляет партнёр, свою наценку ставит владелец, клиенты отправляют
по HTTP и (позже) по SMPP. Провайдером доступа к MAX выбран Green API (аккаунт MAX подключается
как «инстанс» сканированием QR-кода).

## Решение

1. **Провайдер — внутренняя деталь площадки.** Код отправки — за интерфейсом `MessageProvider`
   (как `PaymentProvider`, ADR-0064), единственная реализация — Green API. Партнёр и клиент не видят
   ни названия провайдера, ни его ключей, адресов, идентификаторов инстансов, ни его текстов
   ошибок: в кабинетах, API, письмах и документации для них — «аккаунт MAX». Ошибки провайдера
   переводятся в наши причины (`recipient_not_in_max`, `account_unavailable`, `rate_limited`,
   `platform`); подробность остаётся в журнале площадки. Ключ доступа к инстансу хранится
   зашифрованным (`SECRET_KEY`, назначение `zvonix:messenger-token:v1`), как пароль SIP-транка.
2. **Аккаунт MAX (`messenger_accounts`)** принадлежит партнёру: состояния `pending` (заведён,
   QR не отсканирован) → `active` (вошёл, на связи) ↔ `unavailable` (вышел из MAX / провайдер не
   отвечает) → `retired` (списан; необратимо). Партнёр заводит аккаунт кнопкой: площадка создаёт
   инстанс у провайдера (партнёрский API провайдера; ключ — настройка площадки), отдаёт QR-код
   (через наш сервер, обновляется раз в несколько секунд), следит за состоянием. До получения
   партнёрского ключа провайдера администратор заводит аккаунт вручную по данным готового инстанса.
   Инстансы оплачивает площадка: в ценах это учитывает владелец через наценку.
3. **Цена и наценка.** Партнёр задаёт **цену за одно сообщение** (на свой счёт). Площадка добавляет
   **наценку** — правила владельца (изначально настройка `messages.markup_percent`, 20 %; с 2026-10-05 —
   правила `commission_rules`, [ADR-0073](0073-nacenka-na-soobscheniya-pravilami.md)), округление цены
   клиента вверх до микроединицы; цена клиента = цена партнёра × (1 + наценка). **Цена фиксируется
   на сообщении при приёме** (как строка цены на вызове, CLAUDE.md): смена цены или наценки идущие
   и уже отправленные сообщения не затрагивает. Цену клиента видит клиент, цену партнёра — партнёр
   и сотрудники, наценку — только сотрудники.
4. **Лимиты партнёра.** У аккаунта: сообщений в минуту и в сутки (необязательные), и общая пауза между
   отправками аккаунта: защита от блокировки мессенджером (случайная пауза в пределах настройки
   площадки `messages.pace_seconds`). Лимит исчерпан — сообщение ждёт в очереди, а не отклоняется;
   ждёт дольше `messages.max_wait_minutes` — отклоняется с возвратом денег.
5. **Деньги — той же книгой проводок.** Приём сообщения = проводка `charge` с ключом
   `message:<id>`: клиент платит, партнёр зарабатывает, площадка получает наценку (три
   проводки, сумма ноль — как у вызова). Окончательный отказ (получателя нет в MAX, аккаунт
   недоступен, истёк срок ожидания) — **возврат** обратной проводкой `message_refund:<id>`;
   повтор безопасен (идемпотентность по ключу). Доступно ли клиенту отправить, решает тот же
   запас средств (остаток + минус), что и для звонков.
6. **Очередь.** Сообщение — строка `messages` (`queued` → `sent` → `delivered` → `read`, либо
   `failed`/`rejected`); отправку ведёт задача воркера (ADR-0020, догоняющая: берёт по сроку, а не
   «сделанное с прошлого запуска»), с блокировкой строк, чтобы два воркера не отправили одно и то же.
   Идемпотентность приёма — по ключу клиента (`external_id`): повторный запрос того же сообщения
   возвращает прежнее, деньги не списываются дважды.
7. **Статусы доставки** приходят от провайдера на наш адрес приёма (секретный путь, сверка
   идентификатора инстанса с аккаунтом); опрос состояния аккаунтов — задача воркера.
8. **Выбор аккаунта** при отправке: аккаунты партнёров в состоянии `verified`, с ценой, `active`, в пределах
   лимитов; порядок — цена партнёра, затем давность последней отправки. Клиент партнёра не
   выбирает (в этом выпуске).
9. **Получатель** — российский номер, приводится к каноническому виду теми же правилами, что и
   у вызовов. Наличие MAX у номера **не проверяется до списания**: заранее это лишний обмен с провайдером на
   каждое сообщение, а ответ отправки и так однозначен. Нет MAX — окончательный отказ и **возврат** (п. 5);
   клиент видит «не отправлено, деньги возвращены». (Решение этапа 2, 2026-10-05.)
10. **Включение.** Настройка `messaging.enabled` (выключена по умолчанию): площадка принимает сообщения
    только когда владелец включил продукт.

## Этапы

1. **Аккаунты партнёров** — таблицы, провайдер, заведение/QR/состояние, цена и лимиты, настройка
   наценки, страницы партнёра и администратора.
2. **Отправка клиентом** — приём (HTTP API и кабинет), очередь, деньги и возврат, статусы доставки,
   журналы всех ролей, ключи API клиента.
3. **SMPP** — отдельная служба: клиент подключает свою систему (system_id/пароль, список адресов),
   `submit_sm` становится сообщением этапа 2, отчёты о доставке — `deliver_sm`.

## Не входит

Входящие сообщения (ответы получателей), вложения и файлы, рассылки по спискам, шаблоны, выбор
партнёра клиентом, повторная доставка по SMS, официальный бот MAX.

## Риски и условия

- Личные аккаунты могут блокироваться мессенджером при массовой отправке. Защита — паузы и лимиты;
  последствие (потеря аккаунта) несёт партнёр, поэтому лимиты в его руках.
- Клиент отвечает за согласие получателей на сообщения (закон о рекламе, о персональных данных);
  это условие входит в правила площадки, продукт предназначен для уведомлений и кодов.
- Текст сообщения — персональные данные: в журналах логов не пишется, в базе хранится ограниченный срок
  (настройка `retention.messages_days`, по умолчанию 30 суток).
