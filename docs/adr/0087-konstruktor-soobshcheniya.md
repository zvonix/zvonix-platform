# ADR-0087: Конструктор сообщения клиента

- **Статус:** Принято — 2026-10-19; владелец: «клиенты могли собрать своё сообщение… приветствие с именем или без, свой
  текст, текст из SMPP, ссылка на бота… при первом получении или при каждом»
- **Дата:** 2026-10-19
- **Связано с:** [ADR-0071](0071-soobscheniya-max.md) (сообщения MAX), [ADR-0077](0077-bot-max-vtoroy-kanal.md) (бот клиента,
  «тексты до и после»), [ADR-0005](0005-migracii.md) (миграции), [ADR-0016](0016-soglasheniya-shemy-bd.md) (схема БД)

## Контекст

У клиента был один способ влиять на текст: «текст перед каждым сообщением» и «текст после каждого» — только для бота,
по 150 знаков. Клиенту нужно большее: собрать сообщение из частей в нужном порядке (приветствие с именем или без, свой
текст, сам текст из SMPP/API/формы, ещё свой текст, ссылка на бота) и решать, что добавлять только в первое сообщение
человеку, а что в каждое.

## Решение

1. **Шаблон клиента** — таблица `message_templates` (одна строка на клиента): упорядоченный список блоков, до 12.
   Блоки четырёх видов:
   - `greeting` — приветствие, текст по умолчанию «Здравствуйте, {имя}!»; `{имя}` заменяется именем человека, если оно
     известно, иначе вместе с соседней запятой или пробелом пропадает («Здравствуйте!»);
   - `text` — свой текст, до 300 знаков;
   - `body` — сам текст сообщения (из SMPP, API или формы). Ровно один, удалить нельзя, двигать можно;
   - `bot_link` — ссылка на бота клиента; нет подключения — блок пропускается.
   Каждый блок, кроме `body`, имеет `when`: `always` или `first` (только в первом сообщении этому человеку).
2. **Сборка при отправке, а не при приёме.** В базе остаётся исходный текст клиента (журнал, повтор по ключу, проверка
   дублей работают по нему); итоговый текст собирает воркер перед отправкой, одной чистой функцией
   (`composeMessage`, `packages/shared`) — её же использует предпросмотр в кабинете, поэтому показанное и ушедшее
   совпадают. Блоки соединяются переводом строки. Собранный текст длиннее предела мессенджера — уходит один `body`.
3. **«Первое сообщение»** — нет прежнего отправленного (`sent`/`delivered`/`read`) сообщения этому клиенту на этот номер.
4. **Имя** — только то, что человек сам сообщил: имя профиля MAX из события запуска бота (`bot_subscribers.first_name`).
   Через аккаунты партнёров имени нет: приветствие идёт без имени. Имена в базе клиента не хранятся и не запрашиваются.
5. **Шаблон действует на оба пути** — бот и аккаунты партнёров. Прежние «текст до/после» бота переносятся миграцией
   в шаблон (блоки `text` до и после `body`), из кабинета и API настроек бота убираются; столбцы остаются до отдельной
   миграции (ADR-0005: разрушающее изменение — в два шага). Приветствие при запуске бота (`greeting`) — отдельное и
   прежнее.
6. **Цена не меняется**: одно сообщение — одна цена, независимо от числа блоков.

## Не входит (следующий этап)

Отдельное второе сообщение после основного (удваивает отправки, повторы и возвраты — нужен свой разбор), имена
получателей через API, картинки и кнопки, перетаскивание блоков мышью (порядок меняется кнопками).

## Последствия

- Миграция: таблица `message_templates`, столбец `bot_subscribers.first_name`, перенос прежних вставок.
- Клиент с прежними вставками получает их теперь и в сообщениях через аккаунты партнёров (раньше — только бот).
- Шаблон проверяется на сервере (виды, число, длины, один `body`): кабинету не доверяем.
