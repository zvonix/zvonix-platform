# ADR-0111: Части проекта — отдельными репозиториями в общей рабочей папке

- **Статус:** Принято
- **Дата:** 2026-11-04

## Контекст

Кроме площадки в проекте появятся другие части: Android-приложение партнёра
([ADR-0012](0012-mobilnoe-prilozhenie.md)), расширение для браузера и, возможно,
дальнейшие дополнения. [ADR-0008](0008-stek.md) и `CLAUDE.md` предполагали каталог
`android/` внутри этого монорепозитория, но он так и не был заведён.

Ограничения, которые определили выбор:

- **Обновление через админку** берёт список выпусков из GitHub Releases этого репозитория
  (`deploy/updater.py`, `GITHUB_REPOSITORY` в `/etc/zvonix/github.env`). Выпуски других частей
  в общем репозитории попали бы в этот список, и сервер предлагал бы поставить метку
  мобильного приложения.
- **Команда установки** скачивает `deploy/install.sh` по пути от корня этого репозитория.
  Перенос площадки в подкаталог общего монорепозитория сломал бы уже розданную команду
  и обновление работающих серверов.
- **Общего кода почти нет.** Приложение партнёра пишется на Kotlin, типы TypeScript
  из `packages/shared` ему не подключить. Связь частей — публичный API площадки.
- **Выпуски независимы.** Приложение выходит через магазин, расширение — через Chrome Web Store;
  на сервер ни то, ни другое не ставится.
- Владелец хочет, чтобы проект оставался единым: правила и сведения обо всех частях
  должны быть видны с одного места.

## Рассмотренные варианты

1. **Всё в этом репозитории** (`android/`, `extension/` рядом с `apps/`) — плюсы: одна история,
   изменение API и клиента одним PR. Минусы: выпуски частей смешиваются в списке обновлений
   сервера, CI каждой части приходится отделять фильтрами путей, у Kotlin своя сборка
   (Gradle), которая к pnpm-монорепозиторию отношения не имеет.
2. **Общий монорепозиторий, площадка в подкаталоге** (`platform/`, `android/` в одном git) — плюсы
   те же. Минусы: ломает команду установки и обновление серверов (пути от корня репозитория),
   требует переписать CI, выкладку и проверки; выпуски смешиваются так же.
3. **Отдельный репозиторий на часть, общая рабочая папка** — плюсы: площадка не меняется
   совсем, у каждой части свой CI и свои выпуски, правила частей не смешиваются. Минусы:
   изменение API и клиента — два PR; нужна папка, которая связывает части.

## Решение

**Вариант 3.**

- Каждая часть — свой репозиторий и своя папка в общей рабочей папке:
  `platform/` (этот репозиторий, `zvonix/zvonix-platform`), `android/`, `extension/` и т.д.
- Рабочая папка — отдельный закрытый репозиторий `zvonix/zvonix-workspace`. В нём только общие файлы:
  `CLAUDE.md` с правилами для всех частей и связями между ними, `.mcp.json`,
  `.claude/settings.json`. Папки частей исключены из него списком «разрешено» в `.gitignore`.
- Сессия Claude Code открывается в рабочей папке; `CLAUDE.md` и навыки части подгружаются
  при работе с её файлами.
- Части связаны только публичным API площадки ([docs/api/](../api/)). Код этого репозитория
  другие части не импортируют.
- Этот репозиторий **не переименовывается и не переносится**: на его имя и пути от корня
  опираются установка и обновление серверов.

## Последствия

- Положительные: площадка, её CI, выкладка и обновление через админку не меняются; выпуски
  частей не пересекаются; у каждой части свой стек и свои правила без взаимных исключений.
- Отрицательные и принятая цена: изменение API, которое затрагивает клиента, — PR сначала здесь,
  потом в репозитории клиента; общие типы для клиентов на TypeScript (расширение) берутся
  из описания API, а не из `packages/shared`.
- Обязательно: изменение публичного API — совместимое со старыми клиентами. Приложение у партнёров
  обновляется не сразу: поле сначала помечается устаревшим, удаляется отдельным выпуском позже.
- Каталог `android/` внутри этого репозитория не заводится. Строка «Android: Kotlin»
  в [ADR-0008](0008-stek.md) остаётся в силе: меняется место кода, а не стек.
