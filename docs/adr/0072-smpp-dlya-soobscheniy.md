# ADR-0072: SMPP для сообщений MAX

- **Статус:** Принято — 2026-10-05, решение владельца: SMPP — вторым выпуском сообщений; детали
  (где работает, как хранится пароль, как приходят отчёты) выбраны по рекомендации проектировщика
- **Дата:** 2026-10-05
- **Связано с:** [ADR-0071](0071-soobscheniya-max.md) (этап 3), [ADR-0044](0044-klientskiy-api.md),
  [ADR-0019](0019-dostup-mashin.md), [ADR-0020](0020-fonovye-zadachi.md)

## Контекст

Клиентам с готовыми системами (SMS-шлюзы, CRM, рассылщики) удобнее подключиться стандартным
протоколом SMPP 3.4, чем писать запросы HTTP. Сообщение, принятое по SMPP, должно быть тем же
сообщением, что и принятое по HTTP: те же цена, деньги, очередь, возврат — иначе будет два
продукта с разным учётом.

## Решение

1. **Сервер SMPP — внутри процесса API**, а не отдельной службой. Причины: нужен доступ к тем же
   службам (деньги, сообщения, настройки), отдельный процесс означал бы новую единицу выкладки,
   юнит systemd и смоук ради одного слушающего сокета. Слушатель включается переменными окружения
   (`SMPP_PORT`, по умолчанию `0` — выключен; `SMPP_TLS_PORT` с `SMPP_TLS_CERT_FILE`/`SMPP_TLS_KEY_FILE`
   — то же по TLS). Перезапуск API (выкладка) рвёт сессии — клиенты SMPP переподключаются по своей
   природе. Если нагрузка потребует, слушатель переносится в отдельный процесс без изменения
   остального: он зависит только от `MessagesService`.
2. **Протокол — свой разбор PDU** (`smpp-codec.ts`, ~300 строк), без внешнего пакета: нужна малая
   часть SMPP 3.4 (`bind_*`, `submit_sm`, `deliver_sm`, `enquire_link`, `unbind`, `generic_nack`),
   а доступные пакеты — давно не обновляются (правило 11: зависимость берётся, когда своя реализация
   дороже сопровождения чужой — здесь наоборот).
3. **Учётная запись SMPP (`smpp_accounts`)** — одна на клиента: `system_id` (выдаёт площадка,
   `zx` + 8 знаков), пароль (16 случайных знаков, **показывается один раз**, хранится как SHA-256 с
   солью `system_id` — как ключи машин, ADR-0019: проверка на каждое подключение, а перебирать
   95 бит нечего), необязательный список разрешённых адресов (IPv4/IPv6; пусто — любые), включено
   или нет. Клиент сам создаёт, меняет пароль и отключает в кабинете.
4. **Подключение.** `bind_transmitter` / `bind_receiver` / `bind_transceiver`. Отказ: неверный
   `system_id`/пароль — `ESME_RINVPASWD`/`ESME_RINVSYSID`; адрес не разрешён, клиент не `active`,
   продукт выключен — `ESME_RBINDFAIL`. Защита: 5 неудач с одного адреса за минуту — соединение
   закрывается, а адрес на минуту не принимается; не более 5 сессий на учётную запись и 20 на адрес;
   не вошедший за 10 с отключается; тишина дольше 90 с — отключение (мы сами шлём `enquire_link`
   раз в 30 с).
5. **Приём `submit_sm`** → `MessagesService.send` того же клиента. Кодировки по `data_coding`:
   0 и 1 — Latin-1/ASCII (как принято у SMSC; кириллицу клиенты шлют в 8), 3 — Latin-1, 8 — UCS-2
   (UTF-16BE); текст из `message_payload` (TLV 0x0424) или `short_message`. Длинный текст по частям
   (UDH с `esm_class` 0x40 или TLV `sar_*`) собирается в одно сообщение; неполный набор через
   60 с отбрасывается с записью в журнал. В ответе `message_id` — идентификатор сообщения.
   Отказ → код SMPP: не тот номер/текст — `ESME_RINVDSTADR`/`ESME_RINVMSGLEN`; не хватает денег —
   `ESME_RSUBMITFAIL`; нет аккаунтов — `ESME_RTHROTTLED`; предел частоты — `ESME_RTHROTTLED`;
   прочее — `ESME_RSYSERR`. Идемпотентности по протоколу нет: повтор после обрыва создаёт второе
   сообщение — это свойство SMPP, не нашей реализации.
6. **Отчёты о доставке** — `deliver_sm` (`esm_class` 0x04, стандартный текст `id:… stat:DELIVRD …`).
   Сообщения живут в базе, а статусы меняет **воркер** (другой процесс), поэтому API **опрашивает базу**
   раз в 3 секунды, пока у клиента есть вошедший приёмник: `messages.channel = 'smpp'`,
   `receipt_sent_at is null`, статус `delivered`/`read`/`failed`, не старше 3 суток. Отметка
   `receipt_sent_at` ставится после `deliver_sm_resp` — доставка отчёта «хотя бы раз», а не «ровно раз»
   (так устроен SMPP). Нет приёмника — отчёт ждёт возвращения клиента. Состояние `sent` без
   подтверждения доставки отчёта не порождает.
7. **Деньги и права** — только через `MessagesService.send`: отдельного пути списания нет.
   Провайдер по-прежнему нигде не называется.
8. **Журнал.** Создание, смена пароля и отключение учётной записи — в журнал аудита (сам пароль
   не пишется).

## Следствия

- Миграция: таблица `smpp_accounts`, колонки `messages.channel` (`api`/`smpp`, по умолчанию `api`)
  и `messages.receipt_sent_at`.
- Порт SMPP наружу открывает владелец (файрвол сервера) и включает переменными окружения —
  выкладка их не меняет. Инструкция — [deploy/README.md](../../deploy/README.md).
- Не входит: `query_sm`, `cancel_sm`, `replace_sm`, `data_sm`, исходящие сообщения «с площадки» клиенту
  (ответы получателей — ADR-0071, «Не входит»), SMPP 5.0, отдельный процесс.
