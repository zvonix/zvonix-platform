# ADR-0046: Инициация вызова из API — платформа звонит обеим сторонам

- **Статус:** Принято — 2026-09-09, по решению владельца площадки
- **Дата:** 2026-09-09
- **Связано с:** [ADR-0009](0009-programmnaya-ats.md) (АТС и разделение плоскостей),
  [ADR-0044](0044-klientskiy-api.md) (клиентский API),
  [ADR-0010](0010-model-billinga.md) (модель биллинга),
  [ADR-0014](0014-vybor-partnera-klientom.md) (партнёр в клиентском контуре)

## Контекст

Сегодня клиент подключается к площадке **как к оператору связи**: получает учётную запись
SIP на свою линию, вбивает её в свою АТС или софтфон и звонит. Мы принимаем вызов
и соединяем. Клиенту для этого нужна собственная телефония.

Это отсекает тех, у кого её нет, — а это большинство мелких служб такси. И это не даёт
того, что в такси считается обязательным: **пассажир и водитель не должны узнавать
номера друг друга**.

Инициация из API снимает и то и другое. Программа диспетчера говорит: «соедини вот этого
с вот этим», и платформа звонит обоим сама. Диспетчеру не нужно ни АТС, ни софтфона —
только обращение к нашему API.

## Решение

### 1. Вызов из API — это два плеча, а не один вызов

Платформа звонит **обеим сторонам** и сводит их. Значит через партнёрские SIM уходят
два вызова, и оба тарифицируются: два резерва до начала, два списания после
([ADR-0010](0010-model-billinga.md)). Клиент платит за оба плеча — иначе половина
разговора уходит за наш счёт.

Это принципиально отличается от сегодняшней модели, где вызов один и платит клиент
за одно соединение. Прятать второе плечо в цене первого нельзя: плечи могут уйти через
**разных партнёров**, по разным ценам, и одно из них может не состояться.

Отсюда модель данных: **два `Call` со ссылкой на общую связку**. Не один вызов
с двумя номерами: у каждого плеча свой партнёр, своя SIM, своя цена, своя длительность
и своя причина отказа. Одна строка на два плеча означала бы, что половину этих полей
придётся удваивать в ней же.

### 2. Порядок плеч: сначала заказчик, потом абонент

Первым набирается тот, кто заказал соединение (в такси — водитель), и только после
его ответа — второй (пассажир). Обратный порядок заставляет пассажира слушать гудки,
пока водитель ищет телефон, и в половине случаев соединять уже некого.

Отказ на первом плече означает, что второго не было вовсе: второй абонент не должен
узнать о попытке, которая ни к чему не привела.

### 3. Номера не раскрываются — в этом и смысл

Каждая сторона видит **номер SIM партнёра**, через которую до неё дозвонились, а не номер
собеседника. Ни в одном ответе API номер второй стороны не появляется у первой.

Это накладывает ограничение на отбор: оба плеча по возможности уходят **через одну SIM**,
иначе стороны видят разные номера, и обратный звонок попадает не туда. Когда одной SIM
не хватает (разные операторы у сторон, занятость), плечи уходят через разные — и это
осознанная деградация, а не ошибка: соединение важнее красоты номера.

### 4. Команда доходит до узла по ESL, соединением на один вызов

Узел сегодня **спрашивает** control plane (`mod_xml_curl`) и никогда не слушает его.
Инициация требует обратного направления, и способов два:

| Способ | За | Против |
|---|---|---|
| **ESL с control plane** | `originate` вместе с `bridge` — одна команда, результат приходит по тому же соединению; задержка минимальна | Узел должен принимать соединение от control plane: порт `8021`, закрытый списком адресов |
| Агент узла опрашивает очередь команд | Ничего не нужно открывать на узле | Задержка на опрос там, где человек держит трубку; агент становится посредником в горячем пути; сведение двух плеч по опросу — это состояние, размазанное по двум сторонам |

**Выбран ESL, соединением на один вызов**: подключились, отдали `originate`, получили
результат, закрыли. Долгоживущего потребителя событий (`apps/esl` из
[ADR-0008](0008-stek.md)) для этого заводить не нужно — он понадобится позже, для событий
в реальном времени, и это отдельная работа.

Довод против опроса решающий: между «диспетчер нажал» и «пошёл гудок» стоит живой человек,
и лишние секунды здесь — не техническая мелочь, а причина, по которой сервисом
не пользуются.

### 5. Узел выбирает control plane, а не запрос

Сегодня узел приходит в запросе — его прислал он сам. При инициации узла в запросе нет,
и его выбирает control plane: тот, на котором зарегистрирован шлюз выбранного кандидата.
**Вызов уходит только на железо своего узла** — это правило не меняется, меняется лишь то,
кто его применяет.

### 6. Повтор не создаёт второго звонка

`POST /v1/calls` принимает ключ идемпотентности, как пополнение баланса
([ADR-0010](0010-model-billinga.md)). Сеть рвётся ровно тогда, когда ответ уже отправлен,
и повтор без ключа означал бы второй звонок живому человеку.

## Последствия

- **Положительные.** К площадке могут подключиться службы без своей телефонии — им
  достаточно обращения к API. Номера сторон не раскрываются, а это в такси обязательное
  требование, а не удобство.
- **Отрицательные и принятая цена.** Клиент платит за два плеча вместо одного, и это
  надо объяснять в контракте, а не обнаруживать в счёте. Узел начинает принимать
  соединения от control plane — новая дверь, которую закрывает список адресов.
- **Чего это решение не делает.** Оно не проверяется, пока не поднят хотя бы один узел:
  `originate` — это команда живому FreeSWITCH, и подтвердить её можно только на нём.
  Порядок работ поэтому такой: репозиторий пакетов → первый живой звонок по сегодняшней
  модели → инициация. Строить второе поверх непроверенного первого значит получить
  два непроверенных слоя и разбираться в них одновременно.
