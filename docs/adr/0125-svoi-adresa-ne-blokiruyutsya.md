# ADR-0125: Свои адреса узел не блокирует; отказ входа считается по логину; блокировки видны в кабинете

- **Статус:** Принято — 2026-11-18. Владелец: «Да, снять и чинить» (после бана живого клиента).
- **Дата:** 2026-11-18
- **Развивает:** [ADR-0051](0051-svoya-konfiguraciya-uzla.md) (защита узла fail2ban, ревизии 2026-09-22 и
  2026-09-25), [ADR-0019](0019-dostup-mashin.md) (машинный доступ узла), [ADR-0115](0115-uzel-zabiraet-komandy.md)
  (служба команд узла)
- **Связано с:** [ADR-0127](0127-invite-bez-parolya-blokiruetsya.md) — третья SIP-тюрьма, INVITE без пароля,
  с теми же доверенными адресами и в том же окне «Блокировки»

## Контекст

18.11.2026 на узле 217.197.114.163 тюрьма `zvonix-freeswitch` (чужие логины: 5 неудач за час — блок на сутки)
заблокировала живого клиента с 94.198.51.21. Ведущая сессия разобрала журнал узла:

- `mod_xml_curl` спрашивает учётную запись у площадки (`POST /node/directory`) с `timeout=3`. За день было 17 ошибок
  `CURL error 28 Timeout`, а в журнале доступа площадки в эти моменты запросов нет вовсе. Обычный запрос с узла
  проходит за 50 мс: DNS 2–4 мс, TLS около 45 мс.
- На таймауте FreeSWITCH не находит учётную запись и пишет две строки:
  `Can't find user [ch-or2hggbrys9g@sip.zvonix.local] from 94.198.51.21`, затем
  `SIP auth failure (INVITE) … for [+79330980320@sip.zvonix.com] from ip 94.198.51.21`.
- **У INVITE в скобках стоит номер назначения, а не логин.** Номер не начинается с `ch-`, поэтому строку считал
  фильтр чужих логинов. Пять таймаутов за час превратились в бан живого клиента на сутки.
- У партнёра 31.216.170.27 те же `Can't find user [pt-…]` на REGISTER. Они уходят в тюрьму своих логинов
  с порогом атаки, и бана пока нет.

## Решение

1. **Свои адреса не блокируются.** Площадка отдаёт узлу список доверенных адресов: откуда за последние 7 суток
   были успешные регистрации линий клиентов, шлюзов и линий GOIP (`registration_address` у `channels`, `gateways`,
   `gateway_ports`; пишется только после верного пароля, ADR-0101 и ADR-0103).
   - Отдаёт отдельный машинный обработчик `GET /node/trusted-addresses.txt` по ключу узла — по образцу
     `GET /node/sip-gateways.xml` (ADR-0118). Ответ — готовый текст для shell, адрес на строку; первая строка —
     метка `# zvonix-trusted`, без неё узел ответ не применяет.
   - Пульс узла раз в 30 секунд забирает список. Если список изменился, узел пишет `ignoreip` обеих SIP-тюрем
     в отдельный файл `jail.d/zvonix-freeswitch-trusted.local`, перечитывает только эти две тюрьмы и снимает бан
     с адресов из списка. Список не изменился — fail2ban не трогается.
   - Площадка недоступна или ответ не похож на список — прежний файл остаётся как есть.
   - Сканеры с чужих адресов блокируются как раньше.
   - Почему регистрации, а не вызовы: адрес регистрации записан только после верного пароля, его не подделать.
     Источник вызова площадка не хранит. Клиент, который звонит без регистрации, в список не попадает. Его
     защищает п. 2.
2. **Отказ входа считается по логину.**
   - Тюрьма чужих логинов считает только строки, где в скобках действительно логин: `SIP auth failure (REGISTER)`
     и `Can't find user`. Строку `SIP auth failure (INVITE)` она больше не считает: там номер назначения.
   - Тюрьма своих логинов (`gw-`, `ch-`, `pt-`; порог атаки — 1200 за 10 минут, блок на час) считает те же строки
     со своими логинами **и все** `SIP auth failure (INVITE)`.
   - **Дыры для подбора пароля через INVITE нет.** Неверный пароль к существующей линии даёт только строку
     `auth failure (INVITE)`, и она считается в тюрьме своих логинов. Пароль линии — 32 знака из 55-символьного
     алфавита: на пороге атаки его не подобрать.
   - Сканер с чужими логинами через INVITE по-прежнему даёт и `Can't find user [100@…]`, и попадает в тюрьму
     чужих логинов, как раньше.
   - Таймаут каталога при живом клиенте даёт `Can't find user [ch-…]` и `auth failure (INVITE)`. Обе строки
     считает тюрьма своих логинов, и семнадцать таймаутов в день до её порога не доходят.
3. **Таймаут каталога — 8 секунд** вместо 3 (`xml_curl.conf.xml`, привязка `zvonix-directory`).
   - Запрос учётной записи не на пути разговора. Он держит только регистрацию или первый INVITE, а их программа
     повторяет сама. Обрыв же стоит отказа и строки в журнале, которую считает fail2ban.
   - Маршрут на вызов (`zvonix-dialplan`) остаётся с `timeout=3`: там ждёт абонент, бюджет описан в
     [node.md](../api/node.md).
   - **Причина обрывов не установлена.** Запросов нет в журнале доступа площадки, а DNS узла отвечает за 2–4 мс.
     Значит, обрыв происходит до того, как запрос дошёл до nginx: в сети или при установке соединения. Это не DNS,
     поэтому запасные DNS и кэш DNS не добавляются. Если обрывы при 8 секундах останутся, нужен разбор сети узла
     с площадкой. Строка об этом — в [TASKS.md](../../TASKS.md).
4. **Блокировки видны в кабинете** — «Узлы АТС», значок «Блокировки»: адрес, тюрьма, до какого времени, и значок
   «Снять блокировку» с подтверждением и записью в журнал аудита (`node.ban_removed`).
   - Идёт через службу команд узла (ADR-0115), как проверка связи (ADR-0122). Добавлены две новые разрешённые
     команды: `zvonix-bans` (список, только чтение) и `zvonix-unban <адрес>`.
   - Адрес проверяется трижды: схемой API (IPv4 или IPv6), площадкой перед постановкой команды и скриптом узла
     (только цифры, точки и двоеточия, до 45 знаков). Блокировка снимается во всех трёх тюрьмах узла:
     две SIP-тюрьмы и SSH.
   - Узел на машине площадки команды получает по ESL, где этих команд нет. Тогда ответ — «узел не умеет эту
     команду», как у проверки связи.

## Последствия

- Миграций нет, API узла пополняется одним машинным обработчиком, кабинет — двумя административными.
- Узлы получают новые правила и пульс с обновлением набора (ADR-0068). Узел без обновления работает как прежде.
- Доверенный адрес не блокируется вовсе, даже при атаке с него. Это осознанно: адрес принадлежит тому, кто уже
  входил с верным паролем. Если такой адрес начнёт атаку, через 7 суток без новых регистраций он выпадет
  из списка сам.
