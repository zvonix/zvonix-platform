# ADR-0074: Обновление площадки из кабинета администратора

- **Статус:** Принято — 2026-10-06, решение владельца: «да, согласен» (схема «заявка и отдельная служба от root»,
  начинать с кнопки и онлайн-журнала, токен GitHub — тот, что лежит на сервере)
- **Дата:** 2026-10-06
- **Связано с:** [ADR-0049](0049-vykladka-ploshchadki.md) (выкладка), [ADR-0005](0005-migracii.md),
  [ADR-0062](0062-trevogi-administratoram.md), [ADR-0018](0018-autentifikaciya.md)

## Контекст

Выпуск выкладывает скрипт `zvonix-deploy` от root; запускать его приходилось по SSH. Владелец хочет делать это
сам из кабинета: видеть доступные версии, нажать «Обновить», смотреть журнал в реальном времени, при
необходимости откатить, отложить или отменить.

Главное ограничение — права. Кабинет и API работают от обычного пользователя `zvonix`; выкладка — от root.
Дать API право запускать root-скрипт значит превратить взлом кабинета во взлом сервера.

## Решение

1. **API ничего не запускает.** Он кладёт файл-заявку в каталог обмена `/var/lib/zvonix-updater/requests/`
   (запись только пользователю `zvonix`). Отдельная служба `zvonix-updater` (oneshot от root, запускается
   `zvonix-updater.path` по появлению файла и `zvonix-updater.timer` раз в 10 минут) читает заявки и сама
   вызывает `zvonix-deploy`. Служба обновления **не перезапускается выкладкой** — иначе она убила бы себя
   посреди обновления.
2. **Заявке не доверяют.** Служба читает файл без перехода по ссылкам, не больше 4 КБ, действие — только из
   списка (`deploy`, `rollback`, `refresh`), метка — по строгому шаблону выкладки, идентификатор — UUID. Значения
   никогда не попадают в командную строку через оболочку: только список аргументов.
3. **Состояние и журнал — файлы службы.** Для каждой заявки служба создаёт `runs/<id>/` (читается всеми,
   пишет только root): `state.json` (queued / running / succeeded / failed / cancelled, время, код возврата) и
   `log` (вывод выкладки построчно). API отдаёт журнал кусками по смещению; кабинет опрашивает раз в секунду.
   Опрос, а не SSE: выкладка перезапускает API, и опрос переживает это без особой обработки. Шаги выкладки
   (`=== …`) кабинет разбирает из журнала и рисует как прогресс.
4. **Список выпусков** (`releases.json`) готовит та же служба: у неё есть токен (`/etc/zvonix/github.env`,
   читаем только root), у API его нет и быть не должно. Обновляется раз в 10 минут и по кнопке «Обновить
   список» (заявка `refresh`).
5. **Очередь одна.** Служба обрабатывает заявки по порядку; выкладка берёт замок `flock`, поэтому ручной
   `zvonix-deploy` по SSH и кнопка не столкнутся. Заявку в очереди (ещё не принятую службой) можно
   отменить — API удаляет файл. Принятую отменить нельзя: после начала выкладки она доводится до конца или
   сама возвращает прежний выпуск (ADR-0049).
6. **Доступ — только администратор.** Метка проверяется по списку выпусков, а не принимается произвольной.
   Каждая заявка пишется в журнал действий (кто, какое действие, какая метка). Нет каталога обмена — раздел
   честно говорит «обновление из кабинета не настроено» и ничего не предлагает.
7. **Этапы.** 1 — кнопка, журнал онлайн, откат (этот ADR). 2 — проверка перед обновлением (диск, свежесть
   копии базы, разбор миграций, пробный запуск выпуска на запасном порту). 3 — отложенный запуск
   (`not_before` в заявке уже предусмотрен форматом) и отмена. Каждый этап выкладывается отдельно.

## Ревизия 2026-10-07 — этап 2: проверка перед установкой

- `zvonix-deploy --prepare <метка>` скачивает, распаковывает и проверяет выпуск, ничего не устанавливая; `zvonix-deploy
  <метка>` сам делает то же до миграций, если подготовленного выпуска нет. Отказ проверки — установка не начинается.
- Проверки: место на диске (выпуски от 1 ГБ, копии от 512 МБ), свежесть суточной копии (только предупреждение), состав
  выпуска и **репетиция**: `pg_dump` рабочей базы → временная база → миграции выпуска → API выпуска на порту 18000 до
  `/health/ready`. Репетиция ловит то, чего не видно по тексту миграций: поведение на настоящих данных и запуск кода.
- Почему не `migration-risk`: он читает историю git, а на сервере её нет; разбор текста миграций остаётся за выпуском
  (`/release`). Репетиция его дополняет, а не заменяет.
- Скачивание идёт с докачкой и повторами: канал сервера до GitHub бывает ~11 КБ/с, архив в 15 МБ тогда качается 25
  минут. Поэтому «подготовить» вынесено отдельным шагом: долгое — заранее и видно в журнале, быстрое — в момент установки.
- Не покрыто: рабочая нагрузка на запасном порту и кабинет (Next) не проверяются — только API. Запись разговоров и узлы
  АТС репетиция не затрагивает.

## Последствия

- Обновление не зависит от того, жив ли кабинет в момент выкладки: служба и журнал на диске.
- Выкладка из кабинета и по SSH равноправны, оба оставляют один и тот же след в журнале сервера.
- Новая поверхность: каталог обмена. Худший случай при взломе API — поставить в очередь выпуск **из списка
  реальных выпусков** или откат; произвольный код выполнить нельзя.
- Копия базы лежит на том же сервере (ADR-0049): внешняя копия остаётся открытым хвостом и нужна до того, как
  кнопка начнёт использоваться на боевой площадке.
- Не решено сознательно: обновление без перерыва (два экземпляра за nginx). Переключение занимает секунды,
  звонки на узлах идут, кабинет и API недоступны на это время.
