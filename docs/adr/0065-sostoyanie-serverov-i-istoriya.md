# ADR-0065: Состояние серверов, история нагрузки и сроки хранения

- **Статус:** Принято — 2026-10-03, предложение владельца: «в админку добавить информацию по
  серверу, нагрузку, графики, историю; настройка хранения логов, записей» и «делай всё, что
  порекомендуешь»
- **Дата:** 2026-10-03
- **Связано с:** [ADR-0020](0020-fonovye-zadachi.md) (фоновые задачи),
  [ADR-0031](0031-nastroyki-ploshchadki.md) (настройки площадки),
  [ADR-0062](0062-trevogi-administratoram.md) (тревоги), [ADR-0063](0063-hranilishche-zapisey-na-diske.md)
  (записи на диске), [ADR-0019](0019-dostup-mashin.md) (ключ узла)

## Контекст

Площадка видит про узел только «на связи / нет» и число звонков. Про сам сервер площадки —
ничего: диск с записями заполнится, и об этом узнают по отказам. Истории нет, так что вопрос
«почему вчера вечером всё тормозило» не имеет ответа. Срок хранения записей задан файлом
окружения, то есть меняется только правкой на сервере и перезапуском.

## Решение

1. **Таблица `server_metrics`** — по строке на замер: источник (`node_id`, пусто — сама
   площадка), время, нагрузка процессора (`load1`, сотые доли), память (всего / доступно, МБ),
   диск (всего / свободно, МБ), число активных вызовов (только у узла). Целые числа, без
   дробных. Индекс по `(node_id, taken_at)`.
2. **Откуда замеры.**
   - **Площадка** — задача воркера `servers.sample` раз в минуту: нагрузка и память ОС, диск
     каталога записей (если его нет — корня). Воркер стоит на той же машине, что и API.
   - **Узел** — `POST /node/metrics` по ключу узла, раз в минуту скриптом пульса. Отдельный
     обработчик, а не поля пульса: модуль серверов зависит от модуля узлов, обратной зависимости
     быть не должно. Узел, у которого скрипт старый, просто не присылает замеры — на странице
     «нет данных», ничего не ломается.
3. **Страница «Серверы»** (администратор и поддержка, только чтение): по карточке на площадку
   и на каждый узел — нагрузка, память, диск, состояние, и график за час / сутки / неделю.
   Графики — свой SVG без новой зависимости: нужна ломаная линия на 60–700 точках.
   Историю API отдаёт **уже прореженной** на стороне базы (корзины по времени), а не сырыми
   строками.
4. **Сроки хранения — в настройках площадки** (ADR-0031), меняются мышью без перезапуска:
   - `retention.recordings_days` — срок хранения записей разговоров, по умолчанию 30 (как было на
     сервере), от 1 до 3650. **Заменяет** переменную `RECORDING_RETENTION_DAYS`: у одного значения не должно быть
     двух источников. Действует на записи, принятые **после** изменения: срок уже записан у каждой
     записи, задним числом он не пересчитывается.
   - `retention.metrics_days` — сколько хранится история замеров, по умолчанию 14, от 1 до 90;
     уборка — задача раз в час, догоняющая (ADR-0020).
5. **Что намеренно не настраивается.** Журнал действий и проводки — основание спора о деньгах,
   их срок не «настройка». Журнал процессов (`journalctl`) — сторона операционной системы:
   его объём задаётся её настройками, кабинет к ним доступа не имеет.
6. **Тревога о диске** (ADR-0062, четвёртое условие): свободного места меньше 10 % у площадки
   или узла — письмо администраторам, повтор по источнику раз в 12 часов. Условие по последнему
   замеру, а не по событию. Замер старше 15 минут не считается: молчащий узел — другая тревога.
7. **Лёгкий размер.** Одна строка — около 60 байт; минута × 14 суток × (площадка + 5 узлов) —
   порядка 120 тысяч строк, единицы мегабайт.

## Не входит

Графики по звонкам и деньгам, сеть и ввод-вывод диска, нагрузка по отдельным процессам, внешние
системы наблюдения (Prometheus) — при росте площадки их место, но сейчас это лишняя
инфраструктура. Telegram-тревоги — отдельно.

## Последствия

- Узлы, поставленные раньше, присылают замеры только после обновления скрипта пульса
  (`zvonix-node-update` или повторная установка): до этого карточка узла показывает «нет данных».
- Переменная `RECORDING_RETENTION_DAYS` убрана из схемы конфигурации, `.env.example` и
  `zvonix.env`; оставшаяся в файле на сервере — безвредна, её никто не читает.
- Понижение срока хранения записей не удаляет уже принятые раньше срока: это осознанно, чтобы
  случайная правка не стёрла архив одним нажатием.
