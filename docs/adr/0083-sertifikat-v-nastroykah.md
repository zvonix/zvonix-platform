# ADR-0083: Сертификат кабинета в настройках — даты, выпуск, автопродление

- **Статус:** Принято — 2026-10-12; владелец: «в настройках выпустить сертификат, показывать когда
  выпущен и до какого действует, и галочка — продлевать автоматом»
- **Дата:** 2026-10-12
- **Развивает:** [ADR-0049](0049-vykladka-ploshchadki.md) (сертификат Let's Encrypt, `certbot.timer`),
  [ADR-0074](0074-obnovlenie-iz-adminki.md) (служба обновления от root, каталог обмена),
  [ADR-0082](0082-sayt-proekta.md) (сертификат на три имени)

## Контекст

Сертификат выпускается при установке (`deploy/server-setup.sh`) и продлевается таймером пакета `certbot`.
Из кабинета это не видно: нет ни срока, ни имён, которые он закрывает, ни способа выпустить заново. Предупреждение
браузера на основном домене мы нашли только потому, что владелец открыл его в браузере. API работает без прав
root, а `/etc/letsencrypt` закрыт для пользователя `zvonix`.

## Решение

1. **Состояние читает служба обновления, а не API.** Каждый запуск `zvonix-updater` (таймер — раз в десять
   минут, плюс после каждой заявки) читает `fullchain.pem` через `openssl x509`, состояние `certbot.timer`
   через `systemctl` и пишет `certificate.json` в каталог обмена. API его только читает.
2. **Действия — заявки той же службе** (ADR-0074), четыре: `cert-check`, `cert-issue`, `cert-auto-on`,
   `cert-auto-off`. Заявки идут по одной вместе с выкладкой; `cert-check` — лёгкая, как `refresh`.
3. **Имя сертификата в заявке не передаётся.** Служба берёт его из `WEB_BASE_URL` в `zvonix.env` и из
   `/etc/zvonix/site-domain` (имена: кабинет, основной домен, `www`), как и установка. Выпустить сертификат
   на чужое имя через API нельзя; это проверено тестом.
4. **Выпуск** — `certbot certonly --webroot --expand --force-renewal` под тем же `--cert-name`, что и при
   установке; после него `systemctl reload nginx` (`--deploy-hook`). Повтор чаще раза в десять минут API
   отклоняет: у Let's Encrypt пределы на дубликаты и на ошибки.
5. **Автопродление — это таймер**, а не отдельная настройка: галочка включает или выключает `certbot.timer`
   (`enable --now` / `disable --now`), а её состояние читается обратно из systemd. Второго источника правды нет.
6. **Состояние для кабинета** вычисляется API: `ok`, `soon` (осталось 14 суток и меньше), `expired`,
   `incomplete` (сертификат не закрывает все ожидаемые имена), `missing`, `not_configured` (кабинет без домена),
   `unknown` (служба ещё не читала). Все действия — только администратору и в журнале действий.
7. **Раздел «Сертификат» — в настройках площадки**, а не отдельной страницей: владелец искал его там.

## Последствия и риски

- Выпуск идёт от root и меняет то, что видят посетители. Поэтому домен берётся только из файлов root,
  заявка не несёт данных, а действие подтверждается окном.
- Нет службы обновления (разработка, площадка до выкладки с этой возможностью) — раздел говорит «не прочитан»,
  а не придумывает состояние.
- Служба читает сертификат раз в десять минут, поэтому после ручной правки на сервере раздел отстаёт до десяти
  минут; кнопка «Проверить» читает сразу.
- Письмо администраторам при `soon`/`expired` — отдельным шагом (тревоги, ADR-0062): записано в TASKS.md.

## Проверено

Служба — с подставными `openssl`, `certbot` и `systemctl` (`tests/updater-cert.test.ts`): имена и дата,
отказ certbot, домен из заявки игнорируется, автопродление. API — интеграционными тестами раздела обновлений.
**Не проверено до живого сервера:** реальный выпуск `certbot` с расширением на работающем сервере и вывод
`openssl` на его версии (разбор рассчитан на OpenSSL 3).
