# ADR-0002: Конфигурация через единый валидируемый модуль

- **Статус:** Принято
- **Дата:** 2026-09-01

## Контекст

Приложение работает минимум в двух средах (разработка — Windows, production — Ubuntu)
и будет расти. Типичная деградация: обращения к переменным окружения разбросаны по всему
коду, значения читаются как строки без проверки, а отсутствие переменной обнаруживается
не при запуске, а в момент первого обращения — часто в проде и не сразу.

## Рассмотренные варианты

1. **Читать окружение по месту использования** — ноль подготовки, но нет ни списка
   требуемых переменных, ни валидации, ни типов; ошибка конфигурации всплывает случайно.
2. **Конфиг-файлы по средам (config.dev, config.prod)** — наглядно, но секреты тянет
   в репозиторий и плохо ложится на запуск в контейнерах и CI.
3. **Единый модуль конфигурации, читающий окружение и валидирующий его схемой при старте** —
   один список переменных, типы, fail-fast.

## Решение

Вариант 3.

- Весь доступ к окружению — **только** внутри модуля конфигурации. Нигде больше в коде
  прямого чтения переменных окружения нет.
- Модуль описывает схему: имя, тип, обязательность, значение по умолчанию, допустимый диапазон.
- Валидация выполняется **один раз при старте приложения**. При любой ошибке — падение
  с внятным сообщением, перечисляющим все проблемные переменные сразу, а не первую.
- Секреты никогда не попадают в логи и в текст ошибок валидации (печатается имя переменной,
  не значение).
- `.env.example` лежит в репозитории и содержит **все** переменные с безопасными
  значениями-заглушками и комментарием, зачем каждая нужна. Реальный `.env` — только локально.
- Добавление переменной = правка схемы + `.env.example` в том же изменении.

## Последствия

- Положительные: неверная конфигурация ловится при запуске, а не в проде; список требуемых
  переменных всегда актуален; типы вместо строк.
- Отрицательные: любое добавление переменной требует правки в двух местах.
- В коде: прямое чтение окружения вне модуля конфигурации — нарушение, правится при ревью.
