# ADR-0008: Технологический стек

- **Статус:** Принято
- **Дата:** 2026-09-01

## Контекст

Система состоит из control plane (деньги, тарифы, права, маршрутизация в реальном времени),
кабинетов трёх ролей, агента на узлах и Android-приложения партнёра.
Определяющие требования:

- **Корректность денег важнее всего.** Ошибка в тарификации — прямой убыток.
- **Горячий путь маршрутизации.** FreeSWITCH через `mod_xml_curl` запрашивает решение
  на **каждый** вызов и ждёт ответа. Бюджет — десятки миллисекунд.
- **Долгоживущее соединение ESL** с каждым узлом для событий и метрик в реальном времени.
- **Постоянные фоновые процессы**: сверка CDR, выплаты, агрегация ASR, освобождение
  зависших резервов, обновление базы MNP.
- Существенный объём интерфейса: админка и два кабинета.

## Вопрос: подходит ли Next.js

Next.js рассматривается отдельно, потому что вопрос был задан прямо.

**Что Next.js делает отлично:** интерфейс. Роутинг, серверный рендеринг, формы, загрузка
данных, готовая сборка. Для админки и двух кабинетов — сильный выбор, особенно в связке
с shadcn/ui, под которую уже подключены MCP-серверы.

**Чего Next.js не делает.** Это фреймворк приложения-интерфейса с приложенным бэкендом,
а не платформа для сервиса с фоновой работой:

| Требование | Как ложится на Next.js |
|------------|------------------------|
| Горячий путь маршрутизации | Route Handler ответит за нужное время, но проходит через слой, спроектированный под страницы, а не под RPC с бюджетом в миллисекундах |
| Долгоживущий ESL к узлам | Не ложится: модель Next.js — обработка запроса, а не постоянно живущий процесс. Нужен отдельный сервис |
| Фоновые задачи и расписания | Отсутствуют как понятие. Нужен BullMQ и отдельный воркер-процесс |
| Сверка, выплаты, агрегации | Отдельный процесс |

То есть при выборе «всё на Next.js» через месяц рядом всё равно появятся два-три отдельных
Node-сервиса — и Next.js окажется тем, чем и является: фронтендом.

**Отдельно про деньги.** Ранее в этом ADR утверждалось, что JavaScript плохо подходит
для денег из-за отсутствия десятичного типа. Это утверждение было слишком широким:
при хранении сумм **целыми числами микроединиц** (принято в [ADR-0010](0010-model-billinga.md))
арифметика ведётся в `BigInt` и точна. Требуется дисциплина — запрет `number` для денег,
аккуратная сериализация `BigInt` в JSON — но это закрывается типами и правилом линтера,
а не выбором языка.

## Варианты

| Вариант | За | Против |
|---------|-----|--------|
| **A. Next.js (фронт) + Python/FastAPI (бэк)** | Встроенный `Decimal`; зрелый SQLAlchemy + Alembic; много разработчиков | Два языка, два набора типов, ручная синхронизация контрактов фронта и бэка |
| **B. Полностью TypeScript: Next.js + NestJS + BullMQ** | Один язык на весь проект; **общие типы и zod-схемы между фронтом и бэком** — целый класс ошибок исчезает; NestJS даёт модульность и DI, что прямо ложится на модульную архитектуру; ESL и BullMQ — зрелые пакеты | Деньги требуют дисциплины (`BigInt`, запрет `number`); Node однопоточен — тяжёлые агрегации выносятся в воркеры |
| **C. Next.js как единственный бэкенд** | Меньше всего сервисов на старте | Не покрывает ESL, фоновые задачи и расписания. Через месяц превращается в вариант B, но без его структуры |

## Решение

**Вариант B — полностью TypeScript.**

- **Фронтенд:** Next.js (App Router) · TypeScript · TanStack Query · shadcn/ui
- **Бэкенд:** NestJS · TypeScript в строгом режиме · zod для схем, общих с фронтендом
- **Данные:** PostgreSQL 16 · Drizzle ORM (близость к SQL важна для отчётности и биллинга;
  альтернатива — Prisma) · миграции drizzle-kit
- **Очереди и счётчики:** Redis 7 · BullMQ для фоновых задач и расписаний
- **Записи:** MinIO, S3-совместимое хранилище
- **Телефония:** FreeSWITCH ([ADR-0009](0009-programmnaya-ats.md)); `mod_xml_curl` ходит
  в NestJS за маршрутом, ESL-потребитель — отдельный сервис в том же монорепозитории
- **Агент узла:** TypeScript, собранный в самодостаточный бинарник (`bun build --compile`) —
  сохраняет установку одной командой без рантайма на узле и не добавляет третий язык
- **Android:** Kotlin — альтернативы нет
- **Метрики:** Prometheus + Grafana

Обоснование выбора B над A: проект ведёт один разработчик. Общие типы и схемы валидации
между фронтом и бэком экономят больше, чем даёт встроенный `Decimal` в Python, — тем более
что деньги всё равно хранятся целыми числами, где `Decimal` не нужен.

## Последствия

- Положительные: один язык; контракт между фронтом и бэком проверяется компилятором,
  а не соглашением; NestJS-модули совпадают с модулями из `ARCHITECTURE.md`.
- Отрицательные: деньги требуют дисциплины — обязательны тип-обёртка для сумм и правило
  линтера, запрещающее `number` в денежных вычислениях; тяжёлые отчёты выносятся в воркеры.
- В коде: `strict: true` в TypeScript; денежные величины — только `BigInt` в микроединицах;
  `number` для денег — ошибка линтера, а не замечание на ревью.
