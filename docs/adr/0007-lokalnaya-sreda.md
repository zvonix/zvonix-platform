# ADR-0007: Локальная среда разработки при Windows → Ubuntu

- **Статус:** Принято
- **Дата:** 2026-09-01

## Контекст

Разработка ведётся на Windows, production — Ubuntu. Расходятся не «операционные системы
вообще», а конкретные вещи:

| Что расходится | Чем грозит | Ловится без изоляции? |
|----------------|------------|------------------------|
| Регистр в именах файлов | `UserService` импортирован как `userService` — на Windows работает, на Ubuntu падает | Нет |
| Версии инфраструктуры (БД, кэш, очередь) | Локально одна версия СУБД, в проде другая: разное поведение запросов и типов | Нет |
| Нативные зависимости и бинарники | Пакет собран под Windows, в проде отсутствует | Нет |
| Права на файлы, локаль, таймзона | Расхождения в правах и форматировании дат | Нет |
| Переводы строк | Ломает shell-скрипты | Да — `.gitattributes` |
| Разделители путей | Падение при работе с файлами | Частично — правило 5 в `CLAUDE.md` |

Первые четыре строки дисциплиной не закрываются. Вопрос в том, чем их закрыть.

## Состояние машины на момент решения

Проверено 2026-09-01:

- **WSL2 с Ubuntu 24.04 уже установлен** (состояние `Stopped`). Ставить ничего не нужно.
- **Docker не установлен.**
- node 24.15, npx 11.12, uvx 0.11.7, python 3.12.8, git 2.53 — доступны в Windows.

## Рассмотренные варианты

1. **Ничего, только CI на Ubuntu.**
   Ноль настройки. Расхождение ловится, но поздно — после отправки кода, а не при написании,
   и разбирается по логам CI вместо локального воспроизведения. Версии инфраструктуры
   не совпадают с продом вообще.

2. **WSL2 как основная среда разработки.** ← уже установлен
   Это настоящая Ubuntu на той же машине: тот же регистрозависимый диск, те же бинарники,
   те же права. Бесплатно, ставится одной командой, VS Code и Claude Code работают внутри
   штатно. Не решает только одно — совпадение версий БД и других сервисов
   (их придётся ставить в WSL руками и следить за версиями).

3. **Docker Compose.**
   Закрывает всё, включая версии инфраструктуры: одна команда поднимает те же СУБД, кэш
   и очередь, что в проде. Цена — Docker Desktop на машине, потребление ресурсов,
   и лишний слой при отладке.

4. **WSL2 + Docker внутри него.**
   Максимальное совпадение с продом. Цена — обе технологии сразу.

## Рекомендация

**Вариант 2 сейчас, вариант 4 — когда появится БД.**

Обоснование: WSL2 с Ubuntu 24.04 на машине уже есть, а Docker — нет. Пока в проекте нет
инфраструктурных сервисов, Docker закрывает ровно то же, что WSL2, но дороже и требует
установки. Как только появляется СУБД, разница версий становится реальным
источником ошибок, и Docker для сервисов окупается — при этом WSL2 остаётся средой,
и переход не требует переделки.

Вариант 1 не рекомендуется как единственная мера: он не защищает во время написания кода,
а именно там ошибки регистра и путей возникают.

CI на Ubuntu нужен при любом варианте — как обязательная проверка перед мержем,
но не как замена локальной среде.

## Решение

**Вариант 2: WSL2 (Ubuntu 24.04) как основная среда разработки.**
Docker будет добавлен внутрь WSL2 отдельным ADR, когда в проекте появится СУБД
или другой инфраструктурный сервис — до этого момента он не даёт ничего сверх WSL2.

Из этого следует:

- Код запускается, тестируется и проверяется **в WSL2**, а не в Windows.
- Единая точка проверки — `scripts/check.sh`. Дублирующий `scripts/check.ps1` удалён:
  два скрипта, обязанных оставаться идентичными, — источник расхождения
  «локально проходит, в CI падает», а с WSL2 второй скрипт не нужен.
- Репозиторий рекомендуется держать **внутри файловой системы WSL2**
  (например `~/projects/zvonix`), а не на `/mnt/d`. Доступ к дискам Windows из WSL2
  идёт через 9p и работает в разы медленнее — на большом проекте это ощутимо
  замедляет установку зависимостей, сборку и тесты.
- CI на `ubuntu-latest` сохраняется как обязательная проверка перед мержем.

## Последствия

- Положительные: регистрозависимая ФС, Linux-права, Linux-бинарники и та же версия
  Ubuntu, что в проде — расхождения ловятся при написании кода, а не после отправки.
  Ничего устанавливать не потребовалось.
- Отрицательные: версии СУБД и других сервисов пока не совпадают с продом — это
  остаётся непокрытым риском до появления Docker. Работа через `/mnt/d` медленная,
  поэтому желателен перенос репозитория в ФС WSL2.
- В коде: скрипты и команды пишутся под Linux; Windows-специфичных путей быть не должно.

## Ревизия 2026-09-01: решение на практике не выполняется

Обнаружено при подключении базы данных. Записано здесь, а не только в обсуждении,
потому что расходится с принятым решением и требует явного выбора.

**Факты:**

1. **Проверки выполняются в Windows, а не в WSL2.** Оболочка, из которой запускался
   `scripts/check.sh` во всех сессиях, — Git Bash (MSYS) на Windows. Vitest сообщает
   корень как `D:/Мои разработки/Zvonix`, а не `/mnt/d/…`. То есть пункт «код запускается,
   тестируется и проверяется в WSL2» не соблюдался ни разу с момента принятия ADR.
2. **WSL2 сейчас не отвечает.** Дистрибутив `Ubuntu-24.04` в состоянии `Stopped`;
   ни `wsl -d Ubuntu-24.04 -- echo`, ни `wsl --shutdown` не завершаются за две минуты.
   Похоже на зависшую виртуальную машину; чинится, как правило, перезагрузкой
   или перезапуском службы `LxssManager` (требует прав администратора).
3. **PostgreSQL 16.10 поставлен в Windows** — переносимыми бинарниками EDB
   в `C:\Users\admin\.local\pg`, без установщика, службы и прав администратора,
   данные в `C:\Users\admin\.local\pg\data`. Это отступление от решения ADR-0007,
   сделанное вынужденно: без базы нельзя ни применить миграцию, ни выполнить
   интеграционные тесты, которых требует [ADR-0006](0006-strategiya-testirovaniya.md).

**Управление локальной базой** (Git Bash, без прав администратора):

```bash
PG=/c/Users/admin/.local/pg
$PG/pgsql/bin/pg_ctl.exe -D $PG/data -l $PG/pg.log -o "-p 5432 -c listen_addresses=127.0.0.1" start
$PG/pgsql/bin/pg_ctl.exe -D $PG/data status
$PG/pgsql/bin/pg_ctl.exe -D $PG/data stop
```

Заведены роль `zvonix` с паролем `zvonix` и базы `zvonix` (разработка) и `zvonix_test`
(интеграционные тесты). Кодировка UTF8, локаль `C` — детерминированная сортировка,
которая не ломается при смене версии glibc на сервере. Пароль суперпользователя
`postgres` — `postgres`; сервер слушает только `127.0.0.1`. Это учебные значения
для локальной машины, в прод они не переносятся.

**Что это меняет по существу.** Из четырёх расхождений, ради которых принималось решение,
без WSL2 остаются непокрытыми регистр в именах файлов, нативные зависимости, права и локаль.
Первое закрывает отдельная задача CI (`case-sensitivity`), остальные — нет.
Версия PostgreSQL теперь совпадает с продом (16), и интеграционные тесты в CI выполняются
на `postgres:16` в Ubuntu — то есть по базе покрытие как раз есть.

**Требуется решение** (записано в [TASKS.md](../../TASKS.md)): чинить WSL2 и переносить
разработку туда, как решено в этом ADR, — либо признать средой разработки Windows,
оставив Ubuntu только в CI и проде, и заменить это решение новым ADR. До выбора
действует фактическое положение: разработка в Windows, проверка расхождений — в CI.
