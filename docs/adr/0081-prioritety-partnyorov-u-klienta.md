# ADR-0081: Приоритеты партнёров у клиента — один список на клиента, цифры, звонки и MAX

- **Статус:** Принято — 2026-10-10; владелец: «цифрами, одна цифра у нескольких — поочерёдное использование»,
  «ступени — да», «список — делай как рекомендуешь»
- **Дата:** 2026-10-10
- **Развивает:** [ADR-0014](0014-vybor-partnera-klientom.md), [ADR-0021](0021-ravnomernoe-raspredelenie.md),
  [ADR-0040](0040-poryadok-terminacii-predlozhenie-i-cena.md), [ADR-0080](0080-edinye-limity-i-raspredelenie.md)

## Контекст

У клиента звонки и сообщения MAX, партнёров может быть сто и больше. Клиент хочет сказать: «сначала звонить
и писать через этих, а если у них по лимитам всё занято — через следующих».

Что было:

- **Звонки.** Порядок задаётся **на каждую линию** (`channel_partner_priorities`), список закрытый: кого в нём нет,
  тот не используется. При ста партнёрах и нескольких линиях это ручная расстановка сотни цифр по нескольку раз,
  а новый партнёр площадки не используется, пока его не вписали.
- **Сообщения MAX.** Приоритетов у клиента нет: аккаунты берутся из самой дешёвой цены.

## Решение

1. **Один список на клиента**, отдельно для звонков и для сообщений MAX (`client_partner_priorities`): партнёр
   (у звонков — предложение: SIM или транк, ADR-0040), цифра 1–99 или «не использовать». Цифра меньше — раньше.
2. **Одинаковая цифра у нескольких — поочерёдно.** Внутри цифры сначала цена (дешевле раньше, ADR-0040), при равных —
   по давности (ADR-0021).
3. **Список открытый.** Кого в нём нет, используется **после** всех названных: новый партнёр площадки клиенту
   не пропадает. Отказаться от партнёра — явная отметка «не использовать» (строка без цифры).
4. **Линия может иметь свой список** (прежний `channel_partner_priorities`, его поведение не меняется: закрытый
   список линии). Есть своя строка у линии — действует он; нет — список клиента. Только для звонков: сообщения
   привязаны к клиенту.
5. **«Всё занято — следующая цифра».** Звонки: перебор идёт по цифрам, карта исчерпала лимит или занята — берётся
   следующий кандидат (уже так, ADR-0026). MAX: аккаунты берутся по цифрам; если у всех партнёров цифры нет свободного
   аккаунта с запасом по лимитам, берётся следующая цифра. Если свободных нет вообще — сообщение ждёт в очереди первой
   цифры, а не уходит к дорогому партнёру «на всякий случай».
6. **Цена для клиента — принятая.** Следующая цифра может быть дороже: порядок задал клиент, и цены в списке
   показываются рядом.
7. **Клиент не видит партнёра** (ADR-0014): список строится по псевдонимам.

## Хранение и границы модулей

- Таблица `client_partner_priorities` (клиент, партнёр, предложение `sim`/`sip`/`message`, цифра или пусто, отметка
  последнего маршрута для поочерёдности). Уникальность — клиент + партнёр + предложение.
- Чтение и запись списка — модуль `priorities` (репозиторий, сервис с журналом `client_partner_priorities.set`,
  контроллер кабинета клиента). Отбор SIM-кандидатов читает таблицу в том же запросе и той же транзакцией отмечает
  маршрут, как у приоритетов линии (ADR-0021); выбор аккаунта MAX читает список сервисом.

## Последствия и риски

- Клиент с сотней партнёров расставляет цифры один раз, а не по линиям; новый партнёр не требует ничего.
- Закрытый список линии остаётся: у существующих линий поведение не меняется.
- Горячий путь звонков получает один дополнительный join по индексу (клиент, партнёр, предложение); замер — в отчёте.
- Выбор MAX идёт по цифрам: на каждую цифру один запрос кандидатов вместо одного (цифр обычно две-три).

## Что не делаем сейчас

- Веса вместо цифр внутри цифры, «строго по кругу без учёта цены» — переключатель добавим, если понадобится.
- Приоритеты по операторам направления (разные порядки на МТС и Билайн) — список один на клиента.
