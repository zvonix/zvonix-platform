# ADR-0088: Отчёты по сообщениям MAX и защита аккаунтов от блокировок

- **Статус:** Принято — 2026-10-20; владелец: «отчёты и логи, которые рекомендуешь», «СТОП галочкой у партнёра и полем в шаблоне»,
  «рекомендованные лимиты — параметры в админке, партнёрам не показывать», «если не прочитал — следующее позже»; порядок работ
  утверждён им же, держаться его
- **Дата:** 2026-10-20
- **Связано с:** [ADR-0071](0071-soobscheniya-max.md), [ADR-0078](0078-progrev-akkauntov-max.md) (прогрев),
  [ADR-0079](0079-raspredelenie-soobscheniy-i-zdorove-akkauntov.md) (здоровье аккаунтов), [ADR-0077](0077-bot-max-vtoroy-kanal.md),
  [ADR-0087](0087-konstruktor-soobshcheniya.md), [ADR-0005](0005-migracii.md)

## Контекст

Аккаунты партнёров — экземпляры стороннего провайдера, MAX блокирует их за поведение: объём, много номеров без MAX, жалобы.
Площадка видела только текущее состояние аккаунта, а не историю и не причины; ответы людей («СТОП») через аккаунты не читались.

## Решение (порядок утверждён владельцем)

1. **Отчёты для сотрудников — сделано.** `GET /messages/report?days=` (роли `admin`, `support`; 1–90, по умолчанию 7): по клиентам и по
   аккаунтам — принято, ушло, доставлено, прочитано, не отправлено с разбивкой по причинам, ушедшие через аккаунты старше суток и из них
   прочитанные. Страница «Отчёты MAX» в меню сотрудников. Новых таблиц нет: всё считается по `messages`. «Не прочитано» не считается у
   сообщений бота (статуса «прочитано» у бота нет) и у свежих (младше суток); меньше 20 ушедших — прочерк. Подсвечивается доля
   непрочитанных от 70 % и отказов «нет MAX» от 30 %. Чего отчёт **не** показывает: историю блокировок (у аккаунта хранится только
   текущее состояние) — её даст журнал здоровья (шаг 4).
2. **«СТОП» для аккаунтов партнёров** (следующий шаг, нужна миграция). Приём входящих от провайдера; ответ «СТОП» заносит номер в
   общий список «не писать»: ему не пишет никто, ни аккаунтами, ни ботом; сообщение на такой номер отклоняется до списания денег.
   У партнёра галочка «Добавлять строку про СТОП» для его аккаунтов; клиенты видят, на каких путях строка включена, а предпросмотр
   в конструкторе показывает её. Приём ответов работает всегда, независимо от галочки.
3. **Рекомендованная работа аккаунта.** У партнёра одна галочка; значения (пауза, минута, час, сутки, прогрев) задаёт администратор
   в «Настройки площадки» и партнёру не показываются. Партнёр может поставить свои значения только ниже рекомендованных.
4. **Журнал проверок номеров на MAX и здоровья аккаунтов** (таблицы): сейчас результат проверки живёт только в памяти Redis, а
   пауза аккаунта — единственная строка состояния. Журнал даёт историю для отчёта «блокировок на тысячу сообщений».
5. **Лестница «не прочитал»** (1 → 3 → 7 → 30 суток): правило по клиенту, включает администратор, по умолчанию выключено; не для
   кодов подтверждения. Строится после нескольких недель данных отчётов и проверки, что статусы «прочитано» доходят.

## Последствия

- Шаг 1 не меняет схему и контракты существующих путей; добавлен только новый путь чтения.
- Шаги 2–5 каждый получают свою ревизию этого ADR и миграцию перед реализацией.
- Рекомендованные цифры лимитов выдумывать нельзя: они выставляются по данным отчётов с живых аккаунтов.

## Ревизия 2026-10-21: рекомендованная работа аккаунта — шаг 3

- Галочка `messenger_accounts.recommended` (по аккаунту, как «СТОП» и автопрогрев; по умолчанию включена), решает партнёр
  (`PATCH /partner/messenger/accounts/:id { recommended }`). Включена — к лимитам тарифа добавляется **профиль площадки**: пауза между
  сообщениями, лимиты в минуту, час и сутки. Действует **меньшее из тарифа и профиля**, пауза — большее из общей и рекомендованной;
  профиль только сужает и поднять лимит выше тарифа не может. Свой лимит партнёр, как и раньше, ставит в тарифе.
- Профиль задаёт администратор в «Настройки площадки» → «Рекомендованная работа аккаунта» (`messages.recommended_pace_seconds`,
  `_per_minute`, `_per_hour`, `_per_day`; 0 — не ограничивать). **Партнёру значения не показываются** (владелец: «может партнёрам не
  показывать»): кабинет партнёра видит только галочку, а его лимиты в виде аккаунта остаются лимитами тарифа.
- Стартовые значения (20 с, 2 в минуту, 15 в час, 80 в сутки) осторожные и выставлены без живых данных: подниматься они должны по
  отчёту «Отчёты MAX» (доля «нет MAX», непрочитанные, блокировки), а не на глаз.
- Профиль накладывается чистой функцией `withRecommended` в двух местах: при выборе аккаунта (`AccountPicker`) и при отправке
  (`MessagesService.dispatchOne`). Миграция 0067 — одна колонка с умолчанием «да». Включено по умолчанию у **всех**, в том числе у
  прежних аккаунтов: с первого же прохода они работают в этом темпе.

## Ревизия 2026-10-20 (ночь): «СТОП» по клиенту, страница списка — часть 2в

- **Запрет по клиенту** (владелец: «делай как рекомендуешь» на вопрос, что будет, когда другой клиент пишет человеку, нажавшему «СТОП»).
  `message_stops.client_id`: ответ «СТОП» на аккаунт относится к клиенту, чьё сообщение человек получил с этого аккаунта последним
  (не старше трёх суток, `messages` по инстансу и номеру); другие клиенты пишут ему как раньше — в их сообщениях тоже есть строка про
  «СТОП». Клиент не определился (нет сообщения за три дня) — запрет общий (`client_id` пуст): безопаснее остановить всех. Прежние
  записи (v0.1.142) остаются общими.
- «СТОП» боту ставит запрет каждому клиенту, чьим подписчиком человек был в этом боте.
- Страница «Не писать» (администратор и поддержка, `GET /messages/stops`): номер скрыт (`+7 900 ***-**-67`), поиск — по полному
  номеру; «Убрать» (`DELETE /messages/stops/:id`, только администратор, по просьбе самого человека) пишет `message_stop.removed` в журнал
  с скрытым номером. Клиент не видит, кто отписался: для него это отказ `recipient_stopped`.
- Миграция 0066: колонка `client_id`, два частичных уникальных индекса вместо одного; данные не теряются.

## Ревизия 2026-10-20 (вечер): строка про «СТОП» — часть 2б

- Галочка `messenger_accounts.stop_line` (по аккаунту, как автопрогрев; по умолчанию включена), решает партнёр (`PATCH
  /partner/messenger/accounts/:id`). Включена — в конец сообщения через аккаунт добавляется одна и та же строка (`STOP_LINE` в
  `packages/shared`): «Чтобы отписаться, ответьте СТОП». Не влезает в предел мессенджера — уходит без неё.
- `messages.stop_line` — строка была добавлена; клиент видит это в сообщении (`stop_line`). Кабинет клиента показывает строку в
  предпросмотре «через аккаунты» с пометкой «добавляется, если партнёр включил «СТОП» у аккаунта»: какой именно аккаунт отправит,
  клиент не знает (ADR-0014), поэтому показывается как возможное.
- Партнёр видит только свою галочку и подсказку. Миграция 0065 — две колонки с умолчаниями, ничего не теряет.

## Ревизия 2026-10-20: «СТОП» — разбор

- **Входящие включает площадка, не человек.** Сейчас `configureWebhook` явно ставит инстансу `incomingWebhook: no`. Шаг 2 ставит `yes`;
  существующим аккаунтам настройка применяется при ближайшей сверке состояния (`messenger_accounts.incoming_webhook` — сделано или
  нет), один раз на аккаунт, а не при каждой сверке.
- **Что считается «СТОП».** Входящее текстовое сообщение, которое целиком (без регистра и пробелов) равно «стоп», «stop» или
  «отписаться». Формат уведомления провайдера (`incomingMessageReceived`, номер — в `senderData.chatId`, текст — в
  `messageData.textMessageData.textMessage` или `extendedTextMessageData.text`) описан по документации провайдера для WhatsApp и
  **не проверен на живом MAX-аккаунте**: до проверки приём «СТОП» считается нерабочим, а в `docs/api/messaging.md` помечено, как
  проверить (написать «СТОП» на аккаунт и посмотреть, появился ли номер в списке).
- **Общий список «не писать»** — таблица `message_stops` (номер уникален, источник, время). Номер из списка не получает сообщений ни от
  одного клиента и ни по одному пути (аккаунты, бот). «СТОП» боту тоже заносит номер подписчика в список, если номер известен.
  Хранится только номер и время: текст ответа не сохраняется.
- **Запрет.** На приёме сообщение на такой номер отклоняется `409` с `details.reason = recipient_stopped` до списания денег; если
  «СТОП» пришёл уже после приёма — при отправке сообщение возвращается с причиной `recipient_stopped` (новая причина отказа, `CHECK`
  расширяется миграцией). В отчёте причина отдельным столбцом.
- **Снять номер из списка** может администратор (человек передумал); отдельного экрана пока нет — записано в TASKS.md.
- **Часть 2б (следом):** галочка «строка про СТОП» у аккаунта (по образцу автопрогрева, у партнёра), сама строка в итоговом сообщении
  и в предпросмотре клиента.
