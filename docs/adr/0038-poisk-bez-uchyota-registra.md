# ADR-0038: Поиск без учёта регистра — с явной локалью сравнения

- **Статус:** Принято
- **Дата:** 2026-09-07

## Контекст

Обнаружено 2026-09-07 при отборе клиентов по названию. Администратор ищет «такси» —
и не находит «Такси Первое», хотя тот есть.

PostgreSQL приводит регистр по локали базы, и локаль задаётся **при её создании**.
На локальной базе (`datcollate = C`, PostgreSQL 16.10) проверено:

```sql
select lower('ТАКСИ');                                    -- ТАКСИ  (не изменилось)
select 'Такси Первое' ilike '%такси%';                    -- false
select ('Такси Первое' collate "und-x-icu") ilike '%такси%'; -- true
```

Кириллица в локали `C` не приводится **вовсе** — ни `ilike`, ни `lower()`.
С латиницей всё работает, потому что приведение ASCII встроено и от локали не зависит:
поиск по адресам почты исправен, и потому проблема не видна там, где её ищут первым делом.

**Отказ молчаливый.** Запрос не падает — он возвращает пустой список. Администратор
делает вывод, что клиента нет, а клиент есть. Это худший вид ошибки из возможных:
система отвечает уверенно и неверно.

Проект русскоязычный по существу: службы такси, партнёры, операторы связи — всё
называется по-русски. Значит любой поиск по названию в SQL затронут.

## Рассмотренные варианты

1. **Создавать базу с локалью ICU** (`initdb --locale-provider=icu --icu-locale=und`).
   Чинит всё разом, включая порядок сортировки. Но локаль базы **после создания
   не меняется** — только выгрузка и восстановление. И код всё равно не может знать,
   на какой базе окажется: чужая установка, унаследованная база, ошибка при развёртывании.
   Требование к развёртыванию, о котором код молчит, — это требование, которое однажды
   не выполнят.

2. **Приводить регистр в приложении, хранить отдельную колонку для поиска.**
   Работает на любой локали, но добавляет колонку, её заполнение при каждой записи
   и расхождение, когда заполнить забыли.

3. **Указывать локаль сравнения явно в запросе** — `collate "und-x-icu"`.
   Не зависит от того, как создали базу. Стоит одной подстановки в SQL.
   Требует, чтобы PostgreSQL был собран с ICU, — в сборках 16-й версии это так,
   включая ту, что стоит локально (784 доступные локали ICU).

## Решение

Вариант 3, и **единственным местом**: `containsIgnoringCase` в `@zvonix/db`.

Не `ilike` по месту вызова. Причина ровно та же, что и у самой ошибки: забыть локаль
в одном из двадцати мест — значит получить поиск, который молча не находит. Помощник
делает правильное поведение умолчанием, а неправильное — невозможным написать не заметив.

Он же экранирует знаки шаблона: `%`, введённый в поле поиска, без экранирования означает
«что угодно», а `_` — «любой символ». Тот же класс отказа — отбор, который перестал
отбирать, ничего об этом не сказав.

**Локаль `und`, а не `ru`.** «Язык не указан» — правила Unicode по умолчанию, и русскому
их достаточно. Привязка к `ru` добавила бы правила **сортировки**, которые в поиске
по подстроке ничего не меняют, зато привязали бы платформу к одному языку.

**Свойство базы закреплено проверкой** в `packages/db`: она утверждает, что штатный
`ilike` кириллицу не приводит, а с локалью — приводит. Если однажды базу пересоздадут
с ICU и `ilike` заработает сам, проверка упадёт — и об этом узнают, а не будут гадать.

## Последствия

- Положительные: поиск по-русски работает на любой базе, включая уже существующую
  и созданную не нами. Экранирование шаблона нельзя забыть — оно в том же месте.
- Отрицательные: требуется PostgreSQL с ICU. В 16-й версии это штатная сборка,
  но на урезанной сборке запрос откажет — и откажет **громко**, ошибкой о неизвестной
  локали, а не пустым списком. Это правильная сторона отказа.
- Индекс по колонке с другой локалью для такого сравнения **не подойдёт**: поиск
  по подстроке и так идёт полным перебором, но когда дело дойдёт до `pg_trgm`,
  индекс придётся создавать с той же локалью.
- В коде: поиск по части текста пишется через `containsIgnoringCase`. Прямой `ilike`
  в новом коде — повод спросить, почему.
- **Порядок сортировки — та же болезнь и то же лекарство.** `order by name` в локали `C`
  сравнивает по кодам символов и ставит все заглавные перед строчными: «Яндекс»
  оказывается раньше «абв». Дополнено 2026-09-07 помощником `orderByText` из того же
  модуля и с той же локалью; применено там, где сортируется человекочитаемое название —
  клиенты, партнёры, операторы, узлы, машинные ключи. Свойство базы закреплено такой же
  проверкой: штатное сравнение ставит «Яндекс» первым, с локалью — «абв».

**Замер локалей, 2026-09-21.** Локаль базы по умолчанию у разных установок разная, и
«как у базы» ничего не гарантирует: локальная база разработки — `C`, база в CI (образ
`postgres:16`) — `en_US.UTF-8`, база тестового сервера (пакет `postgresql-16` в Ubuntu
24.04) — `C.UTF-8` с провайдером `libc`, то есть сортировка по кодам символов. Первый
прогон CI это и показал: проверки «штатный `ilike` не умеет» упали там, где база умела.
Теперь они задают локаль `C` явно — фиксируют свойство локали, а не машины.
