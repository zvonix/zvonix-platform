# ADR-0098: Отклонённые при приёме — свой журнал, общий список; две причины «не ушло»

- **Статус:** Принято — 2026-10-23; владелец: «может всё же чтобы попадало? и только в таблице сделать настройку, чтобы такие
  сообщения по стандарту не отображались», «чем плохо всё в одной?» (после объяснения — «на всё да»)
- **Дата:** 2026-10-23
- **Связано с:** [ADR-0071](0071-soobscheniya-max.md), [ADR-0096](0096-zhurnal-podklyucheniy-smpp.md),
  [ADR-0097](0097-zanyato-i-srok-soobshcheniya.md)

## Контекст

Сообщение, отклонённое при приёме («все маршруты заняты», «нет MAX», «не хватает денег»…), не оставляет следа в журнале
сообщений: программа получила отказ, а у клиента и сотрудника нет ни номера, ни времени, ни причины — только строка
«занято — 11 раз» в журнале SMPP без номера. Разбирать работу такси по такому нельзя.

Таблица `messages` — не только журнал: на ней очередь отправки, отчёты SMPP, акт и сводки, начисления партнёрам, здоровье
аккаунта (доля «нет MAX»), предел на номер, защита от повторов, «молчащие получатели». У отклонённого при приёме нет ни
денег, ни аккаунта, ни номера сообщения у программы; ограничения схемы (`route = 'account'` ⇒ цена партнёра) для него
неверны. Строка в `messages` потребовала бы исключать её в каждом из этих мест.

## Решения

1. **Своя таблица `message_refusals`**: клиент, канал (`smpp`, `api`, `cabinet`), номер, причина, время. Ни текста, ни денег:
   для разбора они не нужны, а текст — лишние персональные данные. Деньги, очередь и отчёты её не видят **по построению**.
2. **Пишется в `MessagesService.send`** при отказе, когда номер уже разобран. Причина — `details.reason` отказа: `all_busy`,
   `no_capacity` (нет доступных аккаунтов вовсе), `recipient_not_in_max`, `recipient_inactive`, `recipient_stopped`,
   `duplicate_message`, `recipient_limit`, `insufficient_funds`, `requirements_unmet`, `bot_only` (только подписчикам бота);
   иначе `other`. Сбой записи не меняет ответ программе (журнал). Каждая попытка — своя строка: повторы программы — это
   то, что нужно увидеть.
3. **На экране — один список.** Журнал клиента и сотрудника с флажком `refused=1` возвращает принятые и отклонённые
   вперемешку по времени, с общими страницами; отклонённая строка — `kind: "refused"`, `status: "refused"`, причина в
   `failure_reason`. Отбор «Итог: отклонено при приёме» — только они. В кабинете переключатель «Показывать отклонённые при
   приёме» выключен по умолчанию, выбор помнится в браузере. Партнёру не показываются: аккаунт им не назначался. Внешний
   `GET /v1/messages` не меняется.
4. **Срок хранения** — как у текстов сообщений (`retention.messages_days`), той же задачей воркера: номер — персональные данные.
5. **«Не ушло» — две причины.** Истёк срок, а провайдер ни разу не пробовал отправить (попыток 0) — `wait_expired`
   «свободного маршрута не нашлось»; пробовал — новая `provider_timeout` «MAX не ответил вовремя». Отчёт SMPP для обеих —
   `EXPIRED`, код `err` у новой — `006`. Прежние строки не переписываются.
6. **Приём считает паузу так же, как отправка**: `messages.pace_seconds` передаётся в выбор аккаунта при приёме — иначе
   приём обещал «свободен», а отправка ждала паузу (и сообщение могло истечь).

## Последствия

- Миграция: новая таблица с индексом `(client_id, created_at)`, расширение `messages_failure_reason_check`.
- Строка «За 7 суток» в журнале клиента получает «отклонено при приёме N».
- Отклонённые при приёме не входят в «Принято» сводок и акта — там по-прежнему только принятые.
