# ADR-0076: Отчёты SMPP по настройкам клиента

- **Статус:** Принято — 2026-10-07, идея владельца («клиенты сами выбирают, какой статус и при каком событии отдавать:
  отправлено — отправлено, доставлено — ничего, прочитано — доставлено»); детали — по рекомендации проектировщика
- **Дата:** 2026-10-07
- **Связано с:** [ADR-0072](0072-smpp-dlya-soobscheniy.md) (п. 6 «Отчёты о доставке» уточняется), [ADR-0071](0071-soobscheniya-max.md),
  [ADR-0016](0016-soglasheniya-shemy-bd.md), [ADR-0005](0005-migracii.md)

## Контекст

Сейчас клиент по SMPP получает один отчёт, когда сообщение дошло до конца: `DELIVRD` на «доставлено» и на «прочитано»,
`UNDELIV` или `EXPIRED` на отказ. Отчёта «ушло в MAX» нет. Программы служб такси ведут себя по-разному: одним нужен
быстрый ответ «принято», другим — только «доставлено», а «прочитано» (у MAX оно приходит отдельно) нужно отдавать как
«доставлено» или не отдавать. Единого поведения на всех не угадать.

## Решение

1. **У подключения клиента три настройки** — по одной на событие: «ушло в MAX» (`sent`), «доставлено» (`delivered`),
   «прочитано» (`read`). Значение каждой: `none` — отчёта не отдавать; `accepted` — отдать `ACCEPTD` («принято,
   в пути»); `delivered` — отдать `DELIVRD`. Хранятся в `smpp_accounts` текстом с `CHECK` (ADR-0016):
   `receipt_on_sent`, `receipt_on_delivered`, `receipt_on_read`.
2. **По умолчанию — прежнее поведение:** `sent → none`, `delivered → delivered`, `read → delivered`. Существующие
   подключения ничего не замечают.
3. **Отказ отдаётся всегда** (`UNDELIV` — не отправлено; `EXPIRED` — ждало слишком долго) и не настраивается: по нему
   возвращены деньги, и клиент обязан узнать, что сообщение не дошло.
4. **Один и тот же итог по сообщению отдаётся один раз.** Если два события настроены на одно значение (например,
   «доставлено» и «прочитано» → `DELIVRD`), второй отчёт не уходит. События, наступившие в одном проходе опроса
   (сообщение прыгнуло от `sent` к `read`), отдаются по порядку `sent` → `delivered` → `read`.
5. **Что уже отдано, помнит сообщение:** `messages.receipt_events text[]` — какие события обработаны (`sent`,
   `delivered`, `read`, `failed`). Прежний `receipt_sent_at` остаётся как время последнего отданного отчёта.
   Миграция помечает все события обработанными у сообщений, у которых `receipt_sent_at` уже стоит, — повторных
   отчётов после выкладки не будет.
6. **Опрос базы** (ADR-0072, п. 6) выбирает только сообщения, у которых есть неотданное событие, на которое у клиента
   включён отчёт. Сообщения в состоянии `sent` при `sent → none` опрос не загружают.
7. **Быстрые наборы в кабинете** (кнопки, не отдельная сущность): «Как сейчас» (`none / delivered / delivered`),
   «Сразу, как ушло» (`delivered / none / none` — ответ `DELIVRD` в момент отправки), «Только прочитанные»
   (`none / none / delivered`), «Принято, затем доставлено» (`accepted / delivered / delivered`). Набор лишь
   заполняет три выбора; сохраняется то, что стоит в выборах.
8. **Журнал:** смена настроек — в журнале аудита, до и после (как остальные изменения подключения).

## Риски и оговорки

- `ACCEPTD` — стандартное, но не у всех программ обрабатываемое состояние: часть систем считает любое состояние,
  кроме `DELIVRD`, неудачей. Поэтому по умолчанию он выключен, а в кабинете у варианта есть пояснение.
- «Сразу, как ушло → DELIVRD» — осознанное допущение клиента: доставку MAX мы не подтвердили. Если потом приходит отказ
  (получателя нет), клиент получит `UNDELIV` после `DELIVRD`. Это записано в подсказке к набору.

## Не входит

Настройка отчётов по каждой отправке отдельно (по полю `registered_delivery` в `submit_sm`); отчёты по HTTP-вебхукам.
