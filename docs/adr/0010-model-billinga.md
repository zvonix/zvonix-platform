# ADR-0010: Модель биллинга — двойная запись и резервирование

- **Статус:** Предложено — требуется решение
- **Дата:** 2026-09-01

## Контекст

В системе три стороны с деньгами: клиент платит, партнёр зарабатывает, платформа удерживает
комиссию. Каждый звонок порождает движение по всем трём. Требования: расхождения должны быть
обнаружимы, спор с партнёром или клиентом — разрешим по данным, повторная обработка CDR —
безопасна, а клиент не должен уходить в минус на параллельных звонках.

## Рассмотренные варианты

1. **Поле `balance`, обновляемое при списании.**
   Просто и быстро. Но история движений отсутствует или ведётся отдельно и рассинхронизируется;
   ошибка необратима и не диагностируема; в споре нечего показать.
2. **Event sourcing на весь домен.**
   Полная история, но избыточно: восстанавливаемость нужна для денег, а не для всего домена,
   а цена — сложность каждого запроса.
3. **Двойная запись (ledger) для денег плюс резервирование под активный звонок.**
   Стандарт финансовых систем: каждое движение — минимум две проводки, баланс выводится из них.

## Решение (предлагается)

Вариант 3.

**Счета.** У каждого клиента и партнёра — свой счёт. Плюс системные: `revenue` (комиссия),
`payable` (обязательства перед партнёрами), `settlement` (шлюз платежей).

**Проводки.** Любое движение денег — набор проводок с нулевой суммой. Проводка неизменяема:
ошибка исправляется обратной проводкой, а не правкой. Баланс равен сумме проводок по счёту;
для скорости хранится материализованный остаток, который сверяется фоновой задачей.

**Резервирование.** До начала звонка резервируется максимально возможная стоимость
(максимальная длительность на цену плюс стоимость соединения). По завершении резерв
закрывается фактической суммой. Без резервирования клиент с остатком на одну минуту
запускает сто параллельных звонков и уходит в глубокий минус — это типовой сценарий,
а не теоретический.

**Идемпотентность.** Тарификация ключуется идентификатором вызова. Повторная доставка того же
CDR не создаёт вторых проводок: узел может слать CDR повторно, и это нормальный режим работы.

**Деньги.** Целое число микроединиц валюты. Плавающая точка запрещена везде, включая API.
Округление — только в момент фиксации CDR, по правилу из тарифа.

**Фиксация условий.** В CDR записываются применённая цена клиента, цена партнёра, процент
комиссии и правило тарификации на момент звонка. Изменение тарифов не влияет на прошлое.

**Сверка.** Ежедневная задача сверяет сумму проводок с материализованными остатками,
CDR узлов с тарифицированными CDR, закрытые резервы с завершёнными звонками.
Расхождение — инцидент с отчётом, а не тихая коррекция.

## Последствия

- Положительные: спор разрешается выгрузкой проводок; ошибки находит сверка, а не жалоба
  клиента; повторы CDR безопасны; уход в минус невозможен.
- Отрицательные: больше записей и больше кода, чем при простом поле баланса; резервирование
  добавляет шаг в цепочку вызова и требует освобождения зависших резервов.
- В коде: изменение баланса вне модуля `billing` запрещено; денежные значения — только целые
  микроединицы.
