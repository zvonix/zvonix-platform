# ADR-0049: Выкладка площадки — выпуск собирает GitHub Actions, сервер забирает его сам

- **Статус:** Принято — 2026-09-14, решения владельца площадки. В тот же день владелец
  отказался от панели aaPanel — решение ниже записано уже без неё
- **Дата:** 2026-09-14
- **Связано с:** [ADR-0002](0002-konfiguraciya.md) (конфигурация), [ADR-0005](0005-migracii.md)
  (миграции), [ADR-0007](0007-lokalnaya-sreda.md) (среда), [ADR-0017](0017-sborka-paketov-monorepozitoriya.md)
  (сборка пакетов), [ADR-0037](0037-sessiya-v-brauzere.md) (кабинет и API за одним адресом),
  [ADR-0045](0045-ustanovshchik-uzla.md) (установщик узла)

## Контекст

Порядка выкладки площадки в репозитории нет. Тестовый сервер владельца настраивался
вручную скриптами из рабочего каталога сессии: архив собирался на машине разработчика
под Windows и отвозился по SSH. Ни служб, ни настроек прокси, ни скрипта выкладки в проекте
нет, удалённого репозитория не было вовсе.

Замер сервера 2026-09-14: 1 ядро, 961 МБ памяти, подкачка 3 ГБ. На нём уже работают
FreeSWITCH, PostgreSQL, Redis, API и воркер. Сборка TypeScript и Next на такой машине
не помещается, а на любой машине с узлом отнимала бы процессор у голоса.

Рассматривалось управление сервером через веб-панель aaPanel.

## Рассмотренные варианты

**Где собирать выпуск.**

| Вариант | Почему нет или да |
|---|---|
| На сервере, из клона репозитория | Не помещается в память; сборка забирает процессор у FreeSWITCH |
| На машине разработчика, архив по SSH | Так и было: собирается под Windows, а выкладка зависит от одной машины |
| **GitHub Actions на Ubuntu** | **Выбрано:** та же ОС, что на сервере, повторяемо, собранное проходит гейт |

**Как выпуск попадает на сервер.**

| Вариант | Почему нет или да |
|---|---|
| GitHub заходит на сервер по SSH | Root-ключ сервера хранился бы в секретах GitHub |
| **Сервер скачивает выпуск сам** | **Выбрано:** на сервере лежит токен только на чтение одного репозитория. Его утечка даёт чтение кода, а не сервер |

**Чем управлять процессами и сервером.**

| Вариант | Почему нет или да |
|---|---|
| Node-проекты aaPanel (PM2) | Второй диспетчер процессов и настройки в двух местах |
| Службы systemd, aaPanel — только nginx и файрвол | Выбирался владельцем и отменён им же в тот же день. Панель с правами root открыта в интернет на сервере с деньгами, номерами абонентов и публичным SIP; у неё были уязвимости с выполнением команд (CVE-2025-48702) и SQL-инъекцией (CVE-2025-12914); её файрвол по умолчанию закрывает порты голоса; сборку и миграции всё равно выполняют команды |
| **Без панели: службы systemd, nginx и файрвол ставит скрипт подготовки** | **Выбрано** |

## Решение

### 1. Выпуск

Рабочий процесс `.github/workflows/release.yml` запускается меткой `v*` или вручную.
Сначала он прогоняет полную проверку — тот же `ci.yml`, вызванный как повторно используемый
процесс: **выпуск без пройденного гейта не собирается**. Затем собирает (`pnpm build`,
`pnpm web:build`) и кладёт в GitHub Release архив `zvonix-<метка>.tgz` вместе
с контрольной суммой.

В архиве — только то, что нужно для запуска, в раскладке репозитория:

- манифесты: `package.json` корня и пакетов, `pnpm-lock.yaml`, `pnpm-workspace.yaml`;
- `dist` пакетов и приложений `api` и `worker`;
- каталог `node/`: `GET /install.sh` читает установщик и шаблоны оттуда;
- самодостаточная сборка кабинета — `apps/web/.next/standalone` вместе с `.next/static`;
- каталог `deploy/` той же версии: скрипт выкладки, службы, настройки nginx.

Зависимостей API и воркера в архиве нет: их ставит сервер (`pnpm install --prod
--frozen-lockfile` по фильтру). Нативные модули (`@node-rs/argon2`) берутся под его систему,
а архив остаётся небольшим. Кабинет везёт зависимости сам — их отбирает Next при сборке
на той же Ubuntu.

### 2. Выкладка на сервере

`deploy/deploy.sh <метка>`, запускается от root:

1. скачивает архив и контрольную сумму по токену из `/etc/zvonix/github.env`
   и сверяет сумму;
2. распаковывает в новый каталог `/opt/zvonix/releases/<метка>-<время>` и ставит зависимости;
3. применяет миграции;
4. переключает ссылку `/opt/zvonix/current` и перезапускает `zvonix-api`, `zvonix-worker`,
   `zvonix-web`;
5. ждёт `/health/ready` и страницу входа кабинета. Не дождался — возвращает ссылку
   на прежний выпуск и перезапускает службы.

Хранятся пять последних выпусков; `deploy.sh --rollback` возвращает предыдущий.

**Откат не откатывает миграции.** Это безопасно только потому, что миграция совместима
с предыдущим кодом ([ADR-0005](0005-migracii.md), два шага). Разрушающая миграция без
промежуточного шага делает откат невозможным, и ловится это ревью миграции, а не скриптом.

**Окружение выкладкой не переписывается.** `/etc/zvonix/zvonix.env` и
`/etc/zvonix/secrets.env` порождает подготовка сервера (`deploy/server-setup.sh`) один раз.
Иначе правка настройки на сервере исчезала бы со следующим выпуском.

### 3. Процессы

Службы systemd от пользователя `zvonix`, с `NoNewPrivileges` и `ProtectSystem=strict`.
Все слушают только `127.0.0.1`: API — 8000, кабинет — 3000, у воркера порта нет.
Настройки читаются из окружения ([ADR-0002](0002-konfiguraciya.md)).

### 4. Прокси и файрвол

Оба ставит `deploy/server-setup.sh`, без панели управления.

**nginx.** Сайт делит один адрес ([ARCHITECTURE.md](../ARCHITECTURE.md), «Кабинет и API —
один источник»): `/api/` уходит на `127.0.0.1:8000` с отрезанным префиксом, всё остальное —
на `127.0.0.1:3000`. Ответа прокси ждёт не меньше 45 с: кабинет ждёт пробное письмо 40 с
([ADR-0003](0003-obrabotka-oshibok.md), «Ревизия»). Шаблон сайта —
`deploy/nginx/zvonix.conf`; скрипт подставляет адрес и имя. На стенде сайт слушает только
`127.0.0.1:8080`, с доменом — порт 80, сертификат выпускается отдельно. Штатный сайт nginx,
слушающий 80 на всех адресах, скрипт отключает.

**Файрвол** (`ufw`, всё входящее закрыто по умолчанию):

- **открыты:** порт SSH — его скрипт узнаёт у `sshd` и разрешает **первым**, иначе включение
  файрвола отрезало бы доступ к серверу; SIP 5060 по UDP и TCP; голос — диапазон RTP
  из конфигурации FreeSWITCH (по умолчанию 16384–32768) по UDP; 80 и 443 — только когда
  задан домен;
- **закрыто всё остальное**, в том числе 5080 (внешний профиль FreeSWITCH), 8021
  (управление FreeSWITCH), 8000, 3000, 5432 и 6379.

### 5. Стенд и прод

**Тестовый стенд** — одна машина, увеличенная до 2 ядер и 2–4 ГБ: площадка и узел вместе.
Узел ходит к площадке по `http://127.0.0.1:8000`, кабинет открывается через SSH-туннель,
домена нет.

**Прод** — площадка и узлы на разных серверах ([ARCHITECTURE.md](../ARCHITECTURE.md),
«Развёртывание»). Там домен и HTTPS обязательны: установщик узла принимает адрес площадки
только по https ([ADR-0045](0045-ustanovshchik-uzla.md)).

## Последствия

- **Положительные.** Выкладка — одна команда, и она повторяема. Выложенное прошло гейт
  на Ubuntu. Откат — тоже одна команда. Секрет на сервере даёт только чтение кода.
- **Цена.** Выпуск требует GitHub — Actions и Releases. Токен на сервере живёт ограниченный
  срок, и его нужно продлевать. При каждой выкладке сервер ставит зависимости из интернета.
- **Без панели управления.** Сервер настраивается скриптами из репозитория, и то, как он
  устроен, видно в истории изменений, а не в состоянии чужой панели. Смотреть на сервер
  в браузере нечем — и не нужно: выкладка и откат выполняются одной командой.
- **Проверка.** Гейт проверяет скрипты выкладки механически: синтаксис, переводы строк,
  `set -euo pipefail`. Работают ли они, отвечает только выкладка на живом сервере.

## Ревизия 2026-09-22: копия базы перед миграциями

Решение владельца. Пункт 3 выкладки теперь двухшаговый: **сначала копия базы, потом
миграции**. `deploy.sh` снимает `pg_dump --format=custom` от имени `postgres`
в `/var/backups/zvonix/<метка>-<время>.dump` (каталог `0700`, владелец `postgres`: в копии
данные людей) и хранит пять последних — столько же, сколько выпусков. Копия не снялась
или пустая — выкладка останавливается **до** миграций, и работает прежний выпуск.

Зачем. Откат выпуска возвращает код, но не базу (абзац «Откат не откатывает миграции»
выше), а ревью миграции — это человек: разбор `scripts/migration-risk.mjs` находит
кандидатов, но не гарантирует, что пропущенного нет. Данные, испорченные миграцией,
возвращаются только из копии; раньше она была ручным шагом навыка `/release`, и его можно
было пропустить.

Восстановление — только решением владельца и с потерей всего записанного после копии:
`sudo -u postgres pg_restore --clean --if-exists -d zvonix <файл>` при остановленных службах.
Цена — место на диске: пять копий растут вместе с таблицей вызовов, и на проде это
придётся мерить.

Проверено опытом в Git Bash с подменами `sudo`, `pg_dump`, `install`: из семи выкладок
подряд остаются пять новейших копий; отказ `pg_dump` и пустая копия останавливают
выкладку и не оставляют файла. На живом сервере ещё не запускалось.
