# ADR-0059: Сводки и отчёты по деньгам и качеству

- **Статус:** Принято — 2026-09-30, решение владельца («делай что рекомендуешь»)
- **Дата:** 2026-09-30
- **Связано с:** [ADR-0010](0010-model-billinga.md) (проводки), [ADR-0014](0014-vybor-partnera-klientom.md)
  (клиент не видит партнёра), [ADR-0027](0027-porog-otklyucheniya.md) (качество)

## Контекст

Сравнение с A2Billing (и его родней: JeraSoft, MagnusBilling, pyfreebilling) и аудит кода
2026-09-30. Есть: списки вызовов, счета и проводки, счётчик причин отказа, API качества SIM
без экрана. **Нет:** сводок, графиков, выручки и маржи, расходов клиента и заработка партнёра
по периодам, выгрузок, уведомлений о деньгах и качестве, счетов и актов, выплат, сверки.

Порядок важности для площадки терминации (сводный, по обоим источникам):

1. Выручка, закупка и **маржа** по клиенту, партнёру, оператору и дню.
2. **ASR/ACD** с экраном; затем тревоги и автоотключение по порогам.
3. ~~Блокировка вызовов с отрицательной маржой~~ — не нужна: цена клиента = цена партнёра плюс
   наценка, маржа отрицательной быть не может (нужна только при независимой клиентской сетке цен).
4. Уведомления о низком балансе (почта, затем Telegram).
5. Выгрузка вызовов в CSV; вебхуки клиенту.
6. Счета и акты клиентам, выплаты и акты партнёрам, сверка с выпиской партнёра.
7. Антифрод: лимиты трат, всплески трафика, вызовы на свои номера.

## Решение

Первый срез — **сводки с графиками для трёх ролей**, без изменения схемы БД.

- Деньги вызова берутся из проводки `charge:<вызов>`: строка счёта клиента (минус) — выручка
  с клиента, счёта партнёра — доля партнёра, системного счёта `revenue` — маржа платформы.
  Новых таблиц и полей нет: журнал — единственный источник денег.
- Модуль `reports` — **читающая модель**: он только читает `calls`, проводки и справочники
  одним сводным запросом. Это осознанное исключение из правила «модуль не ходит в чужие
  таблицы» (агрегат по трём модулям иначе не собрать без выгрузки всей истории в память);
  пишущих обращений у него нет.
- Периоды — «последние N дней» (1, 7, 30, 90) по часовому поясу браузера (смещение в
  минутах), а не произвольные даты: границы суток должны совпадать с тем, что видит человек.
- Разрезы: администратор — клиент, партнёр, оператор, канал, SIM, шлюз; клиент — оператор
  и канал; партнёр — SIM, шлюз и оператор.
- **Приватность (ADR-0014).** Клиенту — только «потрачено», минуты, вызовы, ASR; партнёр,
  маржа и закупка в его ответ не попадают. Партнёру — только «заработано»; клиент, цена
  клиента и маржа — нет. Маржа и все три суммы — только сотрудникам.
- Графики рисуются SVG без внешней библиотеки (правило 11: зависимость ради двух
  столбчатых диаграмм не берётся).
- ASR = состоявшиеся / все вызовы; ACD = разговор / состоявшиеся.

## Публичный контракт

`GET /reports/overview`, `GET /reports/breakdown` (администратор, поддержка);
`GET /client/reports/overview|breakdown`; `GET /partner/reports/overview|breakdown`.
Параметры: `days` (1/7/30/90), `offset` (минуты от UTC), у разреза — `by`.

## Последствия

- На большом объёме сводка по 90 дням — тяжёлый запрос. Индекс `calls_started_idx` есть;
  если станет медленно — суточные агрегаты фоновой задачей (отдельное решение).
- Вызовы без проводки (отказы, разговор 0 с) считаются в числе вызовов, но не в деньгах.
