# Архитектура Zvonix

## Контекст системы

```
Клиент (такси)                                          Партнёр
  ├─ веб-кабинет ──┐                        ┌── веб-кабинет ─┤
  ├─ API / вебхуки ─┤                        │                │
  └─ софтфон ───────┤                        └── шлюз GOIP ───┤
                    ▼                                          ▼
            ┌───────────────────┐  маршрут/цена   ┌────────────────────┐
            │  CONTROL PLANE    │◄────────────────┤   MEDIA PLANE      │
            │  (центр, 1 шт.)   │  CDR, метрики   │  (узлы АТС, N шт.) │
            └───────────────────┘────────────────►└────────────────────┘
                    │                                          │
                    ▼                                          ▼
              PostgreSQL, Redis                    GSM-сеть через SIM партнёров
                                                   записи → объектное хранилище
```

Разделение на две плоскости — ключевое архитектурное решение
(см. [ADR-0009](adr/0009-programmnaya-ats.md)):

- **Control plane** знает про деньги, тарифы, лимиты и права. Не пропускает через себя медиа.
- **Media plane** пропускает вызовы и пишет разговоры. Не знает про деньги — на каждый вызов
  спрашивает решение у control plane.

Это позволяет добавлять узлы горизонтально, размещать их ближе к партнёрам и терять
не больше одного узла при аварии.

## Компоненты

Модули NestJS живут в `apps/api/src/modules/<имя>` и совпадают по именам с таблицей ниже.

| `http` | Защитники доступа (роль сотрудника **или** кабинет участника по владению карточкой, [ADR-0052](adr/0052-odin-vkhod-dva-kabineta.md)), разбор входа схемами zod, сквозной идентификатор, отображение доменных ошибок в HTTP | `apps/api/src/http` | `identity`, `billing` (чьи карточки) |

Здесь же предел писем на адрес получателя ([ADR-0030](adr/0030-predel-pisem-na-adres.md)) — внутри `enqueue`, чтобы новый путь отправки подчинялся ему, не зная о нём | `apps/api/src/modules/mail` | БД, SMTP |
| `settings` | Настройки площадки: почта и ключи капчи в базе, секреты шифруются ([ADR-0031](adr/0031-nastroyki-ploshchadki.md)). Глобальный модуль — читают и API, и воркер | `apps/api/src/modules/settings` | БД |
| `payments` | Пополнения клиентов и выплаты партнёрам | `apps/api/src/modules/payments` | `billing` |
| `identity` | Учётные записи, роли, права, 2FA, API-ключи; заявки на кабинет как данные (таблица `applications`) | `apps/api/src/modules/identity` | БД |

| `audit` | Неизменяемый журнал действий: запись рядом с действием, у денежных — **той же транзакцией** ([ADR-0034](adr/0034-zhurnal-deneg-odnoy-tranzakciey.md)), и чтение с отбором ([docs/api/audit.md](api/audit.md)). Только чтение: правки и удаления в API нет. Контроллер зарегистрирован отдельным `AuditHttpModule` — `IdentityModule` импортирует `AuditModule`, и обратный импорт замкнул бы круг | `apps/api/src/modules/audit` | БД, `identity` (имена исполнителей) |
| `web` | Админка и кабинеты клиента и партнёра. Next.js (App Router), сессия в cookie ([ADR-0037](adr/0037-sessiya-v-brauzere.md)), общий источник с API за обратным прокси | `apps/web` | `api` |
| `worker` | Расписание фоновых задач ([ADR-0020](adr/0020-fonovye-zadachi.md)): уборка резервов, зависших вызовов, замолчавших узлов, записей по сроку и закрытых окон лимитов; снятие с маршрутизации по порогу отказов ([ADR-0027](adr/0027-porog-otklyucheniya.md)), отправка писем ([ADR-0029](adr/0029-pochta.md)), обновление плана нумерации ([ADR-0032](adr/0032-zagruzka-plana-numeracii.md)), фоновое обновление просроченных записей об операторах. Дальше — сверка CDR, выплаты | `apps/worker` | `billing`, `telephony`, `nodes`, `recordings`, `limits` |
| `esl` | Долгоживущее соединение с узлами, события вызовов в реальном времени | `apps/esl` | `telephony` |
| `agent` | На узле: установка, обновление, метрики, выгрузка записей | `apps/agent` | control plane |

### Кабинет и API — один источник

Браузер обращается по одному адресу, и обратный прокси делит его:

```
https://cp.example.com/api/*  →  API   (apps/api, порт 8000)
https://cp.example.com/*      →  Next  (apps/web, порт 3000)
```

Это не вкус выкладки, а условие работы сессии: cookie с `SameSite=Strict` отправляется
только своему источнику, а CORS платформа не настраивает вовсе
([ADR-0037](adr/0037-sessiya-v-brauzere.md)). Забытая строка в конфигурации прокси
означает неработающий вход, и симптом у неё внятный — кабинет получает от Next `404`
на `/api/auth/me`.

В разработке ту же развязку делает `rewrites` в `apps/web/next.config.ts`,
и адрес API там задаётся переменной `ZVONIX_API_ORIGIN`.

## Потоки данных

### Сценарий: исходящий вызов

1. Клиент инициирует вызов (софтфон / API / приложение) — вызов приходит на **узел АТС**.
2. Узел не решает сам: он запрашивает у `routing` решение по вызову,
   передавая канал, номер назначения и идентификатор вызова.
3. `routing` последовательно (первым делом — чёрный список, см. ниже):
   - **определяет оператора номера через `OperatorResolver`**: своя база
     (`NumberResolution`, срок годности `NUMBER_RESOLUTION_TTL_DAYS`, по умолчанию 30 суток)
     → внешний lookup → план нумерации.

     Своя база отвечает за микросекунды. При промахе или просроченной записи делается
     **одна** попытка внешнего lookup в пределах 800 мс — иначе первый звонок на каждый
     незнакомый номер не проходил бы, а у службы такси новый пассажир это норма.
     Не успели или не ответили — **вызов отклоняется**, номер ставится в очередь
     на разрешение, чтобы следующий звонок прошёл.

     Правило [ADR-0013](adr/0013-opredelenie-operatora.md) при этом не смягчается:
     догадка о неподтверждённом операторе запрещена. Меняется только то, сколько усилий
     прикладывается, прежде чем признать оператора неподтверждённым. Отсюда потолок:
     источник держит два запроса в секунду, то есть не более двух вызовов в секунду
     **на незнакомые номера**; на знакомые ограничения нет;
   - **до определения оператора** проверяет номер по чёрному списку
     ([ADR-0024](adr/0024-chyornyy-spisok-nomerov.md)): тратить бюджет определения
     на номер, звонить на который запрещено, незачем;
   - **проверяет, что оператор разрешён каналом клиента**
     ([ADR-0025](adr/0025-razreshyonnye-operatory-kanala.md)): список закрытый, пустой
     означает «все операторы». Сравнивается определённый оператор, а не префикс номера;
   - **отбирает только шлюзы со свободной SIM того же оператора** — экономика построена
     на бесплатных внутрисетевых звонках, через SIM другого оператора вызов платный
     для партнёра. Нет свободной SIM — вызова нет;
   - если канал требует запись — исключает шлюзы типа `android`, где запись невозможна;
   - **исключает партнёров, не принимающих вызовы в регион номера**
     ([ADR-0022](adr/0022-pokrytie-regionov.md)). Список регионов закрытый, пустой означает
     «все»; неизвестный регион проходит только к партнёру без списка;
   - **проверяет лимиты клиента и канала** во всех окнах и отклоняет вызов, если хоть
     одно исчерпано; лимиты партнёра и SIM отсеивают кандидатов, а не вызов
     ([ADR-0026](adr/0026-limity-po-oknam.md));
   - **упорядочивает оставшихся по приоритетам, которые клиент назначил партнёрам
     в этом канале** ([ADR-0014](adr/0014-vybor-partnera-klientom.md)), а не по цене:
     цена определяет, сколько клиент заплатит, но не то, к кому вызов пойдёт первым.
     Равные приоритеты чередуются по давности последнего маршрута
     ([ADR-0021](adr/0021-ravnomernoe-raspredelenie.md)). Список приоритетов закрытый:
     партнёра, которого в нём нет, канал не использует; пустой список означает «все».
     Отсюда же исключаются шлюзы с низким ASR и заблокированные SIM;
   - просит `billing` **зарезервировать** максимальную стоимость вызова;
   - возвращает узлу упорядоченный список кандидатов.
4. Узел пробует кандидатов по очереди до ответа.
5. По завершении узел отправляет CDR. `billing` идемпотентно тарифицирует его,
   списывает фактическую сумму, закрывает резерв, начисляет партнёру и комиссию платформе.
6. Запись выгружается узлом в объектное хранилище, `recordings` привязывает её к CDR.
7. Счётчики лимитов и метрики шлюза/SIM обновляются.
8. Партнёр может отметить вызов как ушедший не в его сеть — это отменяет запись
   в `NumberResolution` и запускает повторное разрешение номера. Экономику партнёра
   платформа не измеряет: он сам знает свой тариф и сам выбирает операторов и регионы.

**Критично:** решение принимается на каждый вызов, а не статичным конфигом узла — иначе
изменение тарифа, лимита или баланса не вступит в силу.

Обратная сторона: недоступность control plane останавливает звонки, и это **принятая цена**
(решено 2026-09-01). Маршрут из кэша шёл бы по устаревшему сопоставлению оператора
и устаревшему остатку, а звонить разрешено только по операторам, которых партнёр объявил
своими. Несостоявшийся звонок стоит одной поездки; состоявшийся неправильно — реальных денег
партнёра, которых мы ему не возмещаем. Вкладываться нужно в доступность control plane,
а не в режим, который по построению решает на данных, признанных ненадёжными.
Узел при недоступности отвечает `503`, то есть ведёт себя как перегруженный, а не сломанный.

### Сценарий: подключение узла

1. Админ создаёт узел в панели → система выпускает одноразовый токен и **генерирует
   команду установки** вида `curl -fsSL <url>/install.sh | sudo bash -s -- <token>`.
2. Скрипт ставит АТС и агента, регистрирует узел по токену, получает конфигурацию.
3. Агент шлёт heartbeat и метрики: загрузка, число активных вызовов, состояние шлюзов.
4. Партнёр направляет свой GOIP на выданный узлу адрес — шлюз регистрируется по SIP.

### Сценарий: фоновая уборка

Часть инвариантов домена держится не на запросе, а на времени: их некому нарушить и некому
восстановить, пока никто не пришёл. Этим занят отдельный процесс `apps/worker`
([ADR-0020](adr/0020-fonovye-zadachi.md)).

| Проход | Что чинит | Период |
|---|---|---|
| `reservations.release-expired` | Потерянный CDR замораживает деньги клиента навсегда: он перестаёт звонить, причина не видна | 60 с |
| `calls.close-without-cdr` | Вызов узла, умершего посреди разговора, вечно занимает место на SIM — она больше не примет звонков | 60 с |
| `nodes.retire-silent` | Замолчавший узел остаётся в маршрутизации и получает вызовы, которые некому обслужить | 15 с |
| `recordings.remove-expired` | Разговоры пассажиров хранятся дольше объявленного срока | 5 мин |
| `sessions.purge-expired` | Просроченные сессии хранят адрес и клиента — данные о человеке — без причины | 1 ч |

**Каждый проход идемпотентен и догоняющ:** отбирает работу по сроку, а не «с прошлого
запуска». Пропущенный тик ничего не теряет, два экземпляра воркера не мешают друг другу,
а недоступность Redis откладывает уборку, но не отменяет её.

**Уборка продублирована на путях чтения намеренно.** `GET /clients/:id/funds` освобождает
просроченные резервы, `GET /nodes` снимает замолчавшие узлы, маршрутизация перед отказом
закрывает вызовы без CDR. Это не остаток от прежней реализации: так ответ остаётся верным,
даже когда воркер стоит. Обратное — читать заведомо устаревшее число и надеяться на фоновый
процесс — означало бы, что остановка воркера тихо портит показания API.

## Границы модулей

- **`billing` — единственный, кто пишет проводки.** Никакой другой модуль не меняет балансы.
- **Домен не знает о транспорте**: модули не оперируют HTTP-кодами, только доменными
  ошибками ([ADR-0003](adr/0003-obrabotka-oshibok.md)).
- **Media plane не содержит бизнес-логики**: ни цен, ни лимитов, ни прав. Только исполнение
  решения control plane.
- **Модули не лезут в чужие таблицы** — только через публичный интерфейс модуля.
- **Записи не хранятся на узлах** дольше времени выгрузки: узел одноразов и заменяем.

## Хранилища данных

| Что | Где | Почему |
|-----|-----|--------|
| Домен, деньги, CDR | PostgreSQL | Транзакции и ограничения целостности обязательны для денег |
| Счётчики доменных квот | PostgreSQL | Инкремент идёт **той же транзакцией**, что создаёт вызов ([ADR-0026](adr/0026-limity-po-oknam.md)). Потеря счётчика здесь — не сброс кэша, а молча снятая защита SIM партнёра |
| Счётчики частоты входа | Redis | Короткое окно, высокая частота, потеря допустима: вторая линия обороны (блокировка учётной записи) живёт в PostgreSQL |
| Расписание и очередь фоновых задач | Redis (BullMQ) | Расписание обязано пережить перезапуск, а задание — достаться ровно одному экземпляру ([ADR-0020](adr/0020-fonovye-zadachi.md)). Состояния домена здесь нет: источник истины — PostgreSQL |
| Записи разговоров | S3-совместимое хранилище | Объём растёт линейно и бесконечно; в БД им не место |
| Метрики узлов | Временной ряд (отдельное решение) | Другая нагрузка и другой срок хранения |

## Сквозные механизмы

- Конфигурация — [ADR-0002](adr/0002-konfiguraciya.md)
- Ошибки — [ADR-0003](adr/0003-obrabotka-oshibok.md)
- Логи и correlation-id — [ADR-0004](adr/0004-logirovanie.md). Идентификатор вызова

- Миграции — [ADR-0005](adr/0005-migracii.md)

- Аудит: любое действие админа над деньгами, тарифами и лимитами журналируется до/после.

## Развёртывание

- Control plane — один сервер (в перспективе несколько экземпляров за балансировщиком).
- Узлы АТС — N серверов, устанавливаются одной командой, взаимозаменяемы.
- Выкладка площадки — [ADR-0049](adr/0049-vykladka-ploshchadki.md), порядок действий —
  [deploy/README.md](../deploy/README.md): выпуск собирает GitHub Actions после гейта,
  сервер скачивает его сам и переключается; откат — одной командой.
- Разработка — WSL2 Ubuntu 24.04 ([ADR-0007](adr/0007-lokalnaya-sreda.md)).

## Открытые вопросы

- **Одновременность на SIM:** по умолчанию один вызов; как это отражается в понятии
  «свободная SIM» при разрешённом администратором значении больше единицы.
- Мультивалютность и работа в нескольких юрисдикциях.

Закрыто: **режим деградации узла** — звонки запрещаются, см. «Сценарий: исходящий вызов».
