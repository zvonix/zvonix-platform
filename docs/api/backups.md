# Контракт: резервные копии

Список копий, создание, проверка и скачивание из кабинета. Основание — [ADR-0086](../adr/0086-rezervnye-kopii-v-kabinete.md).
Все пути — только роль `admin`. API копий не читает и ничего не запускает: создание, проверка и выдача — заявки службе
обновления (как у [обновления](updates.md)); исход заявки виден в `GET /updates/:id/log`.

## `GET /backups`

```json
{
  "available": true,
  "generated_at": "2026-10-19T04:00:00+00:00",
  "items": [
    {
      "id": "daily/daily-20261019-030000.dump",
      "kind": "daily",
      "name": "daily-20261019-030000.dump",
      "size": 123456,
      "created_at": "2026-10-19T03:00:00+00:00",
      "check": { "at": "2026-10-19T03:05:00+00:00", "ok": true, "detail": "таблиц 14, пользователей 3" }
    }
  ],
  "last_export": { "at": "2026-10-18T09:00:00+00:00", "by": "admin@example.test", "id": "daily/…" }
}
```

`kind`: `daily` (ежедневная), `manual` (кнопка), `update` (перед обновлением), `before-restore` (перед восстановлением).
`check` — итог последней проверки или `null`. `available: false` — служба ещё не писала список (разработка, сервер до первой
выкладки с этой возможностью).

## `POST /backups/create` → `202 { request }`

Заявка `backup-create`: ручная копия, хранится десять последних. `409` — служба обновления не настроена или занята.

## `POST /backups/verify` `{ id }` → `202 { request }`

Заявка `backup-verify`: копия разворачивается во **временную** базу, считаются таблицы и строки основных таблиц, база удаляется;
рабочие данные не затрагиваются. `404` — такой копии нет в списке.

## `POST /backups/export` `{ id, password, code? }` → `202 { request }`

Заявка `backup-export`: служба кладёт копию в `exports/`. **Подтверждение:** пароль администратора и, если подключён второй
фактор, шестизначный код (иначе `400`; неверный пароль — `401`; неверный код — `400`). Пять неудач за 15 минут — `429`.
Пароль в заявку службе не попадает.

## `GET /backups/exports/:runId`

Файл копии (`application/octet-stream`, формат `pg_restore`) — один раз и только тому, кто заказал выдачу; после потока файл
удаляется, невзятый служба убирает через 30 минут. Иначе `404`. Запись журнала: `backup.downloaded`.

## `POST /backups/restore` `{ id, password, code?, phrase }` → `202 { request }`

Заявка `backup-restore`. Обязательны: пароль, код второго фактора (если подключён) и слово `"ВОССТАНОВИТЬ"` (иное — `400`,
пароль при этом не проверяется и попытка не тратится). Пять неудачных подтверждений за 15 минут — `429`. `404` — копии нет в списке.

Что делает служба (журнал — `GET /updates/:id/log`, строки `1/7 … 7/7`):
1. Копия проверяется (если проверка старше суток или не годна — восстановление не начинается).
2. Снимается страховочная копия рабочей базы (вид `before-restore`); не снялась — восстановление не начинается.
3. Копия разворачивается в **новую** базу `zvonix_restore`; 4. на ней выполняются миграции текущего выпуска.
5. Службы останавливаются (кабинет, воркер, API — **площадка недоступна**, кабинет увидит обрыв и попросит войти заново).
6. Рабочая база **переименовывается** в `zvonix_replaced_<время>`, новая становится рабочей. 7. Службы запускаются.

До пункта 5 любой сбой оставляет рабочую базу нетронутой; после пункта 6 неподнявшиеся службы возвращают прежнюю базу под рабочее
имя (неудачная сохраняется как `zvonix_failed_<время>`). Хранится только последняя замещённая база. Выкладка и восстановление
берут один замок (`/run/zvonix-deploy.lock`) и друг другу не мешают.
