# Контракт: клиенты, партнёры и деньги

Решение и его обоснование — [ADR-0010](../adr/0010-model-billinga.md).
Общий вид ошибок и заголовок `X-Correlation-Id` — как в [auth.md](auth.md).

## Как устроены деньги

**Баланс — это следствие проводок, а не самостоятельное значение.** Материализованный
остаток на счёте существует ради скорости; источник истины — журнал. Прямой правки
остатка нет нигде в коде: журнал, мимо которого прошло хоть одно движение, перестаёт
быть доказательством ровно тогда, когда нужен больше всего.

Каждое движение — **операция** из нескольких **проводок**, сумма которых равна нулю.
Деньги не возникают и не исчезают: у прихода на счёт клиента есть вторая сторона.

Кроме счетов клиентов и партнёров есть три системных, иначе второй стороны не найдётся:
`revenue` (комиссия платформы), `payable` (обязательства перед партнёрами),
`settlement` (шлюз платежей).

### Суммы — строки, а не числа

Суммы принимаются и отдаются **строкой** в основных единицах: `"1500.5"`, `"0.000001"`.

JSON-число здесь недопустимо: `0.1 + 0.2` в двоичной плавающей точке не равно `0.3`,
и копейки теряются молча — обнаруживается это на сверке через месяц, когда уже непонятно,
где именно. Внутри хранится целое число микроединиц (1 рубль = 1 000 000).

Представление **минимальное и обратимое**: `1500.5`, а не `1500.50`; `100`, а не `100.00`.
Принудительные два знака потеряли бы посекундные тарифы, которые задаются
в микроединицах. Разбор принимает обе записи — это одно и то же число.

Больше шести знаков после точки отвергается: за пределом микроединицы значение
пришлось бы округлять, а округление в этом проекте выполняется ровно один раз —
при фиксации CDR, по правилу из тарифа.

### Идемпотентность

У каждой операции есть ключ, который задаёт вызывающая сторона: `deposit:<номер платежа>`,
`charge:<идентификатор вызова>`. Повтор с тем же ключом не создаёт вторых проводок
и возвращает `already_posted: true` с прежним `transaction_id`.

Это не защита от небрежности, а штатный режим: узел АТС может прислать один и тот же CDR
повторно. Уникальность обеспечивает база, а не проверка в коде — иначе два одновременных
запроса оба прошли бы проверку и оба списали деньги.

**Сверяется только ключ, не содержимое.** Повтор с тем же ключом и другой суммой вернёт
`already_posted: true` и **прежнюю** операцию: новая сумма не проведётся. Для повторно
доставленного CDR это верно — содержимое там то же. Для формы это значит, что ключ обязан
опознавать конкретное намерение: правка суммы или основания — уже другое намерение,
и ключ там берётся новый. Так и сделано в админке.

## `POST /clients` — роль `admin`

```json
{ "ownerUserId": "…", "name": "Такси «Ромашка»", "overdraftLimit": "1000" }
```

`201` → `{ "client": { "id", "name", "status", "overdraft_limit", "balance", "created_at" } }`

`overdraftLimit` — насколько глубоко клиенту разрешено уходить в минус. По умолчанию
нисколько. Величина **положительная**: хранить предел со знаком минус — верный способ
однажды перепутать направление и раздать бесконечный кредит.

Счёт клиента заводится сразу: клиент без счёта — участник, которому некуда начислить.

**Один владелец — один клиент**: вторая попытка на ту же учётную запись — `409 conflict`.
Схема этого не требует, а код требует — клиент по владельцу ищется одной строкой,
и второй оказался бы для него самого недоступен: он не увидел бы ни своих каналов,
ни своих записей разговоров.

## `PATCH /clients/:id/overdraft` — роль `admin`

```json
{ "overdraftLimit": "2500.50" }
```

`200` → `{ "client": { "id", "overdraft_limit" } }`

До появления этого обработчика предел задавался **только при заведении** и потом
не менялся ничем: опечатка в разрядах означала кредит, который нечем отозвать.

Уменьшение ниже текущего долга **разрешено** и намеренно: это способ сказать «больше
в долг не даём». Уже потраченное никуда не девается, а новые вызовы перестают проходить
по резерву.

Действие денежное — попадает в журнал (`client.overdraft_changed`) вместе с прежним
значением. Повтор того же значения изменением не считается: ответ `200`, записи нет.

## `PATCH /clients/:id/status` — роль `admin`

```json
{ "status": "active" }
```

`200` → `{ "client": { "id", "status" } }`

Единственный путь к `active`, а без него клиент бесполезен: маршрутизация требует
`active` **и от канала, и от самого клиента** (`findRoutableChannel`, `findActiveChannel`).

```
pending ⇄ active ⇄ suspended
    └───────┴─────────┴──→ closed   (окончательно)
```

| Состояние | Что означает |
|---|---|
| `pending` | Заведён, не допущен. Ни один канал не звонит |
| `active` | Каналы в состоянии `active` звонят, деньги списываются по тарифу |
| `suspended` | Звонки прекращаются сразу. Деньги, каналы и история сохраняются |
| `closed` | Звонки прекращаются. **Обратного пути нет**: `409 conflict` на любую попытку |

Смена состояния попадает в журнал (`client.status_changed`) вместе с тем, что было до.
Повтор того же состояния изменением не считается: ответ `200`, записи в журнале нет.

Неизвестный клиент — `404`, негодное состояние — `400`.

## `POST /clients/:id/deposit` — роль `admin`

```json
{ "amount": "1500.50", "idempotencyKey": "deposit:2026-09-01:0001", "description": "Оплата по счёту 17" }
```

`200` → `{ "transaction_id", "already_posted", "balance" }`

Ручное пополнение — такая же проводка, как платёж через эквайринг. Способ поступления
денег на модель не влияет; при ручных пополнениях журнал даже важнее, потому что человек
ошибается и забывает, а строка «кто, кому, сколько, когда» останется.

Сумма должна быть больше нуля. Отказ, если клиента нет.

## `GET /clients` — роли `admin`, `support`

`200` → `{ "clients": [ … ], "total": 42 }`

```json
{ "id": "…", "name": "Такси «Ромашка»", "status": "active",
  "overdraft_limit": "1000", "balance": "1500.5",
  "created_at": "2026-09-07T10:46:34.952Z" }
```

Остаток приходит **тем же запросом**, что и список: раньше он спрашивался отдельно
на каждого клиента, и на тысяче клиентов это была тысяча запросов.

Параметры отбора (все необязательные, **пустое значение означает «любое»**):

| Параметр | Значение |
|---|---|
| `status` | Одно из состояний клиента. Неизвестное — `400` |
| `name` | Часть названия, **регистр не важен** ([ADR-0038](../adr/0038-poisk-bez-uchyota-registra.md)). Знаки шаблона `%` и `_` экранируются |
| `limit` | Размер страницы, по умолчанию 100, потолок 200 |
| `offset` | Смещение страницы |

Клиент, у которого ещё нет счёта, попадает в список с нулевым остатком, а не пропадает
из него: соединение со счётом внешнее.

## `GET /clients/:id/entries?limit=100&offset=0` — роли `admin`, `support`

```json
{
  "balance": "1500.5",
  "total": 17,
  "entries": [
    { "seq": "42", "transaction_id": "…", "amount": "1500.5",
      "kind": "deposit", "description": "Платёжное поручение № 7 от 07.09.2026",
      "reference_type": "client", "reference_id": "…",
      "created_at": "2026-09-07T10:47:24.000Z" }
  ]
}
```

Каждая проводка идёт вместе с тем, **что произошло**: `kind` и `description` из операции,
частью которой она была. Столбец сумм без этого не отвечает ни на один вопрос разбора,
а разбор здесь — основной сценарий.

`reference_type` с `reference_id` указывают на породившее событие — вызов, платёж.
У ручных операций там сам клиент.

`seq` — монотонный номер для человекочитаемой сверки: UUID упорядочен по времени,
но в разговоре с бухгалтерией на него не сошлёшься. Свежее сверху.
`limit` ограничен сверху двумя сотнями: строка несёт описание, и это таблица для
человека, а не выгрузка.

## `GET /clients/:id/funds` — роли `admin`, `support`

`200` → `{ "balance", "overdraft_limit", "held", "available" }`

Остаток — не ответ на вопрос «сколько клиент может потратить»: часть средств придержана
под идущие вызовы. Подробности о резервах — в [routing.md](routing.md).

## `POST /partners` — роль `admin`

```json
{ "ownerUserId": "…", "name": "Иванов Иван Иванович", "displayName": "Партнёр 17" }
```

`201` → `{ "partner": { "id", "display_name", "status" } }`

**Настоящее имя в ответе не возвращается** даже администратору — так его нельзя случайно
показать в общем интерфейсе. Клиент видит партнёра только под псевдонимом: имя, контакты,
реквизиты, номера SIM и адреса шлюзов в клиентский контур не попадают ни в API,
ни в отчётах, ни в CDR ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)).

Псевдоним не должен намекать на личность и уникален: один партнёр — один псевдоним,
иначе один поставщик превратился бы в нескольких разных в глазах клиента,
и распределение трафика поехало бы.

**Один владелец — один партнёр**: вторая попытка на ту же учётную запись — `409 conflict`.
Схема этого не требует, а код требует — партнёр по владельцу ищется одной строкой,
и второй оказался бы для него самого недоступен.

Учётная запись владельца должна существовать заранее: пароль человек задаёт себе сам
при регистрации (`POST /auth/register`, роль `partner`), администратор затем допускает
запись через `PATCH /users/:id/status`. Заводить учётную запись за человека платформа
не умеет — см. [auth.md](auth.md).


## `GET /partners?status=&name=&limit=50&offset=0` — роли `admin`, `support`

`200` → `{ "partners": [ … ], "total": 12 }`

```json
{
  "id": "…",
  "name": "Иванов Иван Иванович",
  "display_name": "Партнёр 17",
  "status": "verified",
  "listens_to_recordings": false,
  "balance": "1840.5",
  "created_at": "2026-09-07T09:12:00.000Z"
}
```

**Настоящее имя здесь есть**, и это не спор с [ADR-0014](../adr/0014-vybor-partnera-klientom.md):
запрет закрывает *клиентский* контур. Клиентский путь один —
`GET /partner-aliases` ([routing.md](routing.md)), и там имени нет.

`name` ищет **и по имени, и по псевдониму**, без учёта регистра
([ADR-0038](../adr/0038-poisk-bez-uchyota-registra.md)): администратор помнит либо одно,
либо другое, и требовать угадать — способ ничего не найти. Знаки `%` и `_` во вводе
экранируются и ищутся буквально.

`display_name` может быть `null`: псевдоним заводится вместе с партнёром, но список
обязан показать и неполную запись — такого партнёра нужно увидеть и починить,
а не спрятать. То же и со счётом: партнёр без счёта показывается с нулём.

`balance` — долг площадки перед партнёром: доля за вызовы начислена, выплата не сделана.

## `PATCH /partners/:id/status` — роль `admin`

```json
{ "status": "verified" }
```

`200` → `{ "partner": { "id", "status" } }`

Единственный путь к `verified`, а без него партнёр бесполезен: и регистрация шлюза
(`sipUsername` → `directory`), и отбор SIM под вызов требуют именно этого состояния.

```
pending ⇄ verified ⇄ suspended
    └────────┴─────────┴──→ closed   (окончательно)
```

| Состояние | Что означает |
|---|---|
| `pending` | Заведён, не проверен. Трафик не идёт: шлюз не зарегистрируется, SIM в отбор не попадут |
| `verified` | Шлюз регистрируется, SIM участвуют в отборе, псевдоним виден клиенту в `GET /partner-aliases` |
| `suspended` | Трафик прекращается сразу. Данные и оборудование сохраняются, вернуть можно |
| `closed` | Трафик прекращается. **Обратного пути нет**: `409 conflict` на любую попытку |

Смена состояния попадает в журнал действий (`partner.status_changed`) вместе с тем,
что было до. Повтор того же состояния изменением не считается: ответ `200`, записи
в журнале нет.

Неизвестный партнёр — `404`, негодное состояние — `400`.

## `PUT /partners/:id/alias` — роль `admin`

```json
{ "displayName": "Партнёр 21" }
```

`200` → `{ "partner": { "id", "display_name" } }`

Псевдоним — **единственное, что клиент вообще знает о партнёре**
([ADR-0014](../adr/0014-vybor-partnera-klientom.md)), и до появления обработчика он
задавался только при заведении: опечатка оставалась навсегда и на глазах у всех клиентов.

Псевдоним уникален на всю площадку: занятое имя — `409` с названной причиной
(«Такой псевдоним уже занят другим партнёром»), а не общее «такая запись уже существует».
Иначе один поставщик выглядел бы у клиента несколькими разными, и распределение трафика
поехало бы.

То же имя изменением не считается: ответ `200`, записи в журнале нет. Переименование
попадает в журнал (`partner.alias_renamed`) вместе с прежним именем.

Клиенты видят новое имя сразу — `GET /partner-aliases` читает ту же строку.

## `GET /partners/:id/entries?limit=100&offset=0` — роли `admin`, `support`

`200` → `{ "entries": [ … ], "balance": "1840.5", "total": 24 }`

Тот же вид проводки, что и у клиента (см. `GET /clients/:id/entries`), только с другой
стороны: партнёру начисляют долю за вызов и списывают при выплате.

Неизвестный партнёр — `404`, а не пустая лента: счёт заводится по требованию,
и без этой проверки запрос по выдуманному идентификатору отвечал бы «движения нет»
вместо «такого партнёра нет».
## `GET /billing/reconcile` — роль `admin`

`200` → `{ "balanced": true, "discrepancies": [] }`

Сверяет материализованный остаток каждого счёта с суммой его проводок.
Пустой список — норма. Непустой означает, что какое-то движение прошло мимо журнала:
это инцидент с разбором, а не повод подогнать остаток.
