# Контракт: машинные ключи

Выпуск и отзыв учётных данных для узлов АТС и клиентских интеграций.
Обоснование — [ADR-0019](../adr/0019-dostup-mashin.md). Общий вид ошибок
и заголовок `X-Correlation-Id` — как в [auth.md](auth.md).

## Как устроен ключ

У ключа две части. **Идентификатор** `zvx_node_a1b2c3d4e5f6` публичен: он ищется
по индексу, печатается в логах и называется в поддержке. **Секрет** — 32 случайных байта;
в базе лежит только его SHA-256.

**Секрет отдаётся один раз, при выпуске.** Восстановить его неоткуда: потерян — выпускается
новый, старый отзывается. У одного узла допускается больше одного действующего ключа
именно ради этого: завести новый → раскатать конфигурацию → отозвать старый. Обратный
порядок оставляет окно, в котором звонки не маршрутизируются.

Предъявляется в двух видах, это один и тот же ключ:

- `Authorization: Basic base64(идентификатор:секрет)` — **единственное, что умеет
  FreeSWITCH**: `mod_xml_curl` и `mod_json_cdr` задают только `user:pass`;
- `Authorization: Bearer идентификатор.секрет` — для нашего агента, который заголовок
  задать умеет.

## Что не хешируется медленно и почему

Секрет хранится как SHA-256, а не argon2. Проверка выполняется **на каждый звонок**,
а argon2id с 19 МиБ памяти — это 19 МиБ и десятки миллисекунд на каждый запрос маршрута.
Перебирать 256 бит случайности всё равно нечего.

## Список разрешённых адресов

Пустой список означает «откуда угодно». У ключей узлов его положено заполнять: адрес узла
известен, потому что узел заводит администратор. Это **единственная мера, работающая
и против кражи ключа с самого узла** — украденный ключ вне узла бесполезен.

Только точное совпадение адреса; подсети не поддерживаются сознательно. IPv4, пришедший
по IPv6-сокету (`::ffff:203.0.113.7`), приводится к привычному виду — иначе список,
заполненный человеком, не совпал бы никогда, а это отказ телефонии, а не отказ
злоумышленнику.

## `POST /machine-keys/nodes` — роль `admin`

```json
{ "nodeId": "…", "label": "Узел Москва-1, ключ от 2026-09-01", "allowedIps": ["203.0.113.7"] }
```

`201` → `{ "key": { "credential_id", "key_id", "secret", "expires_at" } }`

`expires_at` у ключа узла — `null`. Срока нет намеренно: истёкший ключ узла означает отказ
телефонии, а это худший отказ, чем неотозванный ключ у машины, чей адрес в списке. Взамен
возраст ключа виден в списке.

## `POST /machine-keys/clients` — роль `admin`

То же для клиентской интеграции; владелец — клиент, срок — год.

## Токен установки

Отдельного обработчика для него нет: он выпускается **вместе с узлом**, в
[nodes.md](nodes.md) (`POST /nodes` и `POST /nodes/:id/install-command`). Токен бессмыслен
без узла, для которого предназначен, а второй способ его получить означал бы второй
способ ошибиться.

Живёт **час** и применяется **ровно один раз**, потому что попадает в команду
`curl … | sudo bash -s -- <токен>`, а та — в историю оболочки, в переписку и в буфер обмена.
Рабочим ключом не является: обработчики машинного контура его не принимают.

## `GET /machine-keys?kind=node` — роль `admin`

`200` → `{ "keys": [ { "credential_id", "key_id", "kind", "owner_id", "label",
"allowed_ips", "expires_at", "last_used_at", "revoked_at", "created_at", "age_days" } ] }`

Секрета здесь нет и быть не может. `age_days` показывается потому, что у ключей узлов
срока нет: «этому ключу 400 дней» должно быть видно заранее, а не наступать внезапно.

`kind` — `node` (по умолчанию), `client_api` или `enrollment`. Неизвестное значение —
отказ, а не «показать всё».

## `DELETE /machine-keys/:id` — роль `admin`

`204`. Отзыв действует **немедленно**: ключ проверяется по базе на каждом запросе,
ради этого свойства схема и выбрана.

Отзыв — пометка, а не удаление строки: иначе в журнале дыра ровно там, где чаще всего
и нужно разбираться. Повторный отзыв не ошибка и не меняет момента первого — важен он.
