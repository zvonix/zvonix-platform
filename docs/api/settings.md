# Контракт: настройки площадки и защита форм

Обоснование — [ADR-0031](../adr/0031-nastroyki-ploshchadki.md).

## Что здесь живёт, а что в окружении

В базе — **закрытый список** значений, которые владелец меняет без доступа к серверу:
почта и ключи Яндекс SmartCaptcha. Всё, без чего процесс не стартует — адреса базы
и Redis, порт, `SECRET_KEY`, `PUBLIC_BASE_URL`, `TRUSTED_PROXIES`, — остаётся
в переменных окружения ([ADR-0002](../adr/0002-konfiguraciya.md)).

Граница проведена не по вкусу: ключ, которым расшифровывается пароль почты, не может
лежать зашифрованным в той же таблице.

**Значений по умолчанию из окружения нет.** У одного значения не должно быть двух
источников, иначе вопрос «почему переменная не действует» становится штатным.
Свежая установка настроек не имеет: почта не настроена (письма копятся —
[ADR-0029](../adr/0029-pochta.md)), капча выключена.

Секреты хранятся **шифротекстом**: AES-256-GCM ключом, выведенным из `SECRET_KEY`
с собственным назначением. Дамп базы не отдаёт ни пароль почты, ни серверный ключ капчи.
Назначение у настроек своё, не общее со вторым фактором
([ADR-0028](../adr/0028-vtoroy-faktor.md)): утечка одного шифротекста не должна помогать
разбирать другой.

**Потеря `SECRET_KEY` означает потерю секретных настроек** — их придётся задать заново.
Прочитать их станет нельзя, и об этом будет запись в журнале уровнем `error`.

## `GET /settings` — роль `admin`

`200` → `{ "settings": [ { "key", "kind", "hint", "secret", "value", "is_set", "updated_at" } ] }`.

Отдаётся **весь список**, включая настройки на умолчаниях: иначе админка не знает,
что вообще можно настроить.

У секретных настроек `value: null` **всегда**. Задано значение или нет, видно по `is_set`.
Прочитать секрет обратно через API нельзя ни администратору, ни кому-либо ещё.

## `PUT /settings` — роль `admin`

```json
{ "settings": { "mail.host": "smtp.example.com", "mail.port": 587, "mail.password": "…" } }
```

`200` → тот же список, что и у `GET`.

Меняются **только названные** ключи, остальные не трогаются. Неизвестный ключ — `404`:
список закрыт, и опечатка в имени не должна тихо создавать настройку, которую никто
не читает. Значение не того вида — `400`.

Изменение пишется в журнал действий **той же транзакцией**, что и сама запись
([ADR-0034](../adr/0034-zhurnal-deneg-odnoy-tranzakciey.md)): вопрос «кто выключил капчу»
разбирается так же, как вопрос о списании.

В журнале **и прежнее значение, и новое**: без прежнего видно, на что переключили,
но не видно, было ли это изменением. Прежние значения читаются той же транзакцией —
иначе между чтением и записью успевает вклиниться чужое изменение, и в журнале
окажется состояние не того, кто его менял.

Значения секретов в журнал не попадают — там остаётся `<скрыто>`. Но **пустое значение
секретом не является** и записывается как есть: иначе очистка пароля почты выглядит
в журнале как `<скрыто>` → `<скрыто>`, то есть ни о чём.

Незаданная настройка записывается как `null`, а не как пустая строка: первая действует
умолчанием, вторая — пустым значением, и в журнале это разные события.

**Когда изменение начинает действовать.** В своём процессе — сразу. В соседнем
(API и воркер — разные процессы) — в течение полуминуты: настройки читаются с коротким
кэшем, а механизма рассылки изменений между процессами нет намеренно. Это лишний узел
ради значения, которое правят раз в год, и ломается он молча.

## `POST /settings/mail/test` — роль `admin`

```json
{ "recipient": "admin@example.com" }
```

Адрес **обязателен**, без него — `400`. Раньше его можно было не указывать, и тогда брался
адрес из настройки `mail.test_recipient`; настройку убрали (2026-09-23): два поля для одного
письма на экране путали. Кабинет подставляет адрес того, кто проверяет. Строка прежней
настройки в базе, если осталась, ничего не делает: настройки читаются по известным ключам.

`200` → `{ "delivered": true, "error": null }` либо `{ "delivered": false, "error": "…" }`.

Идёт **мимо очереди писем** и возвращает ответ почтового сервера. Это осознанное
исключение из [ADR-0029](../adr/0029-pochta.md): у пробного письма нет породившего
события, которое надо сохранить вместе с ним, а смысл кнопки ровно в том, чтобы увидеть
отказ сервера сразу, а не через полминуты в таблице. Текст ошибки возвращается целиком —
без него «не работает» неотличимо от «не тот пароль».

Почта не настроена или адрес не задан — `400`.

## Капча

### `GET /auth/captcha` — без входа

`200` → `{ "site_key", "register", "login", "password_reset" }`.

Открыт всем: ключ страницы публичен по устройству SmartCaptcha — он и так уезжает
в браузер. Без этого ответа форма не знает, рисовать ли виджет.

Признаки форм показывают **действующее** состояние: включённая настройкой капча без
ключей отдаётся как выключенная. Иначе форма ждала бы токен, который взять неоткуда.

### Как проверяется

Формы `POST /auth/register`, `POST /auth/login` и `POST /auth/password-reset` принимают
поле `captchaToken`. Оно необязательно в схеме и обязательно по правилу: нужен ли токен,
решает настройка, и вторая копия этого условия в схеме разъехалась бы с первой.

Токен проверяется на стороне сервера — `POST https://smartcaptcha.cloud.yandex.ru/validate`,
тело `x-www-form-urlencoded` с полями `secret`, `token` и `ip`. Токен живёт пять минут
и принимается один раз (проверено по документации Яндекса 2026-09-04).

Токена нет, а капча включена — `400`. Проверка не пройдена — тоже `400`, **с тем же
текстом**: робот и человек с просроченным токеном получают один ответ, потому что разница
подсказывала бы, как подбирать.

### Недоступная проверка не закрывает вход

Сервис не ответил, ответил отказом или прислал незнакомый формат — запрос **пропускается**,
а в журнал уходит запись уровнем `error`. Тот же довод, что у счётчика ограничений
частоты: отказ на этом месте закрыл бы вход **всем**, включая администратора, которому
и предстоит это чинить.

Цена названа прямо: во время недоступности SmartCaptcha формы защищены только пределом
частоты по адресу источника и блокировкой учётной записи.

То же и при включённой капче без серверного ключа: пропускаем и пишем ошибку — иначе
опечатка в настройке закрывает вход в систему, а починить его можно только войдя.

### Порядок проверок

Предел частоты — **раньше** капчи. Иначе поток запросов оплачивался бы обращениями
к чужому сервису, то есть защита сама становилась бы нагрузкой.
