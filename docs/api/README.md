# Контракты API

Здесь лежат спецификации внешних контрактов: OpenAPI для клиентского API,
описание вебхуков и формат обмена с узлами АТС.

Правило: контракт описывается **до** реализации и обновляется в том же изменении,
что и код. Клиенты (службы такси) интегрируются по этим файлам, поэтому расхождение
спецификации с поведением — не документационный, а продуктовый дефект.

## Описано

- [auth.md](auth.md) — вход в кабинеты: регистрация, вход, сессии, права администратора,
  проверки состояния. Обоснование решений — [ADR-0018](../adr/0018-autentifikaciya.md).
- [operators.md](operators.md) — справочник операторов и определение оператора номера.
  Обоснование — [ADR-0013](../adr/0013-opredelenie-operatora.md).
- [billing.md](billing.md) — клиенты, партнёры, счета, журнал проводок, пополнение
  баланса. Обоснование — [ADR-0010](../adr/0010-model-billinga.md).
- [node.md](node.md) — **черновик.** Узел АТС → control plane: учётные записи SIP,
  запрос маршрута на каждый вызов, CDR, регистрация узла, heartbeat. Обоснование —
  [ADR-0009](../adr/0009-programmnaya-ats.md) и [ADR-0019](../adr/0019-dostup-mashin.md).
  Действует после подтверждения ADR-0019.

## Осталось описать, в порядке необходимости

1. **Клиентский API** — инициация вызова, статус, получение записи, баланс.
   Доступ по API-ключу, а не по сессии: схема доступа задана
   в [ADR-0019](../adr/0019-dostup-mashin.md), состав обработчиков — нет.
2. **Вебхуки клиенту** — завершение вызова, низкий баланс, исчерпание лимита.
   Подпись HMAC: здесь она возможна, потому что запрос формируем мы.
