# Контракт: лимиты по окнам

Квоты клиента, канала, партнёра и SIM. Обоснование — [ADR-0026](../adr/0026-limity-po-oknam.md).

## Зачем они

Это в первую очередь **защита SIM партнёра**, и только во вторую — ограничение клиента.
Оператор блокирует SIM за нечеловеческий профиль трафика, а потерянная SIM означает
потерянного партнёра ([BACKLOG.md](../BACKLOG.md)).

## Что и как считается

Лимит принадлежит **ровно одному** субъекту: клиенту, каналу, партнёру или SIM.
Лимит без субъекта не относится ни к кому, а лимит на двоих сразу непонятно кого
ограничивает — и то и другое отвергается.

| Поле | Значения |
|------|----------|
| `window` | `hour`, `day`, `week` (с понедельника), `month` — **календарные, в UTC** |
| `metric` | `calls` — попытки вызова; `minutes` — разговор |
| `value` | Сколько звонков или минут допустимо за окно. Ноль отвергается: «звонить нельзя вовсе» — это состояние субъекта, а не лимит |

**Окно фиксированное, а не скользящее.** Видно, когда счётчик обнулится: в полночь UTC,
в понедельник, первого числа. Скользящее окно потребовало бы хранить отметку каждого
вызова — таблицу, растущую с трафиком.

**Часовой пояс — UTC.** «Сутки» без указания пояса — это спор, который случится один раз
и дорого.

**Звонки считаются штуками, минуты — секундами.** Разговор в 90 секунд — это не «полторы
минуты» и не «одна», а ровно девяносто. Поэтому в ответе `used` и `limit` даны
в единицах хранения: у метрики `minutes` предел в 10 минут выглядит как `limit: 600`.

## Когда счётчик растёт

- `calls` — в момент создания вызова, **той же транзакцией**. Вызова нет — счётчика тоже;
- `minutes` — при тарификации CDR, той же транзакцией, что и деньги. Повторная доставка
  CDR минуты не удваивает: проводки второй раз тоже не будет.

**Квота по минутам может быть перебрана на длительность одного вызова.** Минуты
становятся известны только по CDR, а начатый разговор не отменяется. Резервировать
минуты вперёд не имеет смысла: квота нужна, чтобы профиль трафика SIM не выглядел
машинным, а не чтобы не пустить кого-то в последнюю минуту.

## Изменение и удаление

**Изменение предела не трогает израсходованное:** квота изменилась, потраченное никуда
не делось. **Удаление лимита уносит его счётчики** — это и есть способ обнулить счёт.

---

## `POST /limits` — роль `admin`

```json
{ "clientId": "…", "window": "day", "metric": "calls", "value": 500 }
```

Вместо `clientId` может быть `channelId`, `partnerId` или `simCardId` — ровно один.

`201` → `{ "limit": { "id", "client_id", "channel_id", "partner_id", "sim_card_id", "window", "metric", "value" } }`

Ни одного субъекта или больше одного — `400`. Второй лимит с тем же окном и метрикой
у того же субъекта — `409`: два одинаковых означали бы, что предел зависит от того,
какую строку прочитали первой.

## `GET /limits?clientId=…&channelId=…&partnerId=…&simCardId=…` — роли `admin`, `support`

`200` → `{ "limits": [ { …лимит…, "bucket_start", "used", "limit", "exceeded" } ] }`

Без параметров — все лимиты платформы. `used` и `limit` — в единицах хранения,
`bucket_start` — начало текущего окна в UTC. С этого ответа начинается разбор
«почему у клиента не звонит».

## `PUT /limits/:id` — роль `admin`

```json
{ "value": 1000 }
```

`200` → `{ "limit": { … } }`. Счётчик не трогается.

## `DELETE /limits/:id` — роль `admin`

`200` → `{ "limit": { … } }` — снятый лимит. Вместе с ним удаляются его счётчики.

## Отказ по лимиту

Причина `limit_exceeded`, код SIP `503 Service Unavailable` ([node.md](node.md)).
Отличается от `no_sim_available` намеренно: «все партнёры исчерпали квоту» и «SIM нет
вовсе» — разные разговоры с партнёром.
