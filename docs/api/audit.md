# Контракт: журнал действий

Журнал пишется рядом с действием, а не выводится потом из логов: лог живёт неделями
и хранится вне базы, а разбирать спор о списании или о доступе к записи разговора
приходится через месяцы.

У денежных действий запись идёт **той же транзакцией**, что и само действие
([ADR-0034](../adr/0034-zhurnal-deneg-odnoy-tranzakciey.md)): «не записалось» обязано
означать «не произошло».

**Журнал только читается.** Ни правки, ни удаления в API нет и не будет: строка, которую
можно поправить, перестаёт быть доказательством. Срок хранения не ограничен ничем, кроме
места на диске, — по этой же причине.

## `GET /audit` — роли `admin`, `support`

Поддержке доступен наравне с администратором: разбор обращения начинается с вопроса
«что вообще происходило с этим объектом».

### Параметры отбора

Все необязательные. **Пустое значение означает «любое»**, а не «пустое»: форма отбора
шлёт все свои поля, и `?action=` — это «любое действие». Без этого сброс фильтра
в интерфейсе давал бы отказ вместо полного списка.

| Параметр | Что отвечает |
|---|---|
| `action` | «Когда вообще выключали капчу» |
| `entityType`, `entityId` | «Что происходило с этим объектом» |
| `actorUserId` | «Что делал этот человек» |
| `correlationId` | «Что ещё случилось в том же запросе» — тот же идентификатор, что в логах ([ADR-0004](../adr/0004-logirovanie.md)) |
| `from`, `to` | Период по времени **события**, момент в виде ISO со смещением |
| `limit` | Размер страницы, по умолчанию 100, потолок 200 |
| `offset` | Смещение страницы |

Негодный момент времени и негодный идентификатор исполнителя — `400`. Это не то же самое,
что мусор в `limit`: там опечатка даёт умолчание, потому что размер страницы ни на что
не влияет, а молча показанный не тот период — это неверный ответ на вопрос разбора.

Потолок страницы ниже общего по API (200 против 1000) намеренно: строка журнала несёт
состояние до и после **целиком**, и это могут быть килобайты. Для выгрузки понадобится
свой путь, а не увеличенный предел на этом.

### Ответ

```json
{
  "entries": [
    {
      "id": "…",
      "occurred_at": "2026-09-07T10:15:00.000Z",
      "action": "user.status_changed",
      "entity_type": "user",
      "entity_id": "…",
      "actor": { "id": "…", "email": "admin@example.com", "full_name": "Иван Петров" },
      "actor_role": "admin",
      "before": { "status": "pending" },
      "after": { "status": "active", "revoked_sessions": 0 },
      "ip": "203.0.113.7",
      "correlation_id": "0f0a1b2c-…"
    }
  ],
  "total": 1842
}
```

Свежее сверху, по времени **события**, а не записи: у денежных действий они совпадают,
а у отложенных — нет, и разбор идёт по тому, когда произошло.

`total` — полное число подходящих строк, а не размер страницы. Без него в интерфейсе
остаётся бесконечная прокрутка ([DESIGN.md](../DESIGN.md)).

**`actor` пуст у действий системы:** истечение резерва, автоотключение SIM по порогу
неудач, фоновая сверка. У них нет инициатора-человека, и запись об этом так же важна,
как запись о действии администратора.

**`actor_role` — роль на момент действия**, копией из журнала, а не через связь.
Роль учётной записи меняется, и через год «кто это сделал» должно отвечать тем, кем
человек был тогда.

Учётную запись могли закрыть; ссылка на исполнителя проставлена `on delete set null`,
но между удалением и чтением возможен и просто ненайденный идентификатор. Тогда
в `actor` остаются идентификатор и прочерк вместо адреса — прочерк честнее пустоты.

### Что в журнал не попадает

Пароли, секреты второго фактора, значения секретных настроек площадки и номера абонентов
в открытом виде. Отвечает за это **вызывающий код**: журнал кладёт то, что ему дали.
У секретных настроек площадки, например, остаётся `<скрыто>`
([settings.md](settings.md)).

## `GET /audit/actions` — роли `admin`, `support`

`200` → `{ "actions": ["billing.deposit", "session.created", …] }`

Различные значения `action`, встречающиеся в журнале, по порядку и без повторов.

Спрашивается у журнала, а не перечисляется в коде: имя действия задаёт вызывающий код,
закрытого списка у него нет, и всякий список в интерфейсе разошёлся бы с содержимым
на первом же новом действии.

## Где живёт код

Запись — `AuditService` (модуль `audit`), чтение — `AuditRepository` и `AuditController`.
Контроллер зарегистрирован отдельным модулем `AuditHttpModule`: `IdentityModule`
импортирует `AuditModule` (записи о входе пишет он), и обратный импорт замкнул бы круг,
который пришлось бы разрывать `forwardRef`, то есть прятать.
