# Контракт: узел АТС → control plane

Граница между двумя плоскостями ([ARCHITECTURE.md](../ARCHITECTURE.md)). Выбор АТС
обоснован в [ADR-0009](../adr/0009-programmnaya-ats.md), доступ машин —
в [ADR-0019](../adr/0019-dostup-mashin.md).

**Статус: согласован 2026-09-01, реализуется.** Обработчики появляются по мере готовности
модулей — что уже работает, видно в [TASKS.md](../../TASKS.md).

## `GET /node/sip-gateways` — ключ узла

Обратная сторона каталога. В `POST /node/directory` перечислены те, кто регистрируется
**к нам** (шлюзы партнёров и каналы клиентов). Здесь — те, к кому регистрируемся **мы**:
SIP-транки, привязанные к этому узлу ([ADR-0039](../adr/0039-terminaciya-cherez-sip-trank.md)).

`200` →

```json
{
  "gateways": [
    {
      "name": "gw-a1b2c3d4e5f6",
      "proxy_host": "sip.provider.ru:5060",
      "register": true,
      "username": "zvonix-01",
      "password": "…"
    }
  ]
}
```

Из этого собирается конфигурация исходящих sofia-gateway. **Имя совпадает
с `sip_username` шлюза**, и по нему же диалплан направляет вызов:
`bridge sofia/gateway/gw-a1b2c3d4e5f6/79001234567`.

`register: false` — провайдер узнаёт нас по адресу источника, регистрация не нужна;
`username` и `password` тогда пусты.

**Здесь пароль провайдера уходит в открытом виде** — иначе зарегистрироваться нельзя.
Отсюда два требования, и оба обязательны: обработчик доступен только узлу по его ключу,
и обмен идёт по TLS ([ADR-0019](../adr/0019-dostup-mashin.md)). В ответы человеку пароль
не попадает никогда.

Отдаются только **действующие** транки **своего** узла: отключённый партнёр перестаёт
быть поднятым при следующем же обновлении конфигурации — тем же способом, каким его шлюз
перестаёт находиться в каталоге.

Ответ JSON, а не XML: конфигурацию sofia собирает агент узла, а не `mod_xml_curl`.

## Из чего следует форма этого контракта

Media plane не содержит бизнес-логики: ни цен, ни лимитов, ни прав. Узел спрашивает решение
на **каждый** вызов, потому что иначе изменение тарифа, лимита или баланса не вступает в силу
до перезагрузки конфигурации.

Отсюда главное свойство: **обработчик маршрута лежит в горячем пути телефонии.** Он
выполняется столько раз в секунду, сколько на платформе начинается звонков, и его задержка
— это задержка ответа абонента. Всё остальное в этом файле следует из этого.

## Что узел умеет и чего не умеет

Проверено по конфигурации модулей и документации FreeSWITCH. Это не наши предпочтения,
а границы возможного: контракт, который в них не укладывается, не заработает.

| Свойство | Как есть на самом деле |
|----------|------------------------|
| Формат запроса маршрута | `POST`, `application/x-www-form-urlencoded`. **Не JSON** |
| Формат ответа | XML FreeSWITCH. Не JSON |
| Заголовки | Произвольный задать **нельзя**. Только Basic/Digest либо клиентский сертификат |
| Тайм-аут | `timeout`, целые секунды. **По умолчанию 0 — без ограничения** |
| Ответ не 200 | Отбрасывается целиком, в лог пишется ошибка. Это **не** «маршрут не найден» |
| Размер ответа | `response-max-bytes`, по умолчанию 1 МиБ |
| Состав запроса | Пять служебных полей **плюс все переменные канала в области видимости**, если не ограничить `enable-post-var` |
| Доставка CDR | `mod_json_cdr`: повторы (`retries`, `delay`), при неудаче — на диск в `err-log-dir` |
| Кодирование CDR | `encode-values` по умолчанию **`true`**: каждое значение приходит percent-encoded |

Три следствия, которые определяют всё ниже:

1. **Отказ выражается диалпланом, а не кодом HTTP.** Код, отличный от 200, узел выбросит,
   и абонент услышит невнятный отбой вместо причины.
2. **Тайм-аут задаётся явно.** Иначе неотвечающий control plane держит вызов, пока
   не сработает тайм-аут SIP.
3. **Доставка CDR — «хотя бы один раз».** Приёмник обязан быть идемпотентным; в
   [ADR-0010](../adr/0010-model-billinga.md) это уже так.

## Аутентификация

Basic поверх TLS: имя — идентификатор ключа, пароль — секрет ([ADR-0019](../adr/0019-dostup-mashin.md)).
Наш агент вместо этого может слать `Authorization: Bearer <id>.<secret>` — ключ тот же.

`hostname` из тела запроса **сверяется** с узлом, которому выдан ключ. Расхождение — отказ
и запись в аудит: ключ применён не на том узле, для которого выпущен.

Ключ узла не открывает ни одного человеческого обработчика, а человеческая сессия
не открывает ни одного машинного. Иначе украденный с узла ключ становится администратором
платформы.

### `GET /machine/self` — проверка ключа самой машиной

То же, чем `/auth/me` служит человеку. Нужен скрипту установки и поддержке: снаружи отзыв,
истёкший срок и адрес вне списка выглядят **одинаково** — намеренно, иначе по разнице
ответов перебираются существующие идентификаторы. Этот обработчик отвечает на единственный
вопрос, который узел может задать сам:

`200` → `{ "key_id", "kind", "owner_id" }` — ключ принимается **с этого адреса**.
`401` — не принимается; причина в логе control plane.

Секрет в ответе не участвует.

## `POST /node/directory` — привязка `directory`

**Реализовано.** Полное описание, включая выдачу и перевыпуск учётных данных, —
в [telephony.md](telephony.md).

Коротко: узел спрашивает учётную запись SIP по имени, control plane отвечает документом
`directory` с `a1-hash` вместо пароля. Смысл в том, чтобы **на узле не было ни одного
пароля в файле**: заблокировали партнёра — его шлюз перестал регистрироваться
при следующей же попытке, без раскатки конфигурации.

Отвечает **всегда 200**: и когда запись есть, и когда её нет, и когда запрос не разобрался.
Любой другой код `mod_xml_curl` отбрасывает целиком.

## `POST /node/dialplan` — маршрут на вызов

Привязка `dialplan`. Главный обработчик системы. **Реализован**; порядок проверок,
инварианты одновременности и резерва — в [routing.md](routing.md).

### Что приходит

По умолчанию FreeSWITCH шлёт все переменные канала в области видимости — сотни полей.
На горячем пути это лишний трафик, а в control plane — данные, которые ему не нужны.
Состав ограничивается `enable-post-var` до необходимого:

| Поле | Кто заполняет | Зачем |
|------|---------------|-------|
| `section` | модуль | Обязано быть `dialplan` |
| `tag_name`, `key_name`, `key_value` | модуль | Контекст запроса |
| `hostname` | модуль | Имя узла, сверяется с ключом |
| `Unique-ID` | канал | Идентификатор вызова: он же correlation-id и ключ идемпотентности CDR |
| `Caller-Destination-Number` | канал | Номер назначения |
| `Caller-Caller-ID-Number` | канал | Кто звонит |
| `variable_zvonix_channel` | `directory` | Канал клиента |

Неизвестные поля игнорируются: состав переменных FreeSWITCH меняется от версии к версии,
и строгая проверка «лишних полей нет» ломала бы телефонию при обновлении узла.

### Бюджет времени

| Кто | Ограничение |
|-----|-------------|
| Узел | `timeout=3` — задаётся явно, значение по умолчанию (без ограничения) недопустимо |
| Обработчик целиком | 2 с |
| Из них внешний lookup оператора | не более 800 мс |

**Почему lookup вообще оказался на пути вызова.** [ARCHITECTURE.md](../ARCHITECTURE.md)
описывает шаг 3 как «нет в своей базе → отклонить и поставить в очередь». Буквально это
означает, что **первый звонок на каждый незнакомый номер не проходит** — а у службы такси
новый пассажир это норма, а не исключение. Поэтому порядок такой:

1. своя база `NumberResolution` — индексное чтение, микросекунды;
2. промах или просроченная запись — **одна** попытка внешнего lookup в пределах 800 мс;
3. не успели или не ответили — отказ и постановка номера в очередь, чтобы следующий
   звонок прошёл.

Правило [ADR-0013](../adr/0013-opredelenie-operatora.md) при этом не смягчается ни на шаг:
догадка о неподтверждённом операторе по-прежнему запрещена. Меняется только то, сколько
усилий прикладывается, прежде чем признать оператора неподтверждённым.

**Потолок, который отсюда следует.** Источник lookup держит не более двух запросов в секунду.
Значит платформа начинает не более **двух вызовов в секунду на незнакомые номера**; на
знакомые ограничения нет. Всплеск в полсотни новых номеров упрётся в бюджет 800 мс, и такие
вызовы будут отклонены.

Отсюда два следствия, оба уже записаны в [TASKS.md](../../TASKS.md):

- разрешение базы номеров клиента **до** запуска — часть подключения клиента, а не улучшение;
- платный поставщик lookup — не запасной вариант, а снятие этого потолка.

### Ответ: маршрут найден

Упорядоченный список кандидатов уезжает одним `bridge`: разделитель `|` означает
«пробовать по очереди до ответа». Перебор выполняет узел — это ровно то, чего от него хотят,
и ради чего решение не превращается в серию обращений к control plane.

```xml
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
<document type="freeswitch/xml">
  <section name="dialplan">
    <context name="zvonix">
      <extension name="zvonix-route">
        <condition>
          <action application="set" data="hangup_after_bridge=true"/>
          <action application="set" data="continue_on_fail=NO_ANSWER,USER_BUSY,NO_USER_RESPONSE,NORMAL_TEMPORARY_FAILURE,NETWORK_OUT_OF_ORDER"/>
          <action application="export" data="nolocal:zvonix_call_id=0198f3c4-…"/>
          <action application="record_session" data="/var/lib/zvonix/rec/0198f3c4-….wav"/>
          <action application="bridge" data="user/gw-a1b2c3@${domain}|user/gw-d4e5f6@${domain}"/>
          <action application="hangup"/>
        </condition>
      </extension>
    </context>
  </section>
</document>
```

**`user/`, а не `sofia/gateway/`.** В терминах FreeSWITCH «gateway» — это транк, на который
регистрируемся мы. У нас наоборот: GOIP партнёра регистрируется **на узле**, то есть является
учётной записью каталога, и вызов к нему идёт через `user/`. Совпадение слова «шлюз» в двух
разных значениях — источник ошибки, которая проявляется только на живом железе.

Точный вид строки для GOIP не проверен: см. «Что не проверено на живом железе».

`record_session` появляется, только если канал требует запись. Шлюзы типа `android`
в списке кандидатов при этом отсутствуют — там запись технически невозможна
([ADR-0012](../adr/0012-mobilnoe-prilozhenie.md)).

`zvonix_call_id` экспортируется, чтобы тот же идентификатор дошёл до CDR и до записи:
без него связать разговор, деньги и запись нечем.

### Ответ: отказ

Тоже **200 и тоже диалплан** — просто такой, который кладёт трубку с внятной причиной:

```xml
<document type="freeswitch/xml">
  <section name="dialplan">
    <context name="zvonix">
      <extension name="zvonix-reject">
        <condition>
          <action application="set" data="zvonix_reject_reason=operator_unconfirmed"/>
          <action application="respond" data="404 Not Found"/>
        </condition>
      </extension>
    </context>
  </section>
</document>
```

`zvonix_reject_reason` остаётся переменной канала и приезжает обратно в CDR. Абонент видит
код SIP, поддержка — точную причину. Коды намеренно грубее причин: сообщать звонящему,
что у клиента кончились деньги или что номер в чёрном списке, не следует.

| Причина | Ответ | Что видит звонящий |
|---------|-------|--------------------|
| `channel_unknown` — канал неизвестен или не активен | `respond 403 Forbidden` | 403 |
| `destination_invalid` — набранное не приводится к российскому номеру | `respond 404 Not Found` | 404 |
| `operator_unconfirmed` — оператор номера не подтверждён | `respond 404 Not Found` | 404 |
| `destination_blocked` — номер в чёрном списке | `respond 403 Forbidden` | 403 |
| `operator_not_allowed` — оператор номера не разрешён каналом | `respond 403 Forbidden` | 403 |
| `insufficient_funds` — овердрафт исчерпан | `respond 402 Payment Required` | 402 |
| `limit_exceeded` — окно лимита исчерпано | `respond 503 Service Unavailable` | 503 |
| `no_sim_available` — нет свободной SIM нужного оператора | `respond 503 Service Unavailable` | 503 |
| `recording_required` — подходят только шлюзы без записи | `respond 503 Service Unavailable` | 503 |
| `no_coverage` — регион номера не покрыт ни одним партнёром | `respond 503 Service Unavailable` | 503 |
| `no_tariff` — нет действующего тарифа партнёра или правила наценки | `respond 503 Service Unavailable` | 503 |
| `internal_error` — неисправность control plane | `respond 503 Service Unavailable` | 503 |

**Отказ — это тоже событие.** Каждый пишется как `Call` со статусом `failed` и причиной,
иначе на вопрос «почему у клиента не звонит» отвечать нечем.

Исключение одно — **неизвестный канал**: записать такой запрос не к чему, у вызова канал
обязателен, а строка без канала не отвечает ни на один вопрос. Остаётся строка в логе.

### Резерв

Перед выдачей маршрута `billing` резервирует максимальную стоимость вызова. Инвариант
[DOMAIN.md](../DOMAIN.md) — «баланс не уходит ниже овердрафта» — обеспечивается
резервированием **до** звонка, а не проверкой после: сто одновременных вызовов при остатке
на одну минуту иначе все пройдут проверку и все состоятся.

Резерв освобождается по CDR или по истечении срока фоновой задачей. Не освобождённый
из-за потерянного CDR резерв — не потеря денег, а замороженный остаток, и он обязан
разморозиться сам.

## `POST /node/cdr` — завершённый вызов

`mod_json_cdr`, тело — JSON. **Реализован.**

**`encode-values` обязано быть `false`.** По умолчанию FreeSWITCH percent-кодирует каждое
значение по отдельности, и наивный приёмник сохранит `%D0%9C%D0%A2%D0%A1` как название
оператора. Ошибка тихая: данные приходят, тесты зелёные, в отчётах мусор.

**Доставка «хотя бы один раз».** При неудаче модуль повторяет (`retries`, `delay`), а затем
пишет CDR на диск в `err-log-dir`. Значит один и тот же вызов приходит повторно — это
штатный режим, а не сбой. Идемпотентность по `Unique-ID` уже заложена
в [ADR-0010](../adr/0010-model-billinga.md): повторный CDR не создаёт вторых проводок.

### Что делает приём

Порядок действий не произволен: **сначала деньги, потом резерв, потом состояние вызова.**
Проводка идемпотентна по ключу `charge:<идентификатор вызова>`, снятие резерва —
условным обновлением, состояние вызова перезаписывается. Поэтому повторная доставка
доводит до конца то, что не доделала первая, и ничего не списывает дважды.

Обратный порядок — сначала закрыть вызов — оставлял бы при сбое закрытый вызов
без списания: деньги потеряны, и повторная доставка их уже не найдёт.

Списание — одна операция из трёх проводок: клиент платит, партнёр зарабатывает, платформа
удерживает наценку. Сумма трёх равна нулю.

Цена берётся **на момент начала вызова**, а не приёма CDR: узел мог держать CDR на диске,
пока control plane был недоступен, и сегодняшняя цена переоценила бы прошлое.

Тарифицируется только состоявшийся разговор. Занято, не ответили и отмена закрывают вызов
и освобождают резерв, денег не двигая.

**Плечо B принимается без тарификации.** У него свой `uuid`, но `zvonix_call_id`
экспортирован диалпланом на оба плеча: это тот же разговор, и списание вышло бы двойным.

### Коды ответа

Здесь они, в отличие от диалплана, обычные — и различаются намеренно:

| Код | Когда | Что сделает узел |
|-----|-------|------------------|
| `200` | Принят. **В том числе повтор** | Забудет CDR |
| `400` | Тело не разбирается | Повторит, затем положит на диск — повторять бессмысленно, но человек обязан увидеть |
| `404` | CDR по неизвестному вызову | То же. Узел совершил вызов, которого мы не знаем: это аномалия, а не мелочь |
| `5xx` | Временная неисправность control plane | Повторит, затем положит на диск |

Файлы в `err-log-dir` — это невыставленные счета. Их накопление должно поднимать тревогу,
а не лежать до первой жалобы.

## `POST /node/enroll` — регистрация узла при установке

Вызывается скриптом установки, аутентификация — **одноразовым** токеном из команды
установки ([ADR-0019](../adr/0019-dostup-mashin.md)).

Ответ — постоянные учётные данные и адреса обработчиков, то есть ровно то, что скрипт
подставит в `xml_curl.conf.xml` и `json_cdr.conf.xml`.

Повторное применение токена — `409` и запись в аудит: команду прочитал кто-то ещё.

## `POST /node/heartbeat` — агент узла

Раз в несколько десятков секунд: версия, время работы, число активных вызовов, состояние
шлюзов и портов. Переводит `Node` по жизненному циклу
`online → degraded → offline` ([DOMAIN.md](../DOMAIN.md)).

Молчание дольше порога — узел `offline`, новые вызовы на него не направляются.

## `POST /routing/preview` — роли `admin`, `support`

Тот же расчёт маршрута, но **без побочных действий**: ни резерва, ни записи `Call`,
ни постановки номера в очередь. Вход и выход — JSON.

Нужен для одного вопроса, который будут задавать постоянно: «почему у клиента не звонит
на этот номер». Без него ответ приходится собирать из логов, а по логам не видно, какие
кандидаты отсеялись и на каком шаге.

## Когда control plane недоступен

**Решено 2026-09-01: звонки запрещаются.** Это принятая цена, а не недоработка.

Маршрут из кэша — это маршрут по устаревшему сопоставлению оператора и по устаревшему
остатку. Звонить разрешено только по операторам, которых партнёр объявил своими, а из
запомненного ответа неизвестно, тот ли это оператор сейчас. По
[ADR-0013](../adr/0013-opredelenie-operatora.md) неверный оператор означает списание
реальных денег партнёра, а устаревший остаток — уход клиента в минус глубже разрешённого.
Несостоявшийся звонок стоит одной поездки; состоявшийся неправильно стоит денег партнёру,
которому мы за это не платим.

Правильное вложение — доступность control plane, а не деградационный режим, который
по построению принимает решения на данных, признанных ненадёжными.

Узел при недоступности отвечает `respond 503` — то есть ведёт себя как перегруженный,
а не как сломанный.

## Что не проверено на живом железе

Ни один пункт ниже не подтверждён: шлюза и сервера под рукой нет
([TASKS.md](../../TASKS.md), раздел «Выяснить у внешних сторон»).

- Поведение GOIP при `respond 402`: код зарезервирован в RFC 3261 и обрабатывается
  оборудованием по-разному. Если не отображается внятно — заменить на `403`.
- Перебор кандидатов через `|` в `bridge` совместно с `continue_on_fail`: список причин
  продолжения подобран по документации, а не по наблюдению.
- **Точный вид строки вызова зарегистрированного GOIP.** `user/gw-…@realm` — правильная
  форма для зарегистрированной учётной записи, но GOIP ожидает номер назначения
  в запросе, и вероятнее понадобится `sofia/internal/<номер>@${sofia_contact(...)}`.
  Выясняется одним звонком на живом шлюзе.
- Фактическая задержка `mod_xml_curl` под нагрузкой — от неё зависит, реален ли бюджет 2 с.
- `record_session` на вызове, ушедшем через GOIP: пишется ли обе стороны разговора.
- Состав переменных канала, которые GOIP действительно проставляет.
