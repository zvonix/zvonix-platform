# Контракт: шлюзы, каналы и каталог SIP

Учётные записи SIP обеих сторон вызова и их выдача узлу.
Решение об АТС — [ADR-0009](../adr/0009-programmnaya-ats.md); обмен узла с control plane
целиком — [node.md](node.md).

## Зачем каталог отдаётся из control plane

На узле не должно остаться **ни одного пароля в файле**. Смысл ровно один: заблокировали
партнёра — его шлюз перестал регистрироваться при следующей же попытке, без раскатки
конфигурации и без перезапуска узла.

Проверяется состояние **и записи, и её владельца**. Отдельной проверки шлюза мало:
заблокированный партнёр с активным шлюзом продолжал бы регистрироваться, то есть свойство,
ради которого всё и сделано, не работало бы.

| Кто | Отдаётся каталогом при |
|-----|-----------------------|
| Шлюз партнёра | шлюз `active` **и** партнёр `verified` |
| Канал клиента | канал `active` **и** клиент `active` |

## Пароль не хранится

Хранится `a1-hash` — ровно то, чем SIP проверяет digest: `MD5(имя:realm:пароль)`.
FreeSWITCH принимает его в каталоге вместо пароля, поэтому открытый пароль не нужен
ни в базе, ни в ответе узлу. Показывается один раз при выдаче.

**Честно про предел этой меры.** Обладание `a1-hash` равносильно знанию пароля **для входа
по SIP**: digest устроен так, что больше ничего и не требуется. Мера защищает не учётную
запись, а сам пароль — он придуман нами, показан один раз, и утечка таблицы не даёт строку,
которую можно попробовать где-то ещё. MD5 здесь требование протокола SIP, а не выбор.

### Realm один на всю платформу

`SIP_REALM` — общий, а не свой у каждого узла. Realm входит в хеш, поэтому свой realm
у каждого узла означал бы, что учётная запись годится только на одном узле: шлюз,
перерегистрировавшийся на соседний, перестал бы проходить проверку — а перерегистрация
это штатный способ пережить отказ узла.

**Менять значение после выдачи учётных записей нельзя:** все хеши станут недействительны
разом, и все шлюзы отвалятся.

## `POST /gateways` — роль `admin`

```json
{ "partnerId": "…", "name": "GOIP в гараже", "type": "goip", "model": "GoIP-8", "portCount": 8 }
```

`201` →
```json
{
  "gateway": { "id", "partner_id", "name", "type", "status", "sip_username",
               "node_id", "registered_at", "model", "port_count" },
  "account": { "username": "gw-a1b2c3d4e5f6", "password": "…", "realm": "sip.zvonix.ru" }
}
```

`password` присутствует **только здесь и только один раз**. Восстановить его неоткуда.

Шлюз заводится в состоянии `pending`: учётная запись выдана, но каталог её не отдаёт,
пока не пройдена модерация.

`type` — `goip` или `android`. На `android` **запись разговора технически невозможна**
([ADR-0012](../adr/0012-mobilnoe-prilozhenie.md)), поэтому канал с требованием записи
на такой шлюз не маршрутизируется никогда.

Имя шлюза видит только партнёр и администратор. В клиентский контур оно не попадает
ни в каком виде ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)).

## `POST /gateways/:id/status` — роль `admin`

```json
{ "status": "active" }
```

`201` → `{ "gateway": { … } }`

Отключение действует **немедленно**: каталог перестаёт отдавать учётную запись, и следующая
регистрация не проходит. Уже установленные вызовы не рвутся — их завершает сам разговор.

## `POST /gateways/:id/credentials` — роль `admin`

`201` → `{ "account": { "username", "password", "realm" } }`

Перевыпуск. Меняются **и имя, и пароль**. Только пароля мало: имя уже засветилось в записи
регистрации на узле и в логах, а перенастраивать оборудование партнёру всё равно придётся —
так пусть меняется всё разом. Старое имя перестаёт находиться сразу.

## `GET /gateways?partnerId=…` — роли `admin`, `support`

`200` → `{ "gateways": [ … ] }`. Ни пароля, ни `a1-hash` в ответе нет.

`node_id` и `registered_at` показывают, на каком узле шлюз зарегистрирован и когда —
по ним видно, живой ли он.

## `POST /channels` — роль `admin`

```json
{ "clientId": "…", "name": "Основная линия", "recordingRequired": true, "callerId": "79001234567" }
```

`201` → `{ "channel": { … }, "account": { "username": "ch-…", "password", "realm" } }`

**Канал — линия клиента, а не порт шлюза.** Смешивать эти понятия нельзя,
см. [GLOSSARY.md](../GLOSSARY.md).

`callerId` — номер, который увидит вызываемый. Пусто — номер SIM, с которой ушёл вызов.

## `POST /channels/:id/status` · `GET /channels?clientId=…`

Как у шлюзов: `admin` меняет состояние, `admin` и `support` смотрят.

## `POST /node/directory` — ключ узла

Привязка `directory` для `mod_xml_curl`. Единственный обработчик проекта, который принимает
`x-www-form-urlencoded` и отвечает XML: у модуля нет ни JSON, ни произвольных заголовков.

**Код ответа всегда 200** — и когда запись есть, и когда её нет, и когда запрос не разобрался.
Любой другой код `mod_xml_curl` отбрасывает целиком и пишет ошибку в лог, то есть узел
остаётся без учётных записей вообще. Поэтому ошибок здесь нет как класса: всё непонятое —
это «записи нет», а причина уходит в лог control plane.

Запись есть:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
<document type="freeswitch/xml">
  <section name="directory">
    <domain name="sip.zvonix.ru">
      <user id="gw-a1b2c3d4e5f6">
        <params>
          <param name="a1-hash" value="…"/>
        </params>
        <variables>
          <variable name="zvonix_gateway" value="0198f3c4-…"/>
          <variable name="zvonix_gateway_type" value="goip"/>
        </variables>
      </user>
    </domain>
  </section>
</document>
```

Записи нет:

```xml
<document type="freeswitch/xml">
  <section name="result">
    <result status="not found"/>
  </section>
</document>
```

**Неизвестная и отключённая записи отвечают одинаково.** Иначе по разнице ответов
заблокированный партнёр узнаёт, что его шлюз ещё числится в системе.

### Переменные канала

FreeSWITCH проставит их на всех вызовах этой учётной записи, и они приедут в запрос
маршрута. Так на узле не остаётся вообще никакого знания о том, чей это вызов.

| Переменная | У кого | Зачем |
|------------|--------|-------|
| `zvonix_gateway` | шлюз | Идентификатор шлюза |
| `zvonix_gateway_type` | шлюз | `goip` или `android` |
| `zvonix_channel` | канал | Идентификатор канала: по нему запрос маршрута опознаёт линию |
| `zvonix_recording_required` | канал | Требуется ли запись |
| `zvonix_caller_id` | канал | Если задан |

### Отметка о регистрации

Успешный ответ проставляет шлюзу узел и время: по ним видно, где шлюз сейчас и жив ли он.
Это не подтверждение регистрации SIP — это факт запроса учётных данных, то есть попытки.
Настоящее состояние регистрации приходит событиями ESL и будет отдельно.
