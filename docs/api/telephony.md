# Контракт: шлюзы, каналы и каталог SIP

Учётные записи SIP обеих сторон вызова и их выдача узлу.
Решение об АТС — [ADR-0009](../adr/0009-programmnaya-ats.md); обмен узла с control plane
целиком — [node.md](node.md).

## SIP-транки — второй род ёмкости

Партнёр терминирует не только через GSM. **SIP-транк** — соединение с транзитным
оператором ([ADR-0039](../adr/0039-terminaciya-cherez-sip-trank.md)): ни SIM, ни портов,
ёмкость меряется числом одновременных вызовов.

Транк — это **шлюз вида `sip_trunk`**: тот же владелец, то же состояние, те же пороги
качества. Отличие одно, и оно решает всё: **регистрация идёт в обратную сторону**.
GOIP регистрируется у нас и потому значится в каталоге; к провайдеру регистрируемся мы,
и потому транка в каталоге нет — он значится **исходящим sofia-gateway** в конфигурации
узла, под тем же именем `sip_username`.

### `POST /sip-trunks` — роль `admin`

```json
{
  "partnerId": "…", "nodeId": "…", "name": "Транзит основной",
  "proxyHost": "sip.provider.ru:5060",
  "registersOutbound": true,
  "outboundUsername": "zvonix-01", "outboundSecret": "…",
  "maxConcurrentCalls": 10
}
```

`201` → `{ "trunk": { "id", "sip_username", "proxy_host", "has_secret", … } }`

**Узел обязателен.** К провайдеру регистрируемся мы, и регистрация принадлежит конкретной
машине; транк без узла — это ёмкость, которую некому поднять. По той же причине вызов
на транк выбирается только на **том** узле, к которому транк привязан.

**Способов доступа два.** `registersOutbound: true` — регистрация с именем и паролем;
`false` — провайдер узнаёт нас по адресу источника, и учётные данные не нужны.
Регистрация без имени и пароля отвергается с названной причиной: молча она не состоялась
бы, а платформа продолжала бы считать транк годным.

Заводит **администратор**: пароль провайдера — чужой секрет, за утечку которого платит
партнёр.

### Пароль провайдера

Единственный пароль в проекте, который **шифруется, а не хешируется**: без открытого
значения к провайдеру не зарегистрироваться. Шифрование — то же, что у секрета второго
фактора ([ADR-0028](../adr/0028-vtoroy-faktor.md)), с собственным назначением ключа.

**В ответах человеку пароля нет никогда** — ни при заведении, ни в списке, ни в журнале
действий: там остаётся `has_secret`. Расшифрованным он уходит ровно в одно место —
в `GET /node/sip-gateways`, узлу по его ключу.

### `GET /sip-trunks?partnerId=…` — роли `admin`, `support`

`200` → `{ "trunks": [ … ] }`

### `PATCH /sip-trunks/:id` — роль `admin`

Все поля необязательны, но хотя бы одно обязано быть. **«Поля нет» означает «не трогать»,
а не «очистить»**: правка одного лишь адреса не должна стирать учётные данные — транк
перестал бы подниматься, и увидеть это можно было бы только в логе узла.

Состояние транка меняется общим `POST /gateways/:id/status`: транк это шлюз, и второй
способ включать его разошёлся бы с первым.

## Зачем каталог отдаётся из control plane

На узле не должно остаться **ни одного пароля в файле**. Смысл ровно один: заблокировали
партнёра — его шлюз перестал регистрироваться при следующей же попытке, без раскатки
конфигурации и без перезапуска узла.

Проверяется состояние **и записи, и её владельца**. Отдельной проверки шлюза мало:
заблокированный партнёр с активным шлюзом продолжал бы регистрироваться, то есть свойство,
ради которого всё и сделано, не работало бы.

| Кто | Отдаётся каталогом при |
|-----|-----------------------|
| Шлюз партнёра | шлюз `active` **и** партнёр `verified` |
| Канал клиента | канал `active` **и** клиент `active` |

## Пароль не хранится

Хранится `a1-hash` — ровно то, чем SIP проверяет digest: `MD5(имя:realm:пароль)`.
FreeSWITCH принимает его в каталоге вместо пароля, поэтому открытый пароль не нужен
ни в базе, ни в ответе узлу. Показывается один раз при выдаче.

**Честно про предел этой меры.** Обладание `a1-hash` равносильно знанию пароля **для входа
по SIP**: digest устроен так, что больше ничего и не требуется. Мера защищает не учётную
запись, а сам пароль — он придуман нами, показан один раз, и утечка таблицы не даёт строку,
которую можно попробовать где-то ещё. MD5 здесь требование протокола SIP, а не выбор.

### Realm один на всю платформу

`SIP_REALM` — общий, а не свой у каждого узла. Realm входит в хеш, поэтому свой realm
у каждого узла означал бы, что учётная запись годится только на одном узле: шлюз,
перерегистрировавшийся на соседний, перестал бы проходить проверку — а перерегистрация
это штатный способ пережить отказ узла.

**Менять значение после выдачи учётных записей нельзя:** все хеши станут недействительны
разом, и все шлюзы отвалятся.

## `POST /gateways` — роль `admin`

```json
{ "partnerId": "…", "name": "GOIP в гараже", "type": "goip", "model": "GoIP-8", "portCount": 8,
  "registrationMode": "port" }
```

`201` →
```json
{
  "gateway": { "id", "partner_id", "name", "type", "status", "registration_mode", "sip_username",
               "node_id", "registered_at", "model", "port_count" },
  "account": { "username": "gw-a1b2c3d4e5f6", "password": "…", "realm": "sip.zvonix.ru" },
  "port_accounts": [ { "port_id", "port_number", "username": "pt-…", "password", "realm" } ]
}
```

`registrationMode` — способ подключения ([ADR-0054](../adr/0054-vhod-po-liniyam-goip.md)):
`gateway` (по умолчанию) — один вход на шлюз, линия GOIP выбирается префиксом;
`port` — свой вход у каждого порта, только у `goip` (иначе `400`). При `port` в
`port_accounts` — входы всех заведённых портов, один раз.

**Порты 1…`portCount` заводятся вместе со шлюзом**, той же транзакцией (у транка — нет).
До 2026-09-24 число только записывалось, а портов не появлялось: партнёр указывал восемь
и видел «портов не заведено».

`password` присутствует **только здесь и только один раз**. Восстановить его неоткуда.

Шлюз заводится в состоянии `pending`: учётная запись выдана, но каталог её не отдаёт,
пока не пройдена модерация.

`type` — `goip` или `android`. На `android` **запись разговора технически невозможна**
([ADR-0012](../adr/0012-mobilnoe-prilozhenie.md)), поэтому канал с требованием записи
на такой шлюз не маршрутизируется никогда.

Имя шлюза видит только партнёр и администратор. В клиентский контур оно не попадает
ни в каком виде ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)).

## `POST /gateways/:id/status` — роль `admin`

```json
{ "status": "active" }
```

`201` → `{ "gateway": { … } }`

Отключение действует **немедленно**: каталог перестаёт отдавать учётную запись, и следующая
регистрация не проходит. Уже установленные вызовы не рвутся — их завершает сам разговор.

**Источник отключения** ([ADR-0047](../adr/0047-kto-vyklyuchil-shlyuz.md)). `suspended`
от администратора записывается с `suspended_by: "admin"` — такое отключение партнёр
не снимает. Шлюз, выключенный самим партнёром (`partner`), администратор может **запереть**
тем же запросом `suspended`: состояние не меняется, меняется источник, и партнёр больше
не включит и не спишет шлюз. Любое другое состояние источник очищает. Тот же запрос
в то же состояние с тем же источником ничего не меняет и в журнал не пишется. Если
состояние успели изменить между чтением и записью — `409`.

**Списанный шлюз не возвращается** и этим обработчиком: из `retired` — `409`. Порты
списанного освобождены, а карты могли уже встать в другие шлюзы.

**Списание (`retired`) освобождает порты шлюза** той же транзакцией: карты из них вынимаются
и становятся свободными, а поставить карту в порт списанного шлюза нельзя (`409`). Иначе
карта оказывается неизвлекаемой — ни вынуть, ни списать, ни переставить
([DOMAIN.md](../DOMAIN.md), «Инварианты»).

## `POST /gateways/:id/credentials` — роль `admin`

`201` → `{ "account": { "username", "password", "realm" } }`

Новый пароль: **имя прежнее** ([ADR-0054](../adr/0054-vhod-po-liniyam-goip.md), ревизия
2026-09-25). Прежний пароль перестаёт действовать сразу — каталог отдаёт хеш нового;
отметка регистрации стирается. Имя не секрет: утечку закрывает пароль, а смена имени
заставляла партнёра перенастраивать два поля вместо одного.

## `POST /gateways/:id/registration-mode` — роль `admin`

`{ "mode": "port" | "gateway" }` → `201` `{ "gateway", "port_accounts" }`. То же, что
у партнёра ([partner.md](partner.md)): при переходе на `port` портам без входа он
выдаётся, регистрация стороны, на которую переключились, стирается; `port` не у GOIP
и смена у списанного — `409`; журнал `gateway.registration_mode_changed`.

## `POST /gateways/:id/port-credentials` · `POST /gateway-ports/:id/credentials` — роль `admin`

Входы портам без входа (`{ "port_accounts" }`) и новый пароль одного порта — имя
прежнее (`{ "port_account" }`), как у партнёра. При `gateway` — `409`. Журнал
`gateway_port.credentials_issued` (выдача) и `gateway_port.password_reset` (новый пароль) —
только имя, без пароля.

У порта в `GET /gateways/:id/ports` — `sip_username` (пусто — вход не выдан), `node_id`
и `registered_at` линии.

## `GET /gateways?partnerId=…` — роли `admin`, `support`

`200` → `{ "gateways": [ … ] }`. Ни пароля, ни `a1-hash` в ответе нет.

`node_id` и `registered_at` показывают, на каком узле шлюз зарегистрирован и когда —
по ним видно, живой ли он. `suspended_by` — кто выключил: `partner`, `admin` или
`failure_threshold`; задан ровно у `suspended`. То же поле есть и у транка.

## `POST /channels` — роль `admin`

```json
{ "clientId": "…", "name": "Основная линия", "recordingRequired": true, "callerId": "79001234567" }
```

`201` → `{ "channel": { … }, "account": { "username": "ch-…", "password", "realm" } }`

**Канал — линия клиента, а не порт шлюза.** Смешивать эти понятия нельзя,
см. [GLOSSARY.md](../GLOSSARY.md).

`callerId` — номер, который увидит вызываемый. Пусто — номер SIM, с которой ушёл вызов.

## `POST /channels/:id/status` · `GET /channels?clientId=…`

Как у шлюзов: `admin` меняет состояние, `admin` и `support` смотрят.

Канал звонит только в состоянии `active`, и **этого мало**: маршрутизация требует `active`
и от самого клиента ([billing.md](billing.md), `PATCH /clients/:id/status`). Приостановленный
клиент не звонит ни по одному каналу, сколько бы активных каналов у него ни было.

## `PATCH /channels/:id` — роль `admin`

```json
{ "name": "Диспетчерская", "recordingRequired": true, "callerId": "79005554433" }
```

`200` → `{ "channel": { … } }`

Все поля необязательны, но **хотя бы одно обязано быть**: пустая правка — `400`, а не
тихий успех. До появления обработчика эти три величины задавались только при заведении,
и сменить номер для показа можно было единственным способом — завести канал заново,
то есть выдать новый пароль SIP и заставить клиента перенастроить АТС.

**«Поля нет» означает «не трогать», а не «очистить».** Очистка номера для показа
выражается явным `null`: иначе правка названия однажды молча стёрла бы настроенный номер.

Учётных данных правка не касается — их меняет только перевыпуск.

Смена `recordingRequired` действует на **последующие** вызовы; уже записанное остаётся.
Включение сужает выбор партнёров: канал с записью не уходит на шлюзы типа `android`,
где она технически невозможна ([ADR-0012](../adr/0012-mobilnoe-prilozhenie.md)).

Правка попадает в журнал (`channel.updated`) целиком — все три поля до и после.

## `POST /channels/:id/credentials` — роль `admin`

`201` → `{ "account": { "username", "password", "realm" } }`

Перевыпуск, симметричный шлюзовому: меняются **и имя, и пароль**, старое имя перестаёт
находиться в каталоге сразу. Нужен по той же причине, что и у шлюза, только цена ошибки
другая: утёкший пароль канала — это чужие вызовы **за счёт клиента**, и без перевыпуска
единственным ответом на утечку было бы отключение канала целиком.

Пароль восстановить неоткуда: в базе лежит `MD5(имя:realm:пароль)`.

## `POST /node/directory` — ключ узла

Привязка `directory` для `mod_xml_curl`. Единственный обработчик проекта, который принимает
`x-www-form-urlencoded` и отвечает XML: у модуля нет ни JSON, ни произвольных заголовков.

**Код ответа всегда 200** — и когда запись есть, и когда её нет, и когда запрос не разобрался.
Любой другой код `mod_xml_curl` отбрасывает целиком и пишет ошибку в лог, то есть узел
остаётся без учётных записей вообще. Поэтому ошибок здесь нет как класса: всё непонятое —
это «записи нет», а причина уходит в лог control plane.

Запись есть:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
<document type="freeswitch/xml">
  <section name="directory">
    <domain name="sip.zvonix.ru">
      <user id="gw-a1b2c3d4e5f6">
        <params>
          <param name="a1-hash" value="…"/>
        </params>
        <variables>
          <variable name="zvonix_gateway" value="0198f3c4-…"/>
          <variable name="zvonix_gateway_type" value="goip"/>
        </variables>
      </user>
    </domain>
  </section>
</document>
```

Записи нет:

```xml
<document type="freeswitch/xml">
  <section name="result">
    <result status="not found"/>
  </section>
</document>
```

**Вход линии** (`pt-…`, [ADR-0054](../adr/0054-vhod-po-liniyam-goip.md)) отдаётся
тем же документом с переменной `zvonix_gateway_port`, и только у действующего шлюза
проверенного партнёра в режиме `port`. Вход самого шлюза в этом режиме — «записи нет»,
вход линии при `gateway` — тоже: два пути регистрации одного устройства дали бы два
набора, между которыми площадке не из чего выбирать.

**Неизвестная и отключённая записи отвечают одинаково.** Иначе по разнице ответов
заблокированный партнёр узнаёт, что его шлюз ещё числится в системе.

### Переменные канала

FreeSWITCH проставит их на всех вызовах этой учётной записи, и они приедут в запрос
маршрута. Так на узле не остаётся вообще никакого знания о том, чей это вызов.

| Переменная | У кого | Зачем |
|------------|--------|-------|
| `zvonix_gateway` | шлюз | Идентификатор шлюза |
| `zvonix_gateway_type` | шлюз | `goip` или `android` |
| `zvonix_gateway_port` | линия | Идентификатор порта — при входе по линиям |
| `zvonix_channel` | канал | Идентификатор канала: по нему запрос маршрута опознаёт линию |
| `zvonix_recording_required` | канал | Требуется ли запись |
| `zvonix_caller_id` | канал | Если задан |

### Отметка о регистрации

Успешный ответ проставляет шлюзу узел и время: по ним видно, где шлюз сейчас и жив ли он.
При входе по линиям отметка ставится порту, чей вход спрошен, и отбор кандидатов
смотрит на неё, а не на шлюз.
Это не подтверждение регистрации SIP — это факт запроса учётных данных, то есть попытки.
Настоящее состояние регистрации приходит событиями ESL и будет отдельно.

## SIM-карты

**Номер SIM и ICCID — персональные данные партнёра и в клиентский контур не попадают
никогда** ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)): по номеру клиент вышел бы
на партнёра напрямую в обход платформы. В журнале аудита номер маскируется: `7999*****11`.

### Объявленный оператор сверяется с фактическим

Оператора объявляет партнёр, а от этого значения зависит вся экономика вызова: SIM звонит
бесплатно только внутри своей сети ([ADR-0013](../adr/0013-opredelenie-operatora.md)).
Ошибка означает не «чуть дороже», а платный звонок с **каждого** вызова через эту SIM.

Поэтому собственный номер SIM прогоняется через тот же `OperatorResolver`, что и номера
назначения. Три исхода, и они разные:

| Ответ резолвера | Что происходит |
|-----------------|----------------|
| Подтверждён и совпал | Запись создаётся, проставляется `operator_confirmed_at` |
| **Подтверждён и не совпал** | **Отказ `400`** с обоими операторами в подробностях |
| Не подтверждён | Запись создаётся без отметки |

Третий случай — не то же самое, что второй: «источник не знает» и «источник возразил» —
разные утверждения, и второе не следует из первого.

## `POST /sim-cards` — роль `admin`

```json
{ "partnerId": "…", "operatorId": "…", "msisdn": "+7 916 123-45-67", "iccid": "897010…" }
```

`201` → `{ "sim": { "id", "partner_id", "operator_id", "msisdn", "iccid", "status",
"network_scope", "max_concurrent_calls", "operator_confirmed_at", "activated_at" } }`

Номер нормализуется: `8916…`, `+7 916 …` и `7916…` — один и тот же номер. **Номер
не уникален:** запись с тем же номером заводится сколько угодно раз, в том числе другим
партнёром ([ADR-0043](../adr/0043-partnyor-zavodit-svoyo-oborudovanie.md), «Ревизия: номер
SIM не уникален»). Лимиты от этого не слабеют: они защищают физическую карту, а она стоит
ровно в одном порту.

Заводится в состоянии `new`: в работу пускает человек.

**`operatorId` необязателен.** Без него оператора называет резолвер по самому номеру
([ADR-0013](../adr/0013-opredelenie-operatora.md)): подтверждённый источник — тот,
кто обслуживает номер сейчас, и карта сразу подтверждена; без него — владелец диапазона
по плану нумерации, и карта заводится **неподтверждённой**, ровно как с оператором,
названным партнёром (включить её без подтверждения нельзя). Номера нет и в плане —
`503` `dependency_unavailable` «Не удалось определить оператора номера». Указанный
`operatorId` по-прежнему сверяется, подтверждённое расхождение — `400`.

## `POST /sim-cards/:id/status` — роль `admin`

Жизненный цикл: `new → active → throttled → blocked → retired`.
`throttled` ставит порог отказов сети или администратор. Сама карта в `active`
не возвращается и партнёром не включается — только этим обработчиком
([ADR-0027](../adr/0027-porog-otklyucheniya.md), [ADR-0047](../adr/0047-kto-vyklyuchil-shlyuz.md)).
`blocked` — тоже. Списанную (`retired`) не возвращает и этот обработчик — `409`.

## `POST /sim-cards/:id/concurrency` — роль `admin`

```json
{ "maxConcurrentCalls": 2 }
```

**Только администратор.** Инвариант [DOMAIN.md](../DOMAIN.md): по умолчанию один вызов.
Партнёр заинтересован поднять значение и не увидеть последствий сразу — а последствие одно
и позднее: оператор блокирует SIM за поведение, не похожее на человеческое.

## `POST /sim-cards/:id/test-call` — роль `admin`

Тестовый звонок с любой карты ([ADR-0055](../adr/0055-testovyy-zvonok-s-sim.md)):
когда партнёр пишет «не работает». Тело, ответ и отказы — как у партнёра
([partner.md](partner.md), `POST /partner/sim-cards/:id/test-call`), кроме `404` за чужую
карту. Итог — `GET /test-calls/:id`, роли `admin`, `support`.

## Порты шлюза

**Порт — не канал.** Канал это линия клиента, порт — слот с SIM у партнёра.
Смешивать нельзя, см. [GLOSSARY.md](../GLOSSARY.md).

`POST /gateways/:id/ports` — объявить порт, `GET /gateways/:id/ports` — список,
`POST /gateway-ports/:id/sim` — поставить SIM или вынуть её (`{"simCardId": null}`).

Тело `POST /gateways/:id/ports` — либо `{ "portNumber": 3 }`, либо `{ "count": 4 }`:
четыре порта следующими номерами после наибольшего заведённого. Ответ —
`{ "port": первый, "ports": [все заведённые] }`. Счёт идёт под блокировкой шлюза, так что
два одновременных «добавить четыре» не посчитают от одного номера. Больше 256 портов
у шлюза — `409`.

**У SIP-транка портов нет:** к провайдеру регистрируемся мы, SIM в транке не бывает.
`POST /gateways/:id/ports` для транка отвечает `409` — иначе порт был бы строкой,
в которую вставляется карта, не звонящая никуда ([ADR-0047](../adr/0047-kto-vyklyuchil-shlyuz.md)).

**Одна SIM стоит ровно в одном порту.** Иначе она оказалась бы «свободна» дважды,
и одновременных вызовов на ней стало бы вдвое больше разрешённого. Попытка поставить
занятую SIM — `409` с названной причиной: `Эта SIM уже стоит в другом порту`,
и в `details` — `port_id` и `gateway_id`, где она стоит. Повторная установка той же SIM
в **тот же** порт отказом не считается: форма, отправленная дважды, не должна ругаться
на состояние, которое сама и создала. Повтор ничего не меняет и в журнал не пишется;
«вынуть» из пустого порта — тоже.

**Списанное в порт не ставится.** Списанную SIM в порт не поставить — `409`: в порту
она ожила бы для маршрутизации. Порт у списанного шлюза не завести — `409`: списанный
шлюз портов не держит.

**Одновременно со списанием шлюза** установка карты, «вынуть» и заведение порта дожидаются
списания и проверяют уже списанный шлюз: установка и заведение порта получают `409`,
«вынуть» из освобождённого порта — `201` без записи в журнал. Порядок блокировок —
[ADR-0048](../adr/0048-poryadok-blokirovok-portov.md).

**SIM переживает порт:** вынули — запись осталась со своей историей и счётчиками
и может переехать в другой шлюз.

SIM и шлюз обязаны принадлежать одному партнёру: иначе выручка от вызова уйдёт не тому.

Состояния порта — `unknown`, `idle`, `busy`, `fault`, `disabled`. Первые четыре проставляет
агент узла по данным оборудования, последнее — человек. Пока агента нет, порт остаётся
в `unknown`, и это **не** повод его не использовать: «о состоянии не отчитались»
и «неисправен» — разные утверждения.

## `GET /routing/sim-candidates?operatorId=…&recording=true` — роли `admin`, `support`

`200` → `{ "candidates": [ { "sim_card_id", "msisdn", "max_concurrent_calls",
"gateway_id", "gateway_type", "port_number", "port_state" } ] }`

Какие SIM вообще подходят под оператора. Разбор «почему у клиента не звонит» почти всегда
сводится к этому вопросу.

Кандидатом связка становится, только если выполнено **всё** сразу:

- SIM в состоянии `active` и принадлежит нужному оператору;
- SIM стоит в порту, порт в `unknown` или `idle`;
- шлюз `active`, партнёр `verified`;
- при `recording=true` — шлюз не `android`.

Проверяется одним запросом. Тот же набор условий, разложенный по нескольким чтениям,
разъезжается между ними, и вызов уходит на SIM, которую только что заблокировали.

**Одновременность на SIM здесь не проверяется.** Счётчик активных вызовов — состояние
времени выполнения, оно живёт не в этих таблицах ([ARCHITECTURE.md](../ARCHITECTURE.md),
счётчики лимитов). Этот запрос отвечает на вопрос «какие SIM вообще подходят»,
а не «какая свободна прямо сейчас».
