# Контракт: сообщения MAX — аккаунты партнёров

Основание — [ADR-0071](../adr/0071-soobscheniya-max.md). Этап 1: аккаунты партнёров, их цена и лимиты.
Этап 2: отправка клиентами, очередь, деньги, статусы доставки (ниже). Этап 3: SMPP — [smpp.md](smpp.md).

Провайдер доступа к мессенджеру нигде в этих ответах **не называется**: нет ни его имени, ни адресов,
ни идентификаторов инстансов, ни ключей. Для партнёра и клиента это «аккаунт MAX».

Вид аккаунта:

```json
{
  "id": "…", "label": "Основной", "status": "pending",
  "phone": null, "price": "0.45",
  "limit_per_minute": 10, "limit_per_day": 500,
  "state_checked_at": "…", "created_at": "…"
}
```

`status`: `pending` — заведён, QR не отсканирован; `active` — вошёл и на связи; `unavailable` — вышел из
MAX либо нет связи; `retired` — списан (в списках его нет). `price` — рублями строкой, пусто — не задана
(аккаунт сообщений не принимает). Пока продукт выключен настройкой `messaging.enabled`, партнёрские
обработчики отвечают, но заводить аккаунты нельзя.

## Кабинет партнёра

Только свои аккаунты; чужой — `404`, а не `403`: существование не выдаётся.

### `GET /partner/messenger/accounts`

`200` → `{ "enabled": true, "accounts": [ … ] }`. `enabled: false` — продукт выключен.

### `POST /partner/messenger/accounts`

```json
{ "label": "Основной" }
```

`201` → `{ "account": { … } }` в состоянии `pending`. Площадка создаёт инстанс у провайдера сама.
Отказы: `409` — продукт выключен, партнёр не допущен к работе или аккаунтов уже 20; `503` — провайдер
недоступен либо автоматическое заведение не настроено (тогда аккаунт заводит администратор).

### `GET /partner/messenger/accounts/:id/qr`

`200` → `{ "status": "qr", "image": "data:image/png;base64,…" }` — QR-код для входа
(Профиль → Устройства → Войти по QR-коду); `{ "status": "authorized" }` — уже вошёл (состояние обновлено);
`{ "status": "unavailable" }` — повторить позже. Код живёт недолго: кабинет запрашивает заново раз в 5 секунд.

### `PATCH /partner/messenger/accounts/:id`

```json
{ "label": "Рабочий", "price": "0.45", "limitPerMinute": 10, "limitPerDay": 500 }
```

Всё необязательно, но хотя бы одно поле нужно (`400`). `null` у `price`, `limitPerMinute`, `limitPerDay` —
снять. Цена — от 0,01 до 100 ₽; лимиты — целые от 1; в минуту не больше, чем в сутки (`400`). Журнал:
`messenger_account.terms_changed`, до и после.

### `DELETE /partner/messenger/accounts/:id`

`204`. Списание: аккаунт перестаёт принимать сообщения, инстанс у провайдера удаляется (платит за него
площадка). Необратимо. Повтор — `404`. Журнал: `messenger_account.retired`.

## Сотрудники

### `GET /messenger/accounts` — роли `admin`, `support`

`200` → `{ "accounts": [ { …вид аккаунта, "partner_id", "partner_name" } ] }` — все живые аккаунты.

### `POST /messenger/accounts` — роль `admin`

Ручное заведение по данным готового инстанса — пока нет партнёрского ключа провайдера или когда инстанс
заведён в кабинете провайдера:

```json
{ "partnerId": "…", "label": "Заведён вручную", "instanceId": "1101000001",
  "token": "…", "apiUrl": "https://…" }
```

`201` → `{ "account": { … } }`; состояние сразу сверяется с провайдером. **Ключ в ответ и в журнал не
попадает**, в базе хранится зашифрованным (`SECRET_KEY`, назначение `zvonix:messenger-token:v1`).

### `DELETE /messenger/accounts/:id` — роль `admin`

`204`. То же списание, что у партнёра, но любого аккаунта.

## Отправка сообщений (этап 2)

### Как это устроено

1. **Приём.** Сообщение принимается, если продукт включён, клиент работает, получатель — российский номер
   (приводится к виду `79001234567`), текст — 1…4000 знаков. Площадка выбирает **самый дешёвый рабочий
   аккаунт** допущенного партнёра (при равной цене — давно не работавший), фиксирует цену партнёра, наценку
   (`messages.markup_percent`, округление вверх до микроединицы) и сумму клиента, **списывает деньги и
   ставит сообщение в очередь одной транзакцией**: нет денег — нет сообщения (`409`, тот же запас и минус,
   что у звонков). Нет ни одного рабочего аккаунта с ценой — `503`. Повтор с тем же `externalId` возвращает
   прежнее сообщение без нового списания; тот же ключ с другим текстом или получателем — `409`.
2. **Отправка.** Воркер раз в 5 секунд берёт то, чему пора уходить. Между сообщениями одного аккаунта —
   пауза `messages.pace_seconds`; лимиты аккаунта в минуту и в сутки не превышаются — лишнее **ждёт**, а не
   отклоняется. Временный сбой — повтор через 1, 2, 4, 8 минут, после пяти попыток отказ.
3. **Возврат.** Окончательный отказ (`recipient_not_in_max`, `account_unavailable`, `wait_expired`,
   `platform`) возвращает деньги обратной проводкой (идемпотентно). Ждавшее дольше
   `messages.max_wait_minutes` отклоняется как `wait_expired`.
4. **Статусы доставки** приходят от провайдера на секретный адрес площадки: `sent` → `delivered` → `read`,
   только вперёд. Сообщение о том, что у получателя нет MAX, уже после отправки возвращает деньги.
5. **Текст — персональные данные**: стирается через `retention.messages_days` (по умолчанию 30 суток),
   строка с суммами и статусом остаётся.

Вид сообщения для клиента:

```json
{
  "id": "…", "external_id": "order-17", "to": "79001234567", "text": "Код 1234",
  "status": "queued", "failure_reason": null, "cost": "0.54",
  "created_at": "…", "sent_at": null, "delivered_at": null, "read_at": null
}
```

`cost` — списано, ₽; у не отправленного `null` (деньги возвращены). Партнёра, аккаунта, провайдера и доли
партнёра в ответе клиенту нет ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)).

### Кабинет клиента

- `GET /client/messages/price` → `{ "enabled": true, "price": "0.54" }` — сколько сообщение стоит сейчас;
  `price: null` — принять некуда.
- `GET /client/messages?status=&limit=&offset=` → `{ "messages": [ … ], "total": 3 }`.
- `POST /client/messages` `{ "to": "+7 900 123-45-67", "text": "…", "externalId": "…" }` → `201`
  `{ "message": { … } }` в состоянии `queued`.

### API клиента по ключу (`/v1`, [ADR-0044](../adr/0044-klientskiy-api.md))

`POST /v1/messages` (тело как выше, `201`), `GET /v1/messages`, `GET /v1/messages/:id`. Ключ — тот же,
что у вызовов; чужое сообщение — `404`.

### Сотрудники

`GET /messages?status=&limit=&offset=` (роли `admin`, `support`) → сообщения всех клиентов с деньгами
по трём счетам (`money.client`, `money.partner`, `money.margin`), `partner_id`, `account_id`, `attempts`.
**Текст сотруднику не отдаётся**: разбору хватает получателя, статуса и денег.

### Приём статусов от провайдера

`POST /webhooks/messenger/:secret` — без входа, но путь содержит секрет, выведенный из `SECRET_KEY`
(неверный — `403`). Площадка сама сообщает адрес инстансу при заведении аккаунта. Уведомления, которые нас
не касаются, принимаются молча (`200`).

### Акт и выписка

Списания за сообщения и возвраты идут в акте клиента и выписке партнёра **отдельными итогами**
(`message_charged`, `message_refunded`), а не строками движения ([reports.md](reports.md)).

## Проверка ключа провайдера

`POST /messenger/provider/test` (только администратор) → `200` `{ "ok": true, "message": "Ключ принят. Аккаунтов у
провайдера уже заведено: 3." }` либо `{ "ok": false, "message": "…" }`: ключ не задан, провайдер его не принял,
нет связи. Проверяется **сохранённый** ключ; ничего не создаётся и денег не тратится. Кнопка «Проверить ключ» —
в «Настройки площадки» → «Сообщения MAX». Провайдер в ответе не называется.

## Сверка состояния

Задача воркера `messaging.refresh-accounts` раз в минуту сверяет живые аккаунты с провайдером
(догоняющая, ADR-0020): `authorized` → `active`; вышел из MAX → `unavailable` (ждавший QR остаётся
`pending`); заблокирован → `unavailable`. Сбой провайдера состояние не меняет. Смена состояния пишется
в журнал (`messenger_account.status_changed`).

## Настройки

`messaging.enabled`, `messaging.provider_partner_url`, `messaging.provider_partner_token` (секрет),
`messages.markup_percent`, `messages.pace_seconds`, `messages.max_wait_minutes`, `retention.messages_days` —
[settings.md](settings.md).

## Что не проверено на живом провайдере

Формы ответов провайдера (создание инстанса, QR, состояние, номер) реализованы по его документации
и защищены от отклонений (неизвестное состояние не считается ни рабочим, ни сломанным), но живым
аккаунтом не проверялись: нужны партнёрский ключ и аккаунт MAX. Отдельно не проверено: какие именно коды
ответа провайдер возвращает для получателя без MAX (сейчас `400`, `404`, `422` считаются «получателя нет»,
остальное — временным сбоем с повтором).
