# Контракт: кабинет клиента

Что клиент видит и настраивает сам. Обоснование границы —
[ADR-0014](../adr/0014-vybor-partnera-klientom.md) (партнёр невидим),
[ADR-0018](../adr/0018-autentifikaciya.md) (доступ),
[ADR-0025](../adr/0025-razreshyonnye-operatory-kanala.md) (разрешённые операторы).

## Откуда берётся клиент

**Из сессии, и только из неё.** Ни один обработчик этого раздела не принимает
идентификатор клиента: административные пути начинаются с него (`/clients/:id/…`),
и открыть их роли `client` значило бы разрешить подставить чужой.

Учётная запись с ролью `client`, к которой клиент ещё не привязан, получает `404`
с сообщением «Клиент не найден»: это незавершённое заведение, и человек обязан увидеть,
что дело не в его настройках. Пустой ответ на этом месте выглядел бы как «у вас ничего
нет» — и был бы неправдой.

Все обработчики раздела — роль `client` и только она. Администратор сюда не ходит:
у него свои разделы, где клиент называется явно.

## Чего здесь нет и не будет

**Партнёра — ни в каком виде.** В вызове клиента нет ни партнёра, ни его псевдонима,
ни шлюза, ни SIM. Псевдонимы клиент видит только там, где сам задаёт порядок
(`GET /partner-aliases`); связать конкретный вызов с конкретным псевдонимом он не может.

Показывать псевдоним в строке вызова — открытый вопрос владельца («что клиент видит про
партнёра: цену, ASR, рейтинг»), и до ответа на него в клиентский контур не уходит ничего.

**Точной причины отказа на нашей стороне.** Причина переводится в клиентский набор
функцией `clientFailureReasonOf` из `@zvonix/shared`:

| Внутренняя причина | Что видит клиент |
|---|---|
| `destination_blocked`, `destination_invalid`, `operator_unconfirmed`, `operator_not_allowed`, `insufficient_funds`, `limit_exceeded` | как есть — это про него |
| `no_sim_available`, `no_coverage`, `no_tariff`, `recording_required`, `node_lost`, `internal_error`, `channel_unknown` | `platform` |

Причины первой строки клиент может исправить сам: пополнить счёт, поправить список
операторов, дождаться окна лимита. Вторая строка — сведения о ёмкости площадки: по ним
читалось бы, сколько у нас SIM и где мы их не держим. Факт отказа при этом виден,
скрывается только его устройство.

Список видимых причин перечислен **явно**, а не выведен вычитанием: новая внутренняя
причина обязана по умолчанию оказаться скрытой, а не показанной клиенту из-за того,
что её забыли внести в исключения. Свойство закреплено проверкой.

## `GET /client/account`

`200` →

```json
{
  "client": { "id": "…", "name": "Такси «Волна»", "status": "active", "created_at": "…" },
  "funds": { "balance": "9988.5", "overdraft_limit": "0", "held": "0", "available": "9988.5" }
}
```

Остаток и «доступно» отдаются вместе: по отдельности они порождают ровно тот вопрос,
ради которого сюда и приходят, — «деньги же есть, почему не звонит». Доступно = остаток
плюс разрешённый минус минус придержанное под идущие вызовы.

Состояние клиента здесь есть намеренно: «приостановлен» объясняет, почему не идут вызовы,
и без него человек ищет причину в своей АТС.

Заодно освобождает просроченные резервы — так же, как административный
`GET /clients/:id/funds`: зависший из-за потерянного CDR резерв иначе тихо съедает
доступное.

## `GET /client/entries?limit=100&offset=0`

`200` → `{ "entries": [ … ], "balance": "9988.5", "total": 2 }`

Тот же вид проводки, что и у администратора: видно **что произошло**, а не только сумма.
Потолок страницы — 200.

## `GET /client/channels`

`200` → `{ "channels": [ { "id", "name", "status", "recording_required", "caller_id" } ] }`

Свои линии. **До появления этого обработчика взять их идентификаторы было неоткуда** —
и потому настройки линии, открытые клиенту с самого начала, были ему недоступны.

Учётных данных SIP здесь нет: пароль восстановить неоткуда, а имя пользователя клиент
и так держит в настройках своей АТС. Копия того, что уже настроено, — лишний повод
считать её источником правды.

## `GET /client/calls`

Отбор: `status`, `channelId`, `destination`, `from`, `to`, `limit` (не больше 200),
`offset`. Пустое значение параметра означает «любое».

`destination` приводится к каноническому виду теми же правилами, что и на пути вызова:
`8…`, `+7…`, со скобками и пробелами — одно и то же. Ненормализуемый набор из цифр
принимается как есть: у отказа `destination_invalid` в назначении лежат цифры набранного
([ADR-0042](../adr/0042-diagnoz-po-nerazobrannomu-nomeru.md)), и увиденный в списке вызов
на `112` отбирается по `112`. Отвергается только набор без единой цифры.

`200` → `{ "calls": [ … ], "total": 137 }`

```json
{
  "id": "…", "destination": "79001234567",
  "status": "failed", "failure_reason": "insufficient_funds",
  "duration_seconds": null, "started_at": "…", "answered_at": null, "ended_at": "…",
  "region": "Республика Татарстан",
  "channel":  { "id": "…", "name": "Диспетчерская" },
  "operator": { "id": "…", "name": "ПАО «МегаФон»" }
}
```

Отбора по клиенту нет: он из сессии. Отбора по партнёру нет: партнёры клиенту
неразличимы. Отбора по причине отказа нет: причина в его ответах переведённая, и отбор
по внутреннему значению спрашивал бы о том, чего в ответах не бывает.

Чужой канал в `channelId` отсеивать не требуется — рядом стоит отбор по клиенту, и чужой
канал просто не даёт ни одной строки.

## `GET /client/prices?operatorId=…&seconds=60`

`200` →

```json
{
  "seconds": 60,
  "offers": [
    { "alias_id": "…", "display_name": "Партнёр 17", "termination_kind": "sim",
      "min_price": "1.8", "max_price": "2.4", "directions": 12 }
  ]
}
```

`seconds` — длительность вызова, на которой посчитаны цены (по умолчанию 60, потолок
3600). Она **возвращается вместе с ними**: без неё число ничего не значит. Тариф с шагом
в минуту и посекундный на вызове в 60 секунд стоят одинаково, а на вызове в 15 секунд —
вчетверо по-разному, и одна величина сравнивала бы несравнимое. Негодное значение даёт
умолчание, а не отказ: это сравнение цен, и опечатка в адресе не должна возвращать ошибку
вместо чисел.

Из чего клиент строит порядок. До этого обработчика он расставлял приоритеты **вслепую** —
по псевдониму, ничего не зная о стоимости.

**Цена — своя, а не тариф партнёра.** Чужая экономика клиенту не адресована, собственные
деньги — его дело. Считается стоимость **эталонного вызова в 60 секунд**: тариф это пять
чисел, и сравнение по одной лишь цене за минуту ставит рядом предложения, которые на деле
стоят по-разному ([ADR-0023](../adr/0023-koridory-cen.md) меряет коридор так же).

Диапазон, а не одно число: цена задаётся по направлениям, и у предложения их десятки.
`operatorId` сужает набор до одного оператора — тогда границы обычно совпадают.

Только подтверждённые партнёры: предлагать порядок вокруг того, кто не может принять
вызов, значит звать строить его вокруг пустого места. Партнёр называется **псевдонимом**
и только им ([ADR-0014](../adr/0014-vybor-partnera-klientom.md)).

Дешёвое сверху: список открывают, чтобы понять, кто дешевле, а не чтобы читать целиком.

## `GET /client/tariffs?operatorId=…`

`200` →

```json
{
  "tariffs": [
    {
      "alias_id": "…", "display_name": "Партнёр 17", "termination_kind": "sim",
      "operator_id": "…", "region": null,
      "billing_increment_seconds": 1, "minimum_duration_seconds": 0,
      "price_per_minute": "11.5", "connection_fee": "0",
      "examples": [
        { "seconds": 15, "amount": "2.875" },
        { "seconds": 30, "amount": "5.75" },
        { "seconds": 60, "amount": "11.5" }
      ]
    }
  ]
}
```

**Из чего складывается цена.** `GET /client/prices` отвечает «кто дешевле», этот
обработчик — «почему столько».

Цена вызова — плата за соединение плюс оплата времени, и время считается **шагами**:
`billing_increment_seconds` равный единице означает посекундно, шестидесяти — поминутно.
`minimum_duration_seconds` — первый оплачиваемый период целиком, а не нижняя граница
округления.

Суммы клиентские, наценка площадки уже внутри. `price_per_minute` и `connection_fee`
несут **процентную** часть наценки; фиксированная часть берётся за вызов и потому сидит
в `connection_fee`, а не в цене минуты, — иначе десятиминутный разговор платил бы её
десять раз.

`examples` — точная стоимость вызова названной длительности, посчитанная тем же кодом,
что и настоящее списание. Это **не** сумма показанных выше частей: наценка округляется
один раз на всю сумму вызова, а не по частям. Сравнивать предложения следует по ним.

## Что клиент настраивает сам

Обработчики общие с административными, владение проверяет служба; чужой канал отвечает
`404`, а не `403`, — по разнице ответов перебирались бы чужие идентификаторы.

- `GET|PUT /channels/:id/partner-priorities` — порядок **предложений**: партнёр
  по псевдониму вместе со способом терминации
  ([ADR-0040](../adr/0040-poryadok-terminacii-predlozhenie-i-cena.md),
  [routing.md](routing.md));
- `GET|PUT /channels/:id/allowed-operators` — разрешённые операторы
  ([telephony.md](telephony.md));
- `GET /partner-aliases` — из чего строится порядок;
- `GET /operators` — справочник для списка разрешённых.

Заведение линий и пополнение счёта клиенту недоступны и в кабинете не показываются:
и то и другое делает площадка, а кнопка без права обещала бы несуществующее.

## Ключи API

Доступ своей диспетчерской системы к `/v1` ([client-api.md](client-api.md)) клиент заводит
**сам** ([ADR-0044](../adr/0044-klientskiy-api.md)): никто, кроме него, не знает, из какой
системы он будет звонить и с каких адресов. Выпуск администратором остаётся для клиента,
у которого ещё нет кабинета.

### `GET /client/api-keys`

`200` → `{ "keys": [ … ] }`. Отозванные тоже: по ним разбирают, чем ходила система месяц
назад. Секрета в ответе нет и быть не может — в базе лежит его хеш.

### `POST /client/api-keys`

```json
{ "label": "Диспетчерская, основной сервер", "allowedIps": ["203.0.113.7"] }
```

`201` → `{ "key": { "id", "key_id", "secret", "expires_at" } }`.

**Секрет возвращается здесь и один раз** — там же, где клиент вставит его в свою систему.
Пока ключ выпускал администратор, секрет обязан был дойти до клиента перепиской.

`allowedIps` необязателен: диспетчерская может стоять за меняющимся адресом, и пустой
список — выбор клиента, а не недосмотр. Заполненный при этом остаётся единственной защитой
на случай утечки ключа: украденный вне этих адресов бесполезен.

Количество действующих ключей ограничено `CLIENT_API_KEY_LIMIT` — превышение `409`
с числом в `details.limit`. Отозванные не считаются: ротация «завёл новый, отозвал старый»
не должна упираться в предел.

### `DELETE /client/api-keys/:id`

`204`. Отзыв пометкой, а не удалением строки: иначе в журнале дыра ровно там, где чаще
всего и нужно разбираться. Действует немедленно.

Чужой ключ — `404`, а не `403`: клиент не должен узнавать даже того, что такой ключ
существует.

**Закрытие клиента отзывает все его ключи.** Человек, закрывая клиента, закрывает
и вход его диспетчерской — иначе остаётся дверь, о которой в этот момент никто не думает.
Приостановка ключей не трогает: она обратима, а отзыв нет.
