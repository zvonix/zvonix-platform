# Контракт: вход в кабинеты

Аутентификация людей — администраторов, партнёров и сотрудников клиентов.
Решение и его обоснование — [ADR-0018](../adr/0018-autentifikaciya.md).

Доступ машин (клиентский API, узлы АТС) сюда не входит: у него другие требования,
и он описывается отдельно к этапу 2.

## Общее

Токен передаётся заголовком `Authorization: Bearer <token>` либо cookie
([ADR-0037](../adr/0037-sessiya-v-brauzere.md)).
Все обработчики, кроме помеченных «без входа», требуют одного из двух.

### Cookie для браузера

`POST /auth/login` отвечает заголовком `Set-Cookie` **дополнительно** к токену в теле.
Кабинет пользуется только cookie: токен, доступный сценарию на странице, уносит первый же
скомпрометированный пакет во фронтенде, и уносит **наружу** — дальше он работает месяц
из чужой сети.

| | |
|---|---|
| Имя | `__Host-zvonix_session`, когда адрес кабинета (`WEB_BASE_URL`) на `https`; иначе `zvonix_session` |
| Признаки | `HttpOnly`, `Path=/`, `SameSite=Strict`, `Max-Age` по сроку сессии, `Secure` при `https` |
| Ставится | `POST /auth/login` |
| Снимается | `POST /auth/logout`, а также любой ответ `401` на запрос **с** негодной cookie |

Имя следует за `Secure`: префикс `__Host-` браузер отдаёт только тому, кто поставил
cookie с `Secure`, без `Domain` и с `Path=/`. Принимается **только** имя текущей
настройки — иначе в проде соседний поддомен мог бы поставить `zvonix_session` на весь
домен и подменить сессию.

**Заголовок `Bearer` главнее cookie.** Запрос, назвавший токен явно, разбирается
по нему: забытая в браузере cookie не должна молча подменять токен из заголовка.

### Заголовок `X-Zvonix-Web` — защита от подделки запроса

Запрос, который **меняет состояние** (всё, кроме `GET`, `HEAD`, `OPTIONS`) и опознан
**по cookie**, обязан нести заголовок `X-Zvonix-Web` с любым значением. Без него —
`403 permission_denied`.

Чужая страница поставить произвольный заголовок не может: это переводит запрос в разряд
требующих предварительной проверки CORS, на которую платформа не отвечает ничем.
Запрос с `Bearer` от требования освобождён — там защищаться не от чего.

Кабинет и API видны снаружи **по одному адресу**: обратный прокси отдаёт `/api/*` в API,
остальное — в Next. CORS не настраивается вовсе, и это часть решения:
`Access-Control-Allow-Credentials` вместе с cookie — способ раздать сессию тому,
кого не ждали.

Каждый ответ содержит заголовок `X-Correlation-Id`. Тот же идентификатор клиент может
прислать сам — тогда цепочка не разрывается на границе систем. Значение принимается,
только если состоит из `A-Za-z0-9._-` длиной 8–128 символов; иначе подставляется своё.

### Ошибки

Единый вид ответа при любом отказе ([ADR-0003](../adr/0003-obrabotka-oshibok.md)):

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Данные запроса не прошли проверку",
    "details": { "problems": ["password: не короче 12 символов"] },
    "correlation_id": "0f0a1b2c-..."
  }
}
```

| `code` | HTTP | Когда |
|---|---|---|
| `validation_failed` | 400 | Вход не прошёл схему |
| `unauthenticated` | 401 | Нет токена, токен недействителен, неверные адрес или пароль |
| `permission_denied` | 403 | Роль не подходит, запись не активна, вход временно закрыт |
| `not_found` | 404 | Объект не существует или не принадлежит вызывающему |
| `conflict` | 409 | Адрес уже занят |
| `rate_limited` | 429 | Слишком много попыток с одного адреса. В ответе — заголовок `Retry-After` |
| `internal` | 500 | Всё остальное |

`details` безопасно показывать пользователю. Значения полей туда не попадают:
в теле запроса лежат пароли.

## Обработчики

### `POST /auth/register` — без входа

Самостоятельная регистрация: учётная запись **участника рынка** (роль `member`) и первая
**заявка на кабинет** одной транзакцией ([ADR-0052](../adr/0052-odin-vkhod-dva-kabineta.md)).
Роль не выбирается — сотрудников площадки заводит только команда `admin:create`.

```json
{ "email": "ivan@example.com", "password": "не короче 12 символов",
  "fullName": "Иван Петров",
  "cabinet": "partner",
  "answers": { "region": "Свердловская область", "phone": "+7 900 000-00-00",
               "simCount": 16, "operators": ["МТС", "T2"] } }
```

`cabinet` — `client` (служба такси) или `partner`; `answers` — анкета **этого** вида,
лишние поля отвергаются:

| Кабинет | Поля анкеты |
|---|---|
| `client` | `companyName` (станет названием карточки), `city`, `phone`, `callsPerDay` — необязательно |
| `partner` | `region`, `phone`, `operators` (1–10 названий), `simCount` — необязательно |

Решение по заявке и вторая заявка из кабинета — [applications.md](applications.md).

`202`, тело пустое — **всегда**: и когда запись создана, и когда адрес занят.

Разница в ответе была бы способом перебрать адреса, и она уходит в письмо
([ADR-0029](../adr/0029-pochta.md)): новому адресу — «подтвердите адрес», занятому —
«на ваш адрес пытались зарегистрироваться». Так человек, чей адрес взяли чужие,
об этом узнаёт.

Запись создаётся со `status: "pending"` — войти по ней нельзя, пока администратор
не одобрит заявку (одобрение переводит запись в `active` и заводит карточку). **Подтверждение
адреса модерацию не заменяет:** оно ставит отметку `email_confirmed_at`, без которой заявку
не одобрить, а доступ по-прежнему открывает человек.

**Не больше десяти регистраций в час с одного адреса** (`429`). Считаются все попытки,
а не неудачные: блокировки учётной записи, которая прикрыла бы этот путь, здесь нет
по построению — записи ещё не существует.

### `GET /setup` — без входа

Нужен ли первый запуск ([ADR-0050](../adr/0050-ustanovka-odnoy-komandoy-i-pervyy-vhod.md)):
на площадке нет ни одной учётной записи с ролью `admin` — в любом состоянии.

```json
{ "required": true }
```

Кабинет по нему решает, показывать ли вместо входа форму первого запуска. Самостоятельно
зарегистрированные клиенты и партнёры первый запуск не закрывают — иначе чужая заявка
запирала бы площадку; заблокированный администратор закрывает.

### `POST /setup` — без входа

Первый администратор по **коду первого запуска** — его печатает выкладка
(`zvonix-deploy`), пока администратора нет.

```json
{ "code": "7Q4X-K9MB-2TZA", "email": "admin@example.com",
  "password": "не короче 12 символов", "fullName": "Иван Петров" }
```

`201` с `{ "user": … }` в том же виде, что у входа. **Сессии не выдаёт:** дальше —
обычный `POST /auth/login`.

| Ответ | Когда |
|---|---|
| `400 validation_failed`, в `problems` — `code: …` | Код не подходит. Регистр, пробелы и дефисы не важны |
| `400 validation_failed` | Почта, пароль или имя не прошли схему — как у регистрации |
| `409 conflict` «уже выполнен» | Администратор уже есть — даже при верном коде |
| `409 conflict` | Адрес занят другой учётной записью |
| `429 rate_limited` | Больше десяти попыток за 15 минут с одного адреса |

Код выводится из `SECRET_KEY` и суток UTC; принимаются коды текущих и прошлых суток —
живёт от суток до двух. Две одновременные формы с верным кодом заводят **одного**
администратора: проверка и заведение идут под одной блокировкой. Заведение пишется
в журнал действий как `user.first_admin_created` с адресом источника.

### `POST /auth/login` — без входа

```json
{ "email": "ivan@example.com", "password": "…", "totpCode": "123456" }
```

`200` → `{ "token", "expires_at", "user" }` плюс заголовок `Set-Cookie`.

Токен отдаётся один раз: в базе хранится только его SHA-256. Срок — 30 дней.

Токен в теле остаётся и при выданной cookie: это разные носители для разных
потребителей — `curl` некуда положить cookie, а браузеру нельзя давать токен
в руки. Кабинет токен из тела не сохраняет.

Неизвестный адрес и неверный пароль дают одинаковый `401` с одинаковым текстом
и за одинаковое время. Десять неудач подряд закрывают **учётную запись** на 15 минут (`403`).

**Двадцать неудач за 15 минут закрывают адрес источника** (`429` с полем
`retry_after_seconds`). Это второй рубеж, и он ловит другое: перебор по списку записей,
где на каждую приходится одна-две попытки и блокировка записи не срабатывает никогда.

Считаются **только неудачные** попытки, а удачный вход накопленное прощает. Иначе общий
адрес конторы, откуда утром входят тридцать человек, упирался бы в предел на ровном месте,
а перебору это не мешает: у перебирающего почти все попытки неудачны.

Счётчик ведётся по адресу источника, а адрес берётся из `X-Forwarded-For` **только
от доверенного прокси** (`TRUSTED_PROXIES`, по умолчанию — локальные адреса). Иначе предел
обходился бы сменой одной строки в запросе, а список разрешённых адресов машинного ключа
([ADR-0019](../adr/0019-dostup-mashin.md)) — вместе с ним.

Счётчик ведёт Redis. **При его недоступности проверка пропускается**, и в журнал идёт
ошибка. Довод: блокировка учётной записи живёт в PostgreSQL и продолжает работать,
а отказ на этом месте закрыл бы вход всем — включая администратора, которому и предстоит
чинить упавший Redis. Ограничение целиком выключается переменной
`AUTH_RATE_LIMIT_ENABLED`; в production это снятая защита.

Сессии, у которых истёк срок, **удаляются** фоновой задачей раз в час
([ADR-0020](../adr/0020-fonovye-zadachi.md)). Доступу они не мешают — срок проверяется
на каждом запросе, — но сессия хранит адрес и клиента, то есть данные о человеке.
След о входе и выходе остаётся в журнале аудита: там он и нужен.

### `POST /auth/logout`

`204` плюс `Set-Cookie` со снятием. Сессия помечается отозванной, токен сразу
перестаёт действовать.

Cookie снимается всегда, в том числе когда вошли по `Bearer`: лишний заголовок
машине безвреден, а забытая cookie после выхода — невыполненное обещание.

### `GET /auth/me`

`200` → `{ "user": … }`

Вид учётной записи по проводу — `snake_case`, как у всех ответов:

```json
{ "id": "…", "email": "ivan@example.com", "full_name": "Иван Петров",
  "role": "member", "status": "active", "created_at": "2026-09-01T10:00:00.000Z" }
```

Роли: `admin`, `support` — сотрудники площадки; `member` — участник рынка, чьи кабинеты
определяет владение карточкой ([ADR-0052](../adr/0052-odin-vkhod-dva-kabineta.md)).
`client` и `partner` — прежние значения участника: миграция `0032` переводит их в `member`,
из перечисления они уйдут следующим выпуском.

### `GET /me/cabinets`

Какие кабинеты открыты вошедшему:

```json
{ "cabinets": {
    "client":  { "id": "…", "name": "Такси «Бриз»", "status": "active" },
    "partner": { "id": "…", "display_name": "Партнёр 31", "status": "pending" } } }
```

Нет карточки — `null`. Сотруднику площадки оба `null`: кабинетов у него не бывает.
Живёт в модуле биллинга, а не в `/auth/me`: «чья это карточка» знает только он.

**Доступ к собственному контуру** (`/client/*`, `/partner/*` и общие с сотрудниками
обработчики клиента и партнёра) открывает владение карточкой, а не роль. Участнику без
нужной карточки — `403` с текстом «Кабинет клиента не подключён» /
«Кабинет партнёра не подключён» и `details.cabinet`.

### `GET /auth/sessions`

`200` → `{ "sessions": [ { "id", "current", "ip", "user_agent",
"created_at", "last_seen_at", "expires_at" } ] }`

Только свои действующие сессии. Хеш токена не отдаётся никогда.

### `DELETE /auth/sessions/:id`

`204`. Чужая сессия даёт `404`, а не `403`: иначе по разнице ответов проверяется
существование чужих сессий.

### `GET /users` — роли `admin`, `support`

Учётные записи по отбору. **Единственный способ увидеть заявку на самостоятельную
регистрацию:** она создаётся со статусом `pending`, и `PATCH /users/:id/status` требует
идентификатора, который до этого обработчика взять было неоткуда, кроме как из базы.

Поддержке доступен: разбор «почему человек не может войти» начинается здесь — видно
и состояние записи, и блокировку после неудачных попыток.

Параметры (все необязательные, **пустое значение означает «любое»**):

| Параметр | Значение |
|---|---|
| `role` | Одна из ролей. Неизвестная — `400` |
| `status` | Одно из состояний. Неизвестное — `400` |
| `email` | Часть адреса, регистр не важен. Знаки шаблона `%` и `_` экранируются |
| `limit` | Размер страницы, по умолчанию 100, потолок 200 |
| `offset` | Смещение страницы |

Мусор в `limit` и `offset` даёт умолчание, а не отказ: размер страницы ни на что
не влияет, и опечатка в адресе не должна прятать данные. С `role` и `status` иначе —
там молчаливая подмена показала бы не тот список.

```json
{
  "users": [
    { "id": "…", "email": "petr@example.com", "full_name": "Пётр Заявкин",
      "role": "member", "status": "pending",
      "created_at": "2026-09-07T09:00:00.000Z",
      "email_confirmed_at": null, "totp_enabled": false,
      "last_login_at": null, "locked_until": null }
  ],
  "total": 137
}
```

Свежие сверху: новая заявка на регистрацию — то, ради чего на этот список чаще всего
и приходят. `total` — полное число подходящих записей, а не размер страницы.

**`email_confirmed_at` — главный вопрос при разборе заявки.** Подтверждение адреса
доступ не открывает, но неподтверждённый адрес означает, что заявку подал кто угодно.
**`locked_until`** отвечает на «почему человек не может войти, пароль же верный».

### `PATCH /users/:id/status` — только `admin`

```json
{ "status": "active" }
```

`200` → `{ "user": … }`

Допустимые значения: `pending`, `active`, `suspended`, `disabled`.
Перевод в любое состояние, кроме `active`, немедленно закрывает все сессии этой записи.

Два отказа, оба `409`:

- **своя учётная запись** — администратор не меняет состояние самому себе. Одно неверное
  нажатие закрыло бы все его сессии разом, а вернуть его мог бы только другой
  администратор;
- **из `disabled`** — состояние окончательное, как `closed` у клиента и партнёра.
  Восстановления нет: заводится новая учётная запись, и прежний адрес для неё занят,
  поэтому нужен другой.

Повтор того же состояния — `200` без изменений и без записи в журнал.

## Восстановление пароля и подтверждение адреса

Обоснование — [ADR-0029](../adr/0029-pochta.md). Письмо кладётся в базу **той же
транзакцией**, что и токен, а уходит фоновым проходом воркера. Пока `mail.host` пуст,
письма копятся в таблице и не уходят: система работает, а восстановление пароля молча
не работает — это видно по растущей таблице и предупреждению воркера. Настраивается
в админке ([docs/api/settings.md](settings.md)), а не переменными окружения.

### `POST /auth/password-reset` — без входа

```json
{ "email": "ivan@example.com" }
```

`202`, тело пустое — **всегда**, независимо от того, есть ли такая запись. Ссылка
действует два часа и срабатывает один раз. Новая заявка гасит предыдущую ссылку: письмо
недельной давности не должно работать наравне со свежим.

Не больше пяти заявок в час с адреса источника (`429`): каждая — письмо, и без предела
чужой ящик заваливается письмами от нашего имени.

### `POST /auth/password-reset/confirm` — без входа

```json
{ "token": "…из письма…", "newPassword": "не короче 12 символов" }
```

`204`. Закрываются **все** сессии, включая текущую: пароль восстанавливают, когда доступ
потерян, и оставить живой чужую сессию значит не сделать ничего.

Просроченный, использованный и выдуманный токен отвечают одинаково — `401`: разница
сообщала бы, что такой токен когда-то существовал.

### `POST /auth/email/confirm` — без входа

```json
{ "token": "…из письма…" }
```

`204`. Ставит `email_confirmed_at`. **Доступ не открывает** — партнёра допускает
администратор, и связать это с почтой значило бы пустить в систему любого, у кого есть
почтовый ящик. Ссылка действует сутки и срабатывает один раз.

### `POST /auth/email/resend`

`202`. Повторное письмо тому, кто уже вошёл. Адрес уже подтверждён — `409`.

Не больше пяти обращений в час **по учётной записи** — смена адреса источника предела
не снимает. Превышение и исчерпанный предел писем на адрес отвечают `429` с честным
`retry_after_seconds`: сюда приходят с действующей сессией, скрывать нечего, а молчание
человек прочтёт как «письмо ушло».

### Предел писем на один адрес

Не больше **десяти писем в час на один адрес получателя**, независимо от того, каким
путём они порождены ([ADR-0030](../adr/0030-predel-pisem-na-adres.md)). Ограничение
частоты по адресу источника от заваливания одного ящика не спасает: адресов источника
у ботнета много, а цель одна, — и платит за это репутация нашего отправителя.

Одиннадцатое письмо за час **не отправляется**. Ответ при этом не меняется нигде, кроме
`POST /auth/email/resend`: регистрация и запрос восстановления обязаны отвечать `202`
независимо ни от чего, иначе по ответу перечисляются адреса.

Заявка, чьё письмо не уйдёт, **не гасит действующую ссылку**: место на адрес
спрашивается до записи токена. Иначе заваливание ящика заодно лишало бы человека
возможности восстановить пароль.

## Проверка «я не робот»

`POST /auth/register`, `POST /auth/login` и `POST /auth/password-reset` принимают поле
`captchaToken`. Нужен ли он — решает настройка площадки; форма узнаёт это из
`GET /auth/captcha`. Полный контракт и поведение при недоступности сервиса —
[docs/api/settings.md](settings.md), раздел «Капча».

Коротко о главном: предел частоты проверяется **раньше** капчи, а недоступная проверка
запрос **пропускает** и поднимает тревогу — отказ на этом месте закрыл бы вход всем,
включая администратора.

## Второй фактор и смена пароля

Обоснование — [ADR-0028](../adr/0028-vtoroy-faktor.md).

### `POST /auth/password`

```json
{ "currentPassword": "…", "newPassword": "не короче 12 символов" }
```

`200` → `{ "revoked_sessions": 3 }`

**Текущий пароль обязателен:** украденная сессия иначе превращается в украденную учётную
запись одним запросом. Неверный — `401`; не больше десяти попыток за 15 минут на запись.

**Прочие сессии закрываются, текущая остаётся.** Пароль меняют, когда подозревают, что им
завладели, и оставить чужую сессию живой значит не сделать ничего. А выкинуть человека
из устройства, за которым он только что сменил пароль, — способ научить его пароли
не менять.

### `POST /auth/totp`

`200` → `{ "secret": "JBSWY3DPEHPK3PXP", "otpauth_uri": "otpauth://totp/Zvonix:…" }`

Начинает подключение. **Секрет отдаётся один раз и только здесь**: в базе он лежит
зашифрованным, восстановить его неоткуда.

До подтверждения кодом фактор **не действует**: иначе человек запер бы себя, не проверив,
что аутентификатор показывает верные коды. Повторный вызов заменяет неподтверждённый
секрет новым. Если фактор уже подключён — `409`.

### `POST /auth/totp/confirm`

```json
{ "code": "123456" }
```

`204`. Неверный код — `400`, фактор остаётся выключенным.

Шаг, которым подтвердили подключение, считается использованным: следующий вход попросит
код уже из другого окна. Так работает запрет повторного использования, а не ошибка.

### `DELETE /auth/totp`

```json
{ "password": "…", "code": "123456" }
```

`204`. Спрашиваются **и пароль, и код**: отключение — это снятие защиты, и одной
украденной сессии для него быть недостаточно.

### `DELETE /users/:id/totp` — роль `admin`

`204`. Путь назад при потерянном телефоне.

Кодов восстановления нет намеренно: это ещё один секрет, который люди хранят в заметках
рядом с паролем, а его правильная реализация больше самого второго фактора. У площадки
есть администратор — он и есть путь назад, и его действие остаётся в журнале.

### Как второй фактор виден на входе

Требование кода сообщается **только после верной сверки пароля**: иначе по ответу видно,
у кого фактор включён, то есть кого имеет смысл атаковать иначе.

`401` с `details.totp_required = true` означает «пароль верный, нужен код». Неверный код —
такая же неудача входа, как неверный пароль: считается и счётчиком по адресу,
и блокировкой записи.

Код действует ±30 секунд от своего окна — часы на телефоне уходят, и фактор, отвергающий
верный код из-за пятнадцати секунд расхождения, люди выключают. Один код принимается
**один раз**.

### Что лежит в базе

`totp_secret` — зашифрованный AES-256-GCM ключом, выведенным из `SECRET_KEY`. Смысл ровно
один: утечка одной только базы не даёт генерировать коды. Цена названа в ADR — потеря
`SECRET_KEY` означает потерю вторых факторов у всех, и сбрасывать их будет администратор.

## Проверки состояния — без входа

- `GET /health/live` — процесс жив, зависимости не проверяются. Ошибка означает,
  что процесс надо перезапускать.
- `GET /health/ready` — готов принимать трафик, проверяется база. `503` означает,
  что узел надо вывести из балансировки, но не перезапускать.

## Версия выпуска — только сотрудникам

`GET /health/version` — роли `admin` и `support`; без входа `401`, клиенту и партнёру `403`.
Номер выпуска подсказывает, какие известные уязвимости пробовать, поэтому он не открыт,
как проверки выше.

```json
{ "version": "v0.1.3", "commit": "196005da2974…", "builtAt": "2026-09-22T12:00:00.000Z" }
```

Значения берутся из файла `RELEASE` в корне архива выпуска (`scripts/release-pack.mjs`)
и читаются один раз при старте. Вне выпуска — в разработке и тестах — файла нет, и все три
поля `null`: версия неизвестна, а не выдумана. Кабинет показывает её в углу панели
разделов — «версия v0.1.3» или «сборка не из выпуска».
