## Что это

Площадка терминации исходящих голосовых вызовов через GSM-шлюзы.
**Клиенты** (службы такси) звонят, вызов уходит на шлюз одного из **партнёров**
(физлица с SIM и GOIP), с баланса клиента списывается стоимость, партнёр получает долю,
платформа — комиссию. Админ задаёт коридоры цен, комиссию и лимиты.

Внимание к терминам: **канал** — это линия клиента, **порт шлюза** — слот с SIM у партнёра.
Смешивать нельзя, см. [docs/GLOSSARY.md](docs/GLOSSARY.md).

## Стек

Полностью TypeScript ([ADR-0008](docs/adr/0008-stek.md)). Монорепозиторий на pnpm workspaces.

- Рантайм: Node.js 22 LTS · TypeScript 5 в строгом режиме · pnpm
- Бэкенд: NestJS · zod для схем, общих с фронтендом
- Фронтенд: Next.js (App Router) · TanStack Query · shadcn/ui
- Данные: PostgreSQL 16 · Drizzle ORM + drizzle-kit · Redis 7 · MinIO (записи)
- Фоновые задачи: BullMQ
- Телефония: FreeSWITCH ([ADR-0009](docs/adr/0009-programmnaya-ats.md)), `mod_xml_curl` за маршрутом, ESL для событий
- Android-приложение партнёра: Kotlin
- Разработка: **WSL2 / Ubuntu 24.04**. Прод: **Ubuntu**. См. [ADR-0007](docs/adr/0007-lokalnaya-sreda.md).

## Структура

```
apps/
  api/     — NestJS: HTTP API, маршрутизация, доменные модули
  web/     — Next.js: админка, кабинеты клиента и партнёра
  worker/  — BullMQ: сверка CDR, выплаты, агрегация ASR, резервы, обновление MNP
  esl/     — потребитель событий FreeSWITCH (долгоживущее соединение)
  agent/   — агент узла, собирается в самодостаточный бинарник
packages/
  shared/  — типы, zod-схемы, доменные ошибки, работа с деньгами
  db/      — схема Drizzle и миграции
  config/  — модуль конфигурации (ADR-0002)
  logger/  — логгер (ADR-0004)
node/      — конфигурация FreeSWITCH и скрипт установки узла
android/   — приложение партнёра (Kotlin)
docs/      — документация (см. ниже)
scripts/   — check.sh: единая точка проверки проекта
.github/   — CI: те же проверки, но на Ubuntu
.claude/   — конфигурация Claude Code: settings.json, commands/, skills/
.mcp.json  — MCP-серверы проекта
.env.example — все переменные окружения, которые читает приложение
```
Доменные модули — в `apps/api/src/modules/`, поимённо совпадают с таблицей компонентов

- **playwright** — запуск браузера, E2E-сценарии, скриншоты.
- **chrome-devtools** — отладка фронтенда, сеть, профилирование производительности.
- **git** — операции с историей репозитория.
- **shadcn** — компоненты shadcn/ui для `apps/web`.
- **@21st-dev/magic** — генерация UI-компонентов React.

Ключи MCP лежат в `.claude/settings.local.json` (не в git). В `.mcp.json` — только ссылки
на переменные окружения. Не переносить ключи в файлы, попадающие в репозиторий.

## Правила работы

1. **Контекст перед действием.**
   Перед изменением кода — понять затрагиваемую область: архитектуру, связанные файлы,
   зависимости, существующие реализации. Уже прочитанное в этой сессии не перечитывать.

2. **Не плодить дубли.**
   Сначала искать существующее решение (поиск по домену и именам), потом писать новое.
   Расширить существующее лучше, чем создать параллельное. Следовать сложившимся паттернам
   проекта, даже если лично мне привычнее иначе.

3. **Спрашивать по порогу, а не по любому поводу.**
   Остановиться и спросить, если решение: необратимо; меняет архитектуру, схему БД или
   публичный контракт; либо варианты дают существенно разный результат.
   Мелкие развилки — решать самому и обозначить принятое допущение одной строкой.
   Если задача противоречит архитектуре или ранее принятому ADR — не реализовывать,
   сначала объяснить конфликт и предложить вариант.

4. **Production-ready, но без переусложнения.**
   Да: полная обработка ошибок, валидация входных данных, безопасность, масштабируемость,
   логирование, тесты на новое поведение.
   Нет: заглушки и «пока так», молчаливое проглатывание исключений, абстракции «на будущее»,
   слои ради слоёв. Правильное решение — самое простое из тех, что решают задачу полностью.

5. **Целевая ОС — Linux, всегда.**
   Разработка ведётся в WSL2 (Ubuntu 24.04), прод — Ubuntu. Код, скрипты и команды
   пишутся под Linux; Windows-специфичных путей и зависимостей быть не должно.
   Пути — только через API работы с путями. Имена файлов не различаются регистром
   (проверяется в CI). Переводы строк — LF (см. `.gitattributes`).

6. **Проверка — это запуск, а не обещание.**
   После изменений прогнать полную проверку и показать вывод.
   Не заявлять «ошибок нет», если проверка не запускалась. Если запустить невозможно —
   сказать об этом прямо и перечислить, что осталось непроверенным.

7. **Отчёт после задачи** — кратко и по делу:
   что сделано → что проверено и как → что осталось / не доделано → найденные проблемы
   с указанием `файл:строка`.
   Побочные наблюдения — не больше 3–5 пунктов и только реальные проблемы в затронутом коде.
   Идеи новых фич — в [TASKS.md](TASKS.md), не в отчёт.
   Полный аудит проекта — отдельно, по команде `/audit`.

8. **Контекст обрывается без предупреждения.**
   Сессия может закончиться в любой момент, и всё, что я знаю только из разговора, исчезнет.
   Поэтому важное фиксируется в файлах **сразу, а не в конце**:
   - решение принято → ADR, до начала реализации;
   - выяснен факт о внешней системе, API, оборудовании, ограничении → в `docs/`;
   - задача разбита на шаги → шаги в `TASKS.md`, отмечать по мере выполнения;
   - работа прервана на середине → строка в `TASKS.md` о том, где остановились и почему.
   Проверка: «если сессия оборвётся прямо сейчас, сможет ли следующая продолжить с этого
   места по файлам?» Если нет — сначала записать, потом продолжать.

9. **Документация — часть задачи.**
   Изменилось поведение или контракт → обновить `docs/`.
   Принято архитектурное решение → новый ADR в `docs/adr/`.
   Появился незакрытый хвост → строка в `TASKS.md`, а не безымянный `TODO` в коде.

## Доменные правила, нарушение которых стоит денег

- **Деньги — только `BigInt` в микроединицах** (1 руб = 1 000 000). `number` в денежных
  вычислениях — ошибка линтера, а не замечание. Округление — только при фиксации CDR.
- **Баланс меняется только проводкой** в модуле `billing`. Прямая запись в остаток запрещена.
- **Оператор номера — только через `OperatorResolver`** ([ADR-0013](docs/adr/0013-opredelenie-operatora.md)).
  Определять по префиксу нельзя: из-за MNP это неверный оператор.
- **Неподтверждённый оператор не идёт на SIM с `network_scope = on_net_only`.**
  Это не потеря маржи, а списание денег партнёра вне пакета и сожжённая SIM.
- **Канал с `recording_required` не маршрутизируется на шлюз типа `android`** —
  там запись технически невозможна ([ADR-0012](docs/adr/0012-mobilnoe-prilozhenie.md)).
- **Номера абонентов и записи разговоров — персональные данные.** Номера маскируются в логах,
  записи — только в объектном хранилище с подписанными ссылками и аудитом обращений.
- **Тарификация идемпотентна по идентификатору вызова.** Повторный CDR не создаёт вторых
  проводок — узел может слать его повторно, это штатный режим.

## Никогда

- Не коммитить секреты, `.env`, ключи, дампы с реальными данными.
- Не менять схему БД и публичные контракты без ADR и подтверждения.
- Не глушить линтер и типы ради «чтобы прошло» (`type: ignore`, `eslint-disable`, `any`)
  без обоснования в комментарии рядом.
- Не делать `git push`, `git commit`, деплой и миграции на проде без явной просьбы.
- Не оставлять закомментированный «на всякий случай» код — для этого есть git.
